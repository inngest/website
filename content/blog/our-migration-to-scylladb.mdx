If you've read our [FoundationDB series](/blog/migration-to-foundationdb-part-1?ref=blog-our-migration-to-scylladb), you know the queue team is moving Inngest's queue onto FoundationDB. If you haven't read it yet, it's worth your time.

Meanwhile, the state store has already moved.

Today, the state of every in-flight function run lives in [ScyllaDB](https://www.scylladb.com/), in our own data centers. AWS MemoryDB doesn't hold run state anymore. No customer changed a line of code or a setting, and no run lost its state on the way.

## What's the state store?

Every Inngest function run has a memory. When a [step](/docs/durable-execution/primitives/step-run?ref=blog-our-migration-to-scylladb) finishes, its output has to live somewhere the next step can read it. When a run [sleeps](/docs/durable-execution/primitives/step-sleep?ref=blog-our-migration-to-scylladb) for three days, [waits for an event](/docs/durable-execution/primitives/step-waitforevent?ref=blog-our-migration-to-scylladb), or [retries](/docs/durable-execution/guides-and-advanced/error-handling/retries?ref=blog-our-migration-to-scylladb) after a crash, everything it has done so far has to survive. That place is the state store.

The queue decides *when* your code runs. The state store remembers *what it has already done*. Both are on the critical path of every step of every run.

![Your functions talk to the Inngest Executor. The queue decides when a step runs. Run state used to live in AWS MemoryDB; it now lives in ScyllaDB in our data centers.](/assets/blog/our-migration-to-scylladb/state-store.png)

## Why move at all?

For years the state store ran on a sharded AWS MemoryDB cluster. It's Redis-compatible and fast, and it served us well. The problem was that memory was the unit of capacity. Every byte of in-flight state had to sit in RAM, so more traffic meant more shards. Adding a shard took hours to provision, and then slot rebalancing had to finish before it helped. And we paid for the memory whether we used it or not.

Our workload doesn't make this easier. It's write-heavy and delete-heavy: almost everything we write is deleted soon after. Most runs finish in seconds, but some sleep for days or months. We wanted something durable, that scales horizontally, and that our own team could run. We weren't looking for the best database in the world, just a way off MemoryDB. We eventually settled on ScyllaDB.
