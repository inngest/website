# Slack and GitHub

> Talk to your agent in Slack, and work with it on issues and pull requests, right in the thread.

Slack is one route, one trigger and a set of tools. GitHub works the same way.

- **One route.** Signatures are checked; only messages meant for the agent get through. [Route →](#add-the-route)
- **DMs, mentions and replies.** No channel list to keep. [Trigger →](#start-from-slack)
- **Post, ask and show progress.** Three tools, for the model and for scripts. [Tools →](#post-ask-and-show-progress)
- **Post anywhere.** A channel, a person or a message link. [Destinations →](#post-somewhere-else)
- **Your own rules.** Replace the default, or feed the bridge from Socket Mode. [Rules →](#set-your-own-rules)
- **Pull requests too.** The same pieces on GitHub. [GitHub →](#work-on-github)

## Add the route

`slack.bridge()` is the route Slack sends messages to. It's a Web handler, so it mounts in any framework.

import { slack } from "inngest/experimental/agents";

Three kinds of message reach the agent: a direct message, a message that mentions it in any Slack channel it is in, and a reply in a thread it already answered. Everything else is dropped at the bridge and never stored. Bots, including the agent itself, are ignored unless the bridge sets `allowBots: true`.

## Start from Slack

`slack.thread()` covers every channel the app is in, plus DMs. List channels to limit it:

```typescript
triggers: [slack.thread({ in: ["C0123ABC", "C0456DEF"] })],
```

The model reads a message as `[Ana] can you check order 7?`, not as JSON. The thread's key is in the event as `event.data.threadKey`, a plain field that `waitForEvent` and `cancelOn` can match on. [Threads and memory →](/docs/labs/agents/threads-and-memory?ref=docs-labs-agents-slack-and-github)

The SDK's own writes (`me.post()`, the status line and the default answer) use `SLACK_BOT_TOKEN`. `slack.thread({ token })` takes a string, a function or `secret()` instead.

Besides `slack/message`, the bridge sends `slack/reaction`, `slack/action`, `slack/view` and `slack/stop`. Each carries `threadKey`.

## Post, ask and show progress

`slack.tools()` gives the model three tools, and sandbox code calls the same ones by name. They post in the Slack thread the run came from.

<AnnotatedCode>

```js {{ title: "ship.js" }}
const { tools } = require("inngest_tools");

const main = async () => {
  await tools.slack_progress({
    id: "ship",
    title: "Shipping",
    status: "running",
  });

  const answer = await tools.slack_ask({
    question: "Ship it?",
    options: ["yes", "no"],
  });

  await tools.slack_post({ text: `You said ${answer}.` });
};

main();
```

The same `id` updates the task.
</Annotation>

<Annotation id="ask" lines="10-13" tease="waits in a script" title="slack_ask" href="#gotchas" linkText="Gotchas">
In a script the call waits and gives the answer as a string.
</Annotation>

<Annotation id="post" lines="15" tease="plain text" title="slack_post" href="/docs/labs/agents/handlers?ref=docs-labs-agents-slack-and-github#post-in-the-thread" linkText="Post in the thread">
Lands in the same thread as `me.post()`.
</Annotation>

</AnnotatedCode>

```typescript
await sandboxes.work.commands.run("ship", "node ship.js", {
  tools: { ...slack.tools() },
});
```

When the model calls `slack_ask`, it carries on without waiting. The answer arrives later as a message in its inbox. [Inboxes →](/docs/labs/agents/inboxes?ref=docs-labs-agents-slack-and-github)

Posts use Slack's markup, so links and mentions work. Broadcast mentions in the model's text, such as `<!channel>`, do nothing. The SDK sets Slack's status line while the agent works.

```typescript
await me.post(
  "Deployed. <@U024BE7LH>, see <https://acme.test/deploys/7|deploy 7>.",
);
```

## Post somewhere else

Every Slack tool takes an optional `to`: `#channel`, `@person` or a Slack message link. A cron run has no Slack thread, so set a default.

import { agents } from "../client";
import { claude } from "../models/claude";

export const digest = agents.agent({
  id: "digest",
  triggers: [{ cron: "TZ=UTC 0 9 * * 1-5" }],

  system: "Summarise yesterday's deploys and post it with slack_post.",

## Set your own rules

A `gate` replaces the default rule. A message it rejects never becomes an event. If you run your own Socket Mode connection, give each payload to `bridge.handle()`; the SDK never opens a socket.

{/* not type-checked: slack.bridge({ gate }) and bridge.handle(payload) */}
<AnnotatedCode>

```typescript {{ title: "inngest/slack/bridge.ts" }}
import { secret } from "inngest/experimental";
import { slack } from "inngest/experimental/agents";
import { inngest } from "../client";

export const bridge = slack.bridge({
  client: inngest,
  signingSecret: secret("SLACK_SIGNING_SECRET"),
  gate: ({ message, bot }) => {
    return message.text.includes(`<@${bot.userId}>`);
  },
});

export const onSocketEvent = async (payload: unknown) => {
  await bridge.handle(payload);
};
```

<Annotation id="gate" lines="8-10" tease="replaces the default rule" title="gate" href="#gotchas" linkText="Gotchas">
Gets the message, the thread (`key` and `history()`) and the bot's own `userId`, and returns a boolean or a promise of one. This one passes only mentions.
</Annotation>

<Annotation id="handle" lines="13-15" tease="no signature check" title="handle" href="#how-it-works" linkText="How it works">
For a connection you already trust. The gate and thread key behave as over HTTP.
</Annotation>

</AnnotatedCode>

## Work on GitHub

`github.bridge()` verifies `X-Hub-Signature-256` and sends `github/<event>` events, such as `github/issue_comment`. A redelivered webhook is dropped.

{/* not type-checked: github.bridge({ client, secret }) as a Web handler */}
```typescript {{ title: "app/api/github/route.ts" }}
import { secret } from "inngest/experimental";
import { github } from "inngest/experimental/agents";
import { inngest } from "../../../inngest/client";

export const POST = github.bridge({
  client: inngest,
  secret: secret("GITHUB_WEBHOOK_SECRET"),
});
```

`github.thread()` is the trigger. Each issue or pull request is one thread, keyed by its URL. Without `events` it triggers on `issues`, `issue_comment`, `pull_request`, `pull_request_review` and `pull_request_review_comment`. The event's data is GitHub's webhook payload plus `threadKey`, and the model reads a comment as `[ana-dev] please review`.

## Gotchas

- **Anyone in the thread can answer an ask.** Nothing checks who.
- **A `gate` replaces the default rule.** It has to keep the direct messages and mentions you still want.
- **`to` is needed without a Slack thread.** A cron run, `start()` or a GitHub thread has none, so the model gets an error that names `to`.
- **Messages travel with their full text.** Not as a pointer, and not encrypted.
- **Misconfigured writes warn.** A bad token or missing scope on a write you didn't await becomes a warning on the trace and never fails the run. An awaited write throws.
- **GitHub has no status line.** A call with no GitHub form warns once.

## How it works

- Each bridge sends one event per message meant for the agent, then answers the sender. A Slack redelivery is one event, because the event id is Slack's `event_id`; GitHub's is `X-GitHub-Delivery`.
- The agent marks a Slack thread as its own when it first posts there. The bridge reads that mark to accept replies without a mention.
- `me.post()` and `slack_post` write to the same Slack thread. On GitHub, `me.post()` and `github_comment` comment on the issue or pull request. A GitHub thread's key is its URL, so it is unique across repositories.
