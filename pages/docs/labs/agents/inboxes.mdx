# Inboxes

> Everything sent to a thread waits in order, and your agent reads it when it's ready.

More messages arrive while an agent works: a follow-up, a CI result, a review. The inbox keeps each one, in order, until it is read.

- **Read it your way.** In batches, one at a time, with a timeout, or without waiting. [Read the inbox →](#read-the-inbox)
- **More sources.** Events about the same work reach a live run. [Add sources →](#add-sources)
- **More inboxes.** Open another one inside a handler. [More inboxes →](#more-inboxes)
- **The model can watch too.** It opens and closes inboxes for the event types you allow. [Let the model watch →](#let-the-model-watch)

```typescript {{ title: "inngest/agents/deployer.ts" }}
import { eventType } from "inngest";
import { z } from "zod";
import { agents } from "../client";
import { claude } from "../models/claude";

export const deployRequested = eventType("deploy/requested", {
  schema: z.object({ service: z.string(), branch: z.string() }),
});

export const buildFinished = eventType("build/finished", {
  schema: z.object({
    app: z.string(),
    branch: z.string(),
    passed: z.boolean(),
  }),
});

export const deployer = agents.agent(
  {
    id: "deployer",
    triggers: [deployRequested],
    thread: "event.data.service",
    inbox: [
      {
        event: buildFinished,
        thread: "event.data.app",
        if: "async.data.branch == event.data.branch",
      },
    ],
    model: claude,
    system: "Ship the branch once its build has passed.",
  },
  async ({ inbox, loop }) => {
    let last = "";

    for await (const batch of inbox.batches({ max: 20 })) {
      const result = await loop(batch);

      last = result.text;
    }

    return last;
  },
);
```

## What's in it

An agent's inbox holds everything sent to its thread while a run works:

- **The trigger.** First in the inbox. The handler's `event` is the same message.
- **Source events.** From the `inbox` sources you list.
- **People's messages.** A reply in a Slack thread or a comment on a pull request.
- **Messages from agents.** `agent/message`, `agent/question`, `agent/answer` and `agent/finished`, each with `from`. [Teams of agents →](/docs/labs/agents/teams-of-agents?ref=docs-labs-agents-inboxes)

Answers to your code's `ask()` and `result()` go to the caller, and `stop()` cancels the run instead.

## Read the inbox

Loop over `batches()` for everything unread, with `max` capping a batch, oldest first, or over `inbox` for one message at a time. To wait for a reply, or look without waiting, read with `nextBatch()`, `next()` and `drain()`:

{/* not type-checked: inbox.nextBatch({ max }), inbox.next({ timeout }) and inbox.drain() in an agent handler */}
<AnnotatedCode>

```typescript {{ title: "inngest/agents/releaser.ts" }}
import { slack } from "inngest/experimental/agents";
import { agents } from "../client";
import { claude } from "../models/claude";

export const releaser = agents.agent(
  {
    id: "releaser",
    triggers: [slack.thread()],
    model: claude,
    system: "Plan the release, then wait for a go before you run it.",
  },
  async ({ inbox, loop, me }) => {
    const first = await inbox.nextBatch({ max: 20 });
    const plan = await loop(first ?? []);

    await me.post(plan.text);

    const reply = await inbox.next({ timeout: "1h" });

    if (!reply) {
      await me.post("No reply, so I'm leaving the release alone.");

      return;
    }

    const later = await inbox.drain();
    const result = await loop([reply, ...later]);

    await me.post(result.text);
  },
);
```

## More inboxes

To watch something else mid-run, open another inbox with `step.subscribe` in your handler.

{/* not type-checked: step.subscribe in an agent handler beside the agent's inbox */}
<AnnotatedCode>

```typescript {{ title: "inngest/agents/canary.ts" }}
import { eventType } from "inngest";
import { z } from "zod";
import { agents } from "../client";
import { claude } from "../models/claude";
import { deployRequested } from "./deployer";

export const rollbackRequested = eventType("deploy/rollback.requested", {
  schema: z.object({ service: z.string(), reason: z.string() }),
});

export const canary = agents.agent(
  {
    id: "canary",
    triggers: [deployRequested],
    thread: "event.data.service",
    model: claude,
    system: "Watch a deploy and say when it looks healthy.",
  },
  async ({ inbox, loop, step }) => {
    const rollbacks = step.subscribe("rollbacks", {
      event: rollbackRequested,
      if: "async.data.service == event.data.service",
    });

    for await (const batch of inbox.batches()) {
      await loop(batch);

      const requested = await rollbacks.drain();

      if (requested.length > 0) {
        await rollbacks.close();

        return `Rolled back: ${requested[0].data.reason}`;
      }
    }

    await rollbacks.close();

    return "Healthy";
  },
);
```

<Annotation id="subscribe" lines="20" tease="a second inbox" title="step.subscribe" href="/docs/durable-execution/primitives/step-subscribe?ref=docs-labs-agents-inboxes#more-inboxes" linkText="More inboxes">
Opened before the loop so no event is missed.
</Annotation>

## Let the model watch

List the event types the model may follow in `listen`, and it gets two tools: `inbox_listen` opens an inbox on one of them, and `inbox_close` closes it.

{/* not type-checked: listen on an agent definition */}
<AnnotatedCode>

```typescript {{ title: "inngest/agents/follower.ts" }}
import { eventType } from "inngest";
import { slack } from "inngest/experimental/agents";
import { z } from "zod";
import { agents } from "../client";
import { claude } from "../models/claude";

export const prReview = eventType("pr/review", {
  schema: z.object({ pr: z.number(), body: z.string() }),
});

export const prChecks = eventType("pr/checks", {
  schema: z.object({ pr: z.number(), passed: z.boolean() }),
});

export const follower = agents.agent({
  id: "follower",
  triggers: [slack.thread()],
  model: claude,
  system: "Follow the pull requests people ask about, until they merge.",
  listen: [prReview, prChecks],
});
```

<Annotation id="listen" lines="20" tease="the only events it may watch" title="listen" href="/docs/labs/agents/reference?ref=docs-labs-agents-inboxes#inbox" linkText="Reference">
With no `listen`, the model has neither tool.
</Annotation>

</AnnotatedCode>

The model calls the tools by name:

```typescript
inbox_listen({ source: "pr/checks", match: { pr: 42 }, as: "checks" });
```

`match` compares up to eight fields of the event's `data` for equality; dots reach nested ones, as in `"pull_request.number": 42`. `inbox_close({ as: "checks" })` stops watching.

A sandbox script can wait on a named inbox with `inbox_next({ as })` or `inbox_next_batch({ as })`. [Sandboxes and code →](/docs/labs/agents/sandboxes-and-code?ref=docs-labs-agents-inboxes)

## When a run ends

`idle` ends both loop forms: after that much quiet they finish, the handler returns, and the next message starts a run. [How long a run waits →](/docs/labs/agents/threads-and-memory?ref=docs-labs-agents-inboxes#how-long-a-run-waits)

On a run opened through a handle (`start()`, `message()`, `start_agent`, `message_agent`), both loops behave as if `idle` were zero, so a looping handler normally returns after the first batch. [When the handler returns →](/docs/labs/agents/handlers?ref=docs-labs-agents-inboxes#when-the-handler-returns)

## Gotchas

- **Reading takes.** A message the loop folded, or a read returned, is gone: your `for await` never sees it again.
- **Open before you act.** An inbox from `step.subscribe` keeps only events that arrive after it opens, so open it before the step that causes them. [Things to know →](/docs/durable-execution/primitives/step-subscribe?ref=docs-labs-agents-inboxes#things-to-know)
- **Waits with no timeout keep the run live.** `next()` and `nextBatch()` with no `timeout` wait as long as they must, whatever `idle` says.
- **Every message is a step.** Each counts toward the run's step limit when it arrives, read or not.

## How it works

- The inbox is one `step.subscribe` the SDK opens with the triggers, your `inbox` sources and the agent message types. [`step.subscribe` →](/docs/durable-execution/primitives/step-subscribe?ref=docs-labs-agents-inboxes#how-it-works)
- The trigger is put first at no cost, and a batch read asks the executor, so it includes messages that arrived during a long step.
