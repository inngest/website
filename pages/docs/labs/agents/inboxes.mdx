# Inboxes

> Everything sent to a thread waits in order, and your agent reads it when it's ready.

An agent often gets more messages while it works: a follow-up, a CI result, a review. The inbox keeps each one, in order, until the agent reads it.

- **The trigger comes first.** It is the first message in the inbox. [What's in it →](#whats-in-it)
- **Read it your way.** In batches, one at a time, with a timeout, or without waiting. [Read the inbox →](#read-the-inbox)
- **More sources.** Events about the same work reach a live run. [Add sources →](#add-sources)
- **More inboxes.** Open another one inside a handler. [More inboxes →](#more-inboxes)
- **The model can watch too.** It opens and closes inboxes for the event types you allow. [Let the model watch →](#let-the-model-watch)
- **Runs end on their own.** After `idle` of quiet time. [When a run ends →](#when-a-run-ends)

{/* not type-checked: inbox sources with thread and if, inbox.batches({ max }) and loop(batch) */}
<AnnotatedCode>

```typescript {{ title: "inngest/agents/deployer.ts" }}
import { agents } from "../client";
import { buildFinished, deployRequested } from "../events";
import { claude } from "../models/claude";

export const deployer = agents.agent(
  {
    id: "deployer",
    triggers: [deployRequested],
    thread: "event.data.service",
    inbox: [
      {
        event: buildFinished,
        thread: "event.data.app",
        if: "async.data.branch == event.data.branch",
      },
    ],
    model: claude,
    system: "Ship the branch once its build has passed.",
  },
  async ({ inbox, loop }) => {
    let last = "";

    for await (const batch of inbox.batches({ max: 20 })) {
      const result = await loop(batch);

      last = result.text;
    }

    return last;
  },
);
```

## What's in it

An agent's inbox holds everything sent to its thread while a run works:

- **The trigger.** First in the inbox. The handler's `event` is the same message.
- **Source events.** The events from the `inbox` sources you list.
- **People's messages.** A reply in a Slack thread or a comment on a pull request, while the run is live.
- **Messages from agents.** `agent/message`, `agent/question`, `agent/answer` and `agent/finished`, each with `from`. [Teams of agents →](/docs/labs/agents/teams-of-agents?ref=docs-labs-agents-inboxes)

It never holds the answer to your code's `ask()` or the result of its `result()`; those go to the code that asked. `stop()` isn't a message either, because it cancels the run.

## Read the inbox

`for await (const batch of inbox.batches())` is the usual loop. Each batch is every unread message, as a plain array. `max` caps it and leaves the rest unread, oldest first, so a flood never fills the model's context. `for await (const message of inbox)` reads one at a time and takes no options.

For more control, read with `nextBatch()`, `next()` and `drain()`:

{/* not type-checked: inbox.nextBatch({ max }), inbox.next({ timeout }) and inbox.drain() in an agent handler */}
<AnnotatedCode>

```typescript {{ title: "inngest/agents/releaser.ts" }}
import { slack } from "inngest/experimental/agents";
import { agents } from "../client";
import { claude } from "../models/claude";

export const releaser = agents.agent(
  {
    id: "releaser",
    triggers: [slack.thread()],
    model: claude,
    system: "Plan the release, then wait for a go before you run it.",
  },
  async ({ inbox, loop, me }) => {
    const first = await inbox.nextBatch({ max: 20 });
    const plan = await loop(first ?? []);

    await me.post(plan.text);

    const reply = await inbox.next({ timeout: "1h" });

    if (!reply) {
      await me.post("No reply, so I'm leaving the release alone.");

      return;
    }

    const later = await inbox.drain();
    const result = await loop([reply, ...later]);

    await me.post(result.text);
  },
);
```

## Add sources

`inbox: [...]` lists event sources, written like triggers. A source reaches a live run, and only `triggers` start one.

- **`thread`.** Says which thread the event belongs to, and `event` is the arriving event. Without it, the agent-wide `thread` expression applies. With nothing at the path, the event reaches no thread and the trace warns.
- **`if`.** Keeps only events about the run's own work. `async` is the arriving event and `event` is the run's trigger, as in `waitForEvent`.

## More inboxes

To watch something else mid-run, open another inbox with `step.subscribe` in your handler. The loop folds the agent's own inbox, so you read this one yourself.

{/* not type-checked: step.subscribe in an agent handler beside the agent's inbox */}
<AnnotatedCode>

```typescript {{ title: "inngest/agents/canary.ts" }}
import { agents } from "../client";
import { deployRequested, rollbackRequested } from "../events";
import { claude } from "../models/claude";

export const canary = agents.agent(
  {
    id: "canary",
    triggers: [deployRequested],
    thread: "event.data.service",
    model: claude,
    system: "Watch a deploy and say when it looks healthy.",
  },
  async ({ inbox, loop, step }) => {
    const rollbacks = step.subscribe("rollbacks", {
      event: rollbackRequested,
      if: "async.data.service == event.data.service",
    });

    for await (const batch of inbox.batches()) {
      await loop(batch);

      const requested = await rollbacks.drain();

      if (requested.length > 0) {
        await rollbacks.close();

        return `Rolled back: ${requested[0].data.reason}`;
      }
    }

    await rollbacks.close();

    return "Healthy";
  },
);
```

## Let the model watch

List the event types the model may follow in `listen`, and it gets two tools. `inbox_listen` opens an inbox on one of them, and `inbox_close` closes it. The loop folds what arrives into the model's next call, like any other message.

{/* not type-checked: listen on an agent definition */}
<AnnotatedCode>

```typescript {{ title: "inngest/agents/follower.ts" }}
import { slack } from "inngest/experimental/agents";
import { agents } from "../client";
import { prChecks, prReview } from "../events";
import { claude } from "../models/claude";

export const follower = agents.agent({
  id: "follower",
  triggers: [slack.thread()],
  model: claude,
  system: "Follow the pull requests people ask about, until they merge.",
  listen: [prReview, prChecks],
});
```

<Annotation id="listen" lines="11" tease="the only events it may watch" title="listen" href="/docs/labs/agents/reference?ref=docs-labs-agents-inboxes#inbox" linkText="Reference">
With no `listen`, the model has neither tool.
</Annotation>

</AnnotatedCode>

The model calls the tools by name:

```typescript
inbox_listen({ source: "pr/checks", match: { pr: 42 }, as: "checks" });
```

`match` narrows by fields of the event's `data` equal to values, with dots for nested fields such as `"pull_request.number": 42`, up to eight of them. The model never writes an expression. `inbox_close({ as: "checks" })` stops watching.

A script the model runs in a sandbox can wait on a named inbox: `inbox_next({ as })` returns the next message and `inbox_next_batch({ as })` the next batch, waiting if none has arrived. [Sandboxes and code →](/docs/labs/agents/sandboxes-and-code?ref=docs-labs-agents-inboxes)

## When a run ends

`idle` ends both loop forms. After that much quiet, `for await (const batch of inbox.batches())` and `for await (const message of inbox)` finish, the handler returns, and the next message starts a run on the same thread. [How long a run waits →](/docs/labs/agents/threads-and-memory?ref=docs-labs-agents-inboxes#how-long-a-run-waits)

A run opened through a handle, with `start()`, `message()`, `start_agent` or `message_agent`, is the exception. Both loops behave as if `idle` were zero: they yield what is already in the inbox and end the moment they would have to wait, so a looping handler normally returns right after the first batch.

## Gotchas

- **Reading takes.** A message the loop folded, or a read returned, is gone from the inbox. Your `for await` never sees it again.
- **Open before you act.** An inbox from `step.subscribe` only receives events that arrive after it opens, so open it before the step that causes them. [Things to know →](/docs/durable-execution/primitives/step-subscribe?ref=docs-labs-agents-inboxes#things-to-know)
- **Waits with no timeout keep the run live.** `next()` and `nextBatch()` with no `timeout` wait as long as they must; `idle` doesn't end them.
- **Every message is a step.** Messages count toward the run's step limit when they arrive, read or not.

## How it works

- The inbox is one `step.subscribe` the SDK opens with the triggers, your `inbox` sources and the four agent message types. [`step.subscribe` →](/docs/durable-execution/primitives/step-subscribe?ref=docs-labs-agents-inboxes#how-it-works)
- Each arriving message is saved as its own step. The trigger is put first at no cost.
- A message for a live thread lands in the run's inbox. A message for a quiet thread starts a run.
- A batch read asks the executor, so it includes messages that arrived while a long step ran.
