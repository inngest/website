# Sandboxes and code

> Give an agent a machine of its own that is still there on its next message.

A sandbox is the machine for one [thread](/docs/labs/agents/threads-and-memory?ref=docs-labs-agents-sandboxes-and-code). List it on an agent and the model gets a shell on it, your code gets the same machine, and the files are there next time.

- **A shell for the model.** Listing a sandbox gives the model `work_run`. [Give the agent a sandbox →](#give-the-agent-a-sandbox)
- **Files that stay.** One machine per thread, paused when unused. [Keep files between runs →](#keep-files-between-runs)
- **Your code on the same machine.** Run commands from a handler. [Use it from a handler →](#use-it-from-a-handler)
- **Scripts that call your tools.** Each call is a durable step in your app. [Let code call your tools →](#let-code-call-your-tools)
- **Credentials stay with you.** A shim runs a program with a token only your app holds. [Hand a program a credential →](#hand-a-program-a-credential)
- **Pushes your policy checks.** Your app pushes, so the sandbox never holds a write token. [Check out and push →](#check-out-a-repo)

## Give the agent a sandbox

`sandbox()` returns a definition and creates nothing, so importing one is safe. Define it at module scope and list it on any agent. An app whose agents list sandboxes adds `sandboxMiddleware()` to its client.

{/* not type-checked: sandboxMiddleware() on the client */}
```typescript {{ title: "inngest/client.ts" }}
import { Inngest } from "inngest";
import { sandboxMiddleware } from "inngest/experimental";
import { createAgents } from "inngest/experimental/agents";

export const inngest = new Inngest({
  id: "coder",
  middleware: [sandboxMiddleware()],
});

export const agents = createAgents(inngest);
```

## Keep files between runs

The thread owns its sandbox. It starts the first time the model or your code uses it. Ten minutes after its last use it pauses, whether the run is still waiting or has ended, and the next use brings it back with its disk as it was.

```text {{ title: "One thread, two runs" }}
09:00  work_run  npm install   the sandbox starts
09:04  the run ends
09:14  ten minutes unused      the sandbox pauses
11:30  work_run  npm test      the sandbox resumes, node_modules is there
```

A run that never needs the sandbox never starts one.

## Work in a shell

The model works in a shell, not file by file. `work_run` keeps `cd` and `export` from one call to the next, and into the thread's next run. Files stay on the machine instead of passing through step state. There is no write tool: a heredoc in `work_run` writes a file.

`read`, `search` and `edit` are off until you ask for them. `sandbox.tools.code()` takes `only`, `tools`, `shims` and `timeout`.

<AnnotatedCode>

{/* not type-checked: sandbox.tools.code with only and timeout */}
```typescript {{ title: "inngest/sandboxes/editor.ts" }}
import { sandbox } from "inngest/experimental/agents";

export const editor = sandbox({
  id: "editor",
  tools: sandbox.tools.code({
    only: ["run", "read", "search", "edit"],
    timeout: "10m",
  }),
});
```

<Annotation id="only" lines="6" tease="editor_run, editor_edit" title="Only">
The tools the model gets. Without `only` it gets `run`, plus `run_code` once you give tools.
</Annotation>

<Annotation id="timeout" lines="7" tease="longest one command may run" title="Timeout">
The default is five minutes. A longer one works. [Run long commands →](#run-long-commands)
</Annotation>

</AnnotatedCode>

## Use it from a handler

A [handler](/docs/labs/agents/handlers?ref=docs-labs-agents-sandboxes-and-code) gets the same machine the model uses. `sandboxes.work` opens it on first use, so a run that never touches it starts nothing. `{ sandbox: work, model: false }` keeps a sandbox for your code only.

<AnnotatedCode>

{/* not type-checked: sandboxes.work.commands.run in a handler, { sandbox, model: false } */}
```typescript {{ title: "inngest/agents/tester.ts" }}
import { github } from "inngest/experimental/agents";
import { agents } from "../client";
import { claude } from "../models/claude";
import { work } from "../sandboxes/work";

export const tester = agents.agent(
  {
    id: "tester",
    triggers: [github.thread()],
    model: claude,
    system: "Explain the test results you are given.",
    sandboxes: { work: { sandbox: work, model: false } },
  },
  async ({ inbox, me, loop, sandboxes }) => {
    const tests = await sandboxes.work.commands.run("tests", "npm test", {
      cwd: "/work",
    });

    await me.message({ tests: tests.stdout.slice(-2000) });

    for await (const batch of inbox.batches()) {
      const { text } = await loop(batch);

      await me.post(text);
    }
  },
);
```

<Annotation id="code-only" lines="12" tease="the model gets none of its tools" title="Code only">
Without `model: false`, the model would get `work_run` too.
</Annotation>

<Annotation id="commands" lines="15-17" tease="a command on the thread's machine" title="Run a command" href="/docs/labs/agents/reference-sandboxes?ref=docs-labs-agents-sandboxes-and-code#the-handlers-sandbox" linkText="Reference">
Each call is a durable step, so a replay never runs the tests twice.
</Annotation>

<Annotation id="message" lines="19" tease="the model reads it next" title="Hand it over" href="/docs/labs/agents/handlers?ref=docs-labs-agents-sandboxes-and-code#message-yourself" linkText="Handlers">
The result lands in the agent's own inbox, and the loop shows it to the model.
</Annotation>

</AnnotatedCode>

Besides `commands`, `sandboxes.work` has:

- `files`, to move files in and out.
- `repo.push(branch)`, when the definition has a `repo`. [Push a branch →](#push-a-branch)
- `recycle()`, which pauses the machine at once. The next use brings it back.
- `close()`, which destroys it.

[Reference: the handler's sandbox →](/docs/labs/agents/reference-sandboxes?ref=docs-labs-agents-sandboxes-and-code#the-handlers-sandbox)

## Let code call your tools

A script on the machine can call your [tools](/docs/labs/agents/tools?ref=docs-labs-agents-sandboxes-and-code). They run in your app, with your credentials, as durable steps, so the sandbox never holds a secret. The key in the `tools` record names a tool for the model and for the script alike.

<AnnotatedCode>

{/* not type-checked: sandbox.tools.code({ tools }), which gives the model analyst_run_code */}
```typescript {{ title: "inngest/sandboxes/analyst.ts" }}
import { sandbox } from "inngest/experimental/agents";
import { getAccount } from "../tools/getAccount";
import { waitForCi } from "../tools/waitForCi";

export const analyst = sandbox({
  id: "analyst",
  tools: sandbox.tools.code({
    tools: { getAccount, waitForCi },
  }),
});
```

<Annotation id="tools" lines="8" tease="adds analyst_run_code" title="Tools for scripts" href="/docs/labs/agents/tools?ref=docs-labs-agents-sandboxes-and-code" linkText="Tools">
Giving the code tools some tools adds `run_code`. The script calls them as `tools.getAccount(...)`. `now` and `sleep` are built in.
</Annotation>

</AnnotatedCode>

List `analyst` on an agent, and the model writes scripts that `analyst_run_code` runs:

```python {{ title: "A script the model runs" }}
account = await tools.getAccount(id="a-42")

if account["plan"] == "pro":
    ci = await tools.waitForCi(branch="agent/fix")
```

These are ordinary tools: the same record works in an agent's `tools`.

{/* not type-checked: tool.step called by a script */}
```typescript {{ title: "inngest/tools/getAccount.ts" }}
import { tool } from "inngest/experimental";
import { z } from "zod";

export const getAccount = tool.step({
  description: "Find an account by ID",
  input: z.object({ id: z.string() }),
  run: async ({ id }) => {
    return { id, plan: "pro" };
  },
});
```

`waitForCi` can take hours. Declared with `waits: true`, it makes the script exit instead of holding the command open. When the tool answers, the script runs again from the top and its earlier calls return their saved answers.

<AnnotatedCode>

{/* not type-checked: tool.group with waits: true called from a script */}
```typescript {{ title: "inngest/tools/waitForCi.ts" }}
import { step } from "inngest";
import { tool } from "inngest/experimental";
import { z } from "zod";

export const waitForCi = tool.group({
  description: "Wait for CI to finish on a branch",
  input: z.object({ branch: z.string() }),
  waits: true,
  run: async ({ branch }) => {
    const finished = await step.waitForEvent("ci-finished", {
      event: "ci/finished",
      timeout: "2h",
      if: `async.data.branch == "${branch}"`,
    });

    return { passed: finished?.data.passed ?? false };
  },
});
```

<Annotation id="waits" lines="8" tease="the script exits and re-runs" title="Waits" href="/docs/labs/agents/tools?ref=docs-labs-agents-sandboxes-and-code" linkText="Tools">
Inline when the model calls it; a pause the script survives when a script calls it.
</Annotation>

</AnnotatedCode>

Your own code passes tools to a command with `tools`. The script imports them with `from inngest_tools import tools`. The core Sandbox `$` template takes `tools` too. [Tools and code mode →](/docs/sandboxes/features/tools?ref=docs-labs-agents-sandboxes-and-code)

```typescript
await sandboxes.work.commands.run("summarise", "python summarise.py", {
  tools: { getAccount },
});
```

A tool you make inside a handler and pass with `loop(batch, { tools })` makes `run_code` appear for that call. A script calls the tool by the same name, so it can call back into the run with everything the handler can see. [Give the model a tool →](/docs/labs/agents/handlers?ref=docs-labs-agents-sandboxes-and-code#give-the-model-a-tool)

## Hand a program a credential

A shim is a program on the shell's `PATH` that calls your app first. Your app decides what happens: run the real program with something added, change its arguments, or answer on its own. The model types `flyctl deploy` and never handles the token.

<AnnotatedCode>

{/* not type-checked: tool.shim passed to sandbox.tools.code({ shims }) */}
```typescript {{ title: "inngest/sandboxes/deployer.ts" }}
import { tool } from "inngest/experimental";
import { sandbox } from "inngest/experimental/agents";

const flyctl = tool.shim("flyctl", {
  only: ["deploy"],
  handle: async ({ run }) => {
    const token = process.env.FLY_DEPLOY_TOKEN ?? "";

    return run({ env: { FLY_API_TOKEN: token } });
  },
});

export const deployer = sandbox({
  id: "deployer",
  tools: sandbox.tools.code({
    shims: [flyctl],
    timeout: "15m",
  }),
});
```

<Annotation id="only" lines="5" tease="only deploy calls your app" title="Only">
Any other `flyctl` call runs the real program at once, with no trip to your app.
</Annotation>

<Annotation id="run" lines="9" tease="the real program, plus a token" title="Run it">
The token joins the environment of that one process and isn't saved in the run.
</Annotation>

<Annotation id="shims" lines="16" tease="on PATH for run and run_code" title="Shims">
The model's `run` and `run_code` find `flyctl` on `PATH`. It isn't a tool in the model's list.
</Annotation>

<Annotation id="timeout" lines="17" tease="a long deploy is one call" title="Timeout" href="#run-long-commands" linkText="Run long commands">
Longer than five minutes works.
</Annotation>

</AnnotatedCode>

A shim can also decline with `refuse("message")` or answer on its own with `reply(0, { stdout })`.

## Run long commands

A command with a `timeout` over five minutes works, including one that calls tools or uses shims. The model's commands take it from `sandbox.tools.code({ timeout })`. Your code passes it per command:

```typescript
await sandboxes.work.commands.run("deploy", "flyctl deploy", {
  shims: [flyctl],
  timeout: "15m",
});
```

## Check out a repo

`repo` on a sandbox checks a repository out when the sandbox starts, so the model begins with the code in front of it. The checkout uses a short-lived read-only token. It goes to the one `git` process that clones and is never written into the checkout's config.

{/* not type-checked: githubApp() with a secret() private key */}
```typescript {{ title: "inngest/github.ts" }}
import { secret } from "inngest/experimental";
import { githubApp } from "inngest/experimental/agents";

export const app = githubApp({
  appId: process.env.GITHUB_APP_ID ?? "",
  privateKey: secret("GITHUB_APP_PRIVATE_KEY"),
});
```

<AnnotatedCode>

```typescript {{ title: "inngest/sandboxes/service.ts" }}
export const service = sandbox({
```

Asked for a read-only token to check out and a write token to push, each short-lived and made on your host. A function of `{ access }` that returns a token works too.

<Annotation id="ref" lines="9" tease="the branch, tag or commit" title="Ref">

The model's shell starts in the checkout's `path`.

`repo` can also be a function of `{ event, thread }`, run once when the run starts. A reviewer checks out the pull request it was triggered by. When a resumed sandbox's checkout is on another ref, the sandbox fetches the new one and checks it out. Uncommitted changes in the working tree make that an error the run sees.

```typescript {{ title: "inngest/sandboxes/review.ts" }}
  id: "review",

    return {
      url: event.data.repo,
      ref: event.data.head,
      auth: app,
    };
  },
});
```

## Push a branch

The model commits in the sandbox with its own messages and calls `work_push({ branch })`. Your app makes the push, with its own write token, after `policy` has seen the branch, the commits and the paths they touch. The sandbox never holds a write token.

<AnnotatedCode>

{/* not type-checked: repo.policy reading the push and returning refuse or notes */}
```typescript {{ title: "inngest/sandboxes/guarded.ts" }}
import { sandbox } from "inngest/experimental/agents";
import { app } from "../github";

export const guarded = sandbox({
  id: "guarded",
  repo: {
    url: "https://github.com/acme/api",
    auth: app,
    policy: async (push) => {
      if (!push.branch?.startsWith("agent/")) {
        return { refuse: "Branches for the agent start with agent/" };
      }

      const touched = push.paths.filter((path) => {
        return path.startsWith(".github/");
      });

      if (touched.length > 0) {
        return { refuse: `Not allowed to change ${touched.join(", ")}` };
      }

      return { notes: [`${push.commits.length} commits to ${push.branch}`] };
    },
  },
});
```

<Annotation id="policy" lines="9" tease="runs on your host" title="Policy">
Sees `push.branch`, `push.commits` with their messages and `push.paths` before anything is pushed. It returns `{ refuse }`, `{ notes }` or nothing.
</Annotation>

<Annotation id="refuse" lines="11" tease="the model reads the reason" title="Refuse" href="#push-a-branch" linkText="Push a branch">
A refused push comes back to the model as an error it can read and fix.
</Annotation>

<Annotation id="paths" lines="14-16" tease="by path" title="Paths">
Every path the commits touch.
</Annotation>

<Annotation id="notes" lines="22" tease="kept with the result" title="Notes" href="#push-a-branch" linkText="Push a branch">
Returned in the push result, for an audit trail.
</Annotation>

</AnnotatedCode>

Your code pushes the same way, through the same policy. `repo.push(branch)` returns `{ branch, sha, notes }`. A refusal throws `PushRefusedError`, which isn't retried.

<AnnotatedCode>

{/* not type-checked: sandboxes.guarded.repo.push and PushRefusedError */}
```typescript {{ title: "inngest/agents/nightly.ts" }}
import { PushRefusedError } from "inngest/experimental/agents";
import { agents } from "../client";
import { guarded } from "../sandboxes/guarded";

export const nightly = agents.agent(
  {
    id: "nightly",
    triggers: [{ cron: "TZ=UTC 0 3 * * *" }],
    sandboxes: { guarded },
  },
  async ({ sandboxes }) => {
    const guard = sandboxes.guarded;

    await guard.commands.run(
      "fix",
      "npm audit fix && git commit -am audit",
      { cwd: "/work" },
    );

    try {
      return await guard.repo.push("agent/audit-fix");
    } catch (error) {
      if (error instanceof PushRefusedError) {
        return { refused: error.reason };
      }

      throw error;
    }
  },
);
```

</Annotation>

## Secrets

`sandbox({ secrets })` and `secret()` are different things. `secrets` puts values into the sandbox, where any code running there can read them. `secret()` keeps a value on your host.

<AnnotatedCode>

{/* not type-checked: sandbox({ environment, secrets }) */}
```typescript {{ title: "inngest/sandboxes/builder.ts" }}
import { sandbox } from "inngest/experimental/agents";

export const builder = sandbox({
  id: "builder",
  environment: { NODE_ENV: "test" },
  secrets: ["NPM_TOKEN"],
});
```

<Annotation id="environment" lines="5" tease="plain values" title="Environment">
Set in the sandbox when it is created.
</Annotation>

<Annotation id="secrets" lines="6" tease="names of workspace secrets" title="Secrets" href="/docs/sandboxes/features/secrets?ref=docs-labs-agents-sandboxes-and-code" linkText="Secrets">
Each value is set in the sandbox as an environment variable with that name.
</Annotation>

</AnnotatedCode>

Pass `secret("NAME")` wherever a token goes, as the GitHub App's private key above. It prints as `[secret NAME]` and is read only inside the call that needs it. For anything the model's code shouldn't hold, use a tool or a short-lived token. [Tools →](/docs/labs/agents/tools?ref=docs-labs-agents-sandboxes-and-code)

## Gotchas

- **The shell's environment has a cap.** Every `export` rides along on every later command. At 256 entries or 64 KiB the shell fails early and names the limit.
- **An `EXIT` trap or `exec` drops the place.** A command that sets its own `EXIT` trap or uses `exec` doesn't carry its `cd` and `export` to the next call.
- **Exports stay in run history.** An exported value is saved with the call. Put credentials in `secrets`, or behind a tool.
- **A new `ref` needs a clean tree.** When a run's `ref` differs from the checkout's, uncommitted changes make the checkout an error. Commit or discard them first.
- **A recreated sandbox starts at the default.** The shell's place returns only with the same sandbox or its snapshot.
- **A long tool call needs a long command.** In a script, a tool call that outlives the command's `timeout` (five minutes by default) aborts the command. Declare the tool `waits: true`, or give the command a longer `timeout`.
- **A script that waits runs again.** Calls it already made return saved answers. Files it writes and processes it starts happen again, so read the clock with `tools.now()`.
- **A shim is a program on `PATH`.** Code that runs the real program by its full path skips the shim.
- **One repo per sandbox.** A second repo gets a second sandbox. A push names the branch and opens no pull request; your app does that with its GitHub tools or its own code.

## How it works

- The sandbox starts in one durable step, so every call shares it. Ten minutes after its last use it pauses; a run that waits longer pauses it at that mark.
- Each `run` is its own shell process, started in the saved directory with the saved environment. It reports its new place when it exits, and the SDK saves that with the call, so a restart or another machine replays to the same place.
- A push is four steps: the sandbox bundles the new commits, your app reads the bundle, `policy` sees the branch, commits and paths, and your app pushes with its write token. It sends the commits that are there and never forces or deletes.
- A command over five minutes runs as a process that steps follow in windows of five minutes, one wait step each.
