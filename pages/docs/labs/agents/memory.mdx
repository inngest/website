# Memory

> A thread remembers, because it is a run, not a lookup.

A run's variables are gone when it ends, but a thread is not a function call — it is its own long-lived run, and that run is the only writer to the thread's state. There is no store and no `kv` import in this iteration: a thread is not a key-value service you read and write from the outside, it is state that belongs to a run, delivered to each agent run through its inbox when it starts.

## What already survives

Two things a thread holds for you, with nothing to configure:

- **The model's history.** [Models →](/docs/labs/agents/models?ref=docs-labs-agents-memory#it-remembers) The loop folds every turn into the thread's state after each batch, and a later run of the same thread picks that history up and carries the conversation on. This is why an agent with [no handler at all](/docs/labs/agents/agents?ref=docs-labs-agents-memory#no-handler) still feels continuous across many short-lived runs: the run is disposable, the thread's memory of what was said isn't.
- **A sandbox's files.** [Sandboxes →](/docs/labs/agents/sandboxes?ref=docs-labs-agents-memory#it-belongs-to-the-thread) A sandbox belongs to the thread: its files are restored from the thread's newest snapshot when a run first touches it, and snapshotted again when the run ends.

Both of these are the thread's own state, written once by the thread's own run, and read by whichever agent run needs them next.

## Your own values

You want to count CI failures on a PR, the way [Inboxes](/docs/labs/agents/inboxes?ref=docs-labs-agents-memory) counted them in a plain variable that didn't survive past one run's `idle`. That specific gap — a named value of your own, kept on the thread across runs, independent of the model's history — needs a mechanism this iteration does not ship yet.

TODO: the no-store design in `16-iteration-one.md` says this state lives in the thread run's own state, delivered through the agent's inbox, but the user-facing API for it (what used to be `kv.thread`) has not landed in the SDK as of this writing. Don't guess at a signature here — check `inngest/experimental/agents`'s current exports before writing code against this.

Until it does, two honest options:

- **Fold the count into the conversation.** If a value can be read back out of what happened — "CI has failed 3 times" said in a past turn — the model's own remembered history already carries it; ask the model, or read the history yourself with `agent.loop()`'s `history` option.
- **Keep it outside the thread.** Nothing stops you from calling your own storage (a database you already run, a cache, a queue) from a `step.run()` inside the handler. You lose nothing Inngest would have given you here, because Inngest isn't giving you a thread-scoped store to lose.
