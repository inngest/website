# Inngest Agents overview

> Learn how an agent is put together, then see three complete agents: a support assistant, a pull request reviewer, and a lead that hands work to specialists.

<Info>
  Inngest Agents is an Inngest Labs project: early, moving fast, and shaped by your feedback. Install it with `npm install inngest@agents`. The API can change between releases. [What's Labs?](/docs/labs?ref=docs-labs-agents-overview)
</Info>

An Inngest agent is a durable function that calls a model in a loop. You give it a model, a system prompt, and tools. Inngest starts it from your events, keeps each conversation on its own thread, and delivers new messages to it while it works. Every model call and tool call is a [durable step](/docs/durable-execution/primitives/step-run?ref=docs-labs-agents-overview), so a crash, a retry, or a deploy never repeats work that already finished.

## Concepts

An agent is built from a small set of parts. Each part has its own page under Concepts.

- **Agent.** An Inngest function you define with `agents.agent()`. It starts from triggers, such as events or a schedule, and either runs the model loop for you or runs a handler you write. See [Agents](/docs/labs/agents/agents?ref=docs-labs-agents-overview).
- **Thread.** The conversation an event belongs to, such as a customer, a support ticket, or a pull request. You name it with an expression over your event, such as `"event.data.ticket"`. A thread keeps the model's history and your own state between runs. See [Threads](/docs/labs/agents/threads?ref=docs-labs-agents-overview).
- **Run.** One execution of the agent on a thread. A run handles the messages in front of it and ends. The next message on the thread starts a new run that picks up the same history.
- **Inbox.** The queue of messages on a thread. Messages that arrive while a run works wait in its inbox and reach the model on its next call, so a correction lands mid-task instead of starting a second run. See [Inboxes](/docs/labs/agents/inboxes?ref=docs-labs-agents-overview).
- **Model and loop.** The loop sends the thread's history to the model, runs the tools the model asks for, and repeats until the model answers. Each model call and each tool call is its own step. See [Models and the loop](/docs/labs/agents/models?ref=docs-labs-agents-overview).
- **Tools.** Functions the model can call. A tool runs in your app as a durable step, with your code and your credentials. See [Tools](/docs/labs/agents/tools?ref=docs-labs-agents-overview).
- **Skills.** Instructions in `SKILL.md` files that the model opens when a task needs them, such as your team's review checklist. See [Skills](/docs/labs/agents/skills?ref=docs-labs-agents-overview).
- **Sandboxes.** An isolated machine for each thread, where the model can run commands, read and edit files, and work in a checked-out repository. See [Sandboxes](/docs/labs/agents/sandboxes?ref=docs-labs-agents-overview).
- **Agent teams.** Agents can start other agents, message them while they work, and wait for their results. Each agent publishes a card, so a model can find the right agent at run time. See [Agent teams](/docs/labs/agents/agent-teams?ref=docs-labs-agents-overview) and [Agent discovery](/docs/labs/agents/agent-discovery?ref=docs-labs-agents-overview).

## How a run works

<Mermaid
  wide
  label="An event names a thread. If a run is already working on that thread, the event goes into its inbox. Otherwise a new run starts. The run's loop calls the model and runs the tools it asks for, each as a step, until the model answers. The history is saved on the thread, and the run ends when its inbox is empty."
  chart={`flowchart LR
  E["Event"] --> T["Thread"]
  T --> R["Run"]
  R --> I["Inbox"]
  I --> L["Loop"]
  L --> M["Model call"]
  M --> X["Tool calls"]
  X --> L
  L --> A["Answer"]
  A -. "history saved" .-> T
  class E,A accent
  class T,I info`}
/>

1. **An event arrives.** The agent's `thread` expression reads a key from it, such as a ticket ID, and the event joins that thread.
2. **A run picks it up.** If a run is already working on the thread, the event goes into that run's inbox. Otherwise Inngest starts a new run.
3. **The loop works.** The loop calls the model with the thread's history and runs the tools the model asks for. Each call is a step in the run's trace.
4. **Messages land mid-task.** Before each model call, the loop adds any messages that arrived in the inbox.
5. **The run ends.** When the model answers and the inbox is empty, the run saves the history to the thread and ends. The next message on the thread starts a new run with that history.

## Set up the client

Every example on this page uses the same client. `inboxMiddleware()` adds `step.subscribe()`, which agents use to read their inboxes, and `createAgents()` gives you `agents.agent()` to define agents.

```typescript {{ title: "inngest/client.ts" }}
import { Inngest } from "inngest";
import { inboxMiddleware } from "inngest/experimental";
import { createAgents } from "inngest/experimental/agents";

export const inngest = new Inngest({
  id: "acme",
  middleware: [inboxMiddleware()],
});

export const agents = createAgents(inngest);
```

Each agent imports its model from one file, so you can change the model in one place:

```typescript {{ title: "inngest/models/claude.ts" }}
import { anthropic } from "inngest/experimental/agents";

export const claude = anthropic({ model: "claude-sonnet-5-5" });
```

The [quick start](/docs/labs/agents/quick-start?ref=docs-labs-agents-overview) installs the package and serves these files to the Dev Server.

## Example: a support assistant

This agent answers support tickets. It needs no handler: a model, a system prompt, and two tools make a complete agent.

```typescript {{ title: "inngest/events.ts" }}
import { eventType } from "inngest";
import { z } from "zod";

export const ticketOpened = eventType("ticket/opened", {
  schema: z.object({ ticket: z.string(), text: z.string() }),
});

export const ticketReplied = eventType("ticket/replied", {
  schema: z.object({ ticket: z.string(), text: z.string() }),
});
```

<AnnotatedCode>

```typescript {{ title: "inngest/agents/support.ts" }}
import { agents } from "../client";
import { ticketOpened, ticketReplied } from "../events";
import { claude } from "../models/claude";
import { lookupOrder } from "../tools/lookupOrder";
import { sendReply } from "../tools/sendReply";

export const support = agents.agent({
  id: "support",
  triggers: [ticketOpened, ticketReplied],
  thread: "event.data.ticket",
  model: claude,
  system: "You answer customer questions about orders. Send each answer with sendReply.",
  tools: { lookupOrder, sendReply },
});
```

<Annotation id="triggers" lines="9" tease="what starts a run" title="Triggers" href="/docs/labs/agents/agents?ref=docs-labs-agents-overview#add-triggers" linkText="Agents">
A new ticket or a customer's reply starts a run, or joins the run already working on that ticket.
</Annotation>

<Annotation id="thread" lines="10" tease="one thread per ticket" title="Thread" href="/docs/labs/agents/threads?ref=docs-labs-agents-overview" linkText="Threads">
Both events carry the ticket ID, so a follow-up days later lands on the same thread and the model sees the whole conversation.
</Annotation>

<Annotation id="loop" lines="11-12" tease="no handler needed" title="Model and system prompt" href="/docs/labs/agents/models?ref=docs-labs-agents-overview" linkText="Models and the loop">
With a model and no handler, the agent runs the loop for you: it calls the model, runs the tools it asks for, and repeats until the model answers.
</Annotation>

<Annotation id="tools" lines="13" tease="durable steps" title="Tools" href="/docs/labs/agents/tools?ref=docs-labs-agents-overview" linkText="Tools">
Each tool call runs in your app as its own step. If `sendReply` fails, only that call retries, and the customer never gets the same reply twice.
</Annotation>

</AnnotatedCode>

A tool is a description, an input schema, and a function:

```typescript {{ title: "inngest/tools/lookupOrder.ts" }}
import { tool } from "inngest/experimental";
import { z } from "zod";
import { orders } from "../lib/orders";

export const lookupOrder = tool.step({
  description: "Look up an order by its ID",
  input: z.object({ id: z.string() }),
  run: async ({ id }) => {
    return await orders.get(id);
  },
});
```

```typescript {{ title: "inngest/tools/sendReply.ts" }}
import { tool } from "inngest/experimental";
import { z } from "zod";
import { helpdesk } from "../lib/helpdesk";

export const sendReply = tool.step({
  description: "Send a reply to the customer on their ticket",
  input: z.object({ ticket: z.string(), body: z.string() }),
  run: async ({ ticket, body }) => {
    return await helpdesk.reply(ticket, body);
  },
});
```

`orders` and `helpdesk` are your own API clients. The [Support assistant recipe](/docs/labs/agents/recipes/support-assistant?ref=docs-labs-agents-overview) has the complete project.

## Example: a pull request reviewer

This agent reviews each pull request in a sandbox that has the pull request checked out. It runs the tests, follows your team's review checklist, and posts its review. Because it has a handler, you control what happens with each answer.

<AnnotatedCode>

```typescript {{ title: "inngest/agents/reviewer.ts" }}
import { skills } from "inngest/experimental/agents";
import { agents } from "../client";
import { prComment, prOpened } from "../events";
import { gh } from "../lib/github";
import { claude } from "../models/claude";
import { checkout } from "../sandboxes/checkout";

export const reviewer = agents.agent(
  {
    id: "pr-reviewer",
    triggers: [prOpened, prComment],
    thread: "event.data.pr",
    model: claude,
    system: "You review pull requests on acme/web. Run the tests before you review.",
    sandboxes: { checkout },
    skills: [skills.folder("./skills")],
  },
  async ({ inbox, loop, step, thread }) => {
    for await (const batch of inbox.batches()) {
      const result = await loop(batch);

      await step.run("post-review", async () => {
        return await gh.comment(Number(thread.key), result.text);
      });
    }
  },
);
```

<Annotation id="thread" lines="11-12" tease="one thread per PR" title="One thread per pull request" href="/docs/labs/agents/threads?ref=docs-labs-agents-overview" linkText="Threads">
A comment on the pull request lands on the same thread as the review, so "can you look at the tests again?" reaches a model that has the context.
</Annotation>

<Annotation id="sandbox" lines="15" tease="a machine per thread" title="Sandbox" href="/docs/labs/agents/sandboxes?ref=docs-labs-agents-overview" linkText="Sandboxes">
The model gets `checkout_run`, `checkout_read`, and `checkout_search` to work on the thread's own machine. The machine pauses when the run ends and resumes, files intact, on the next comment.
</Annotation>

<Annotation id="skills" lines="16" tease="read when needed" title="Skills" href="/docs/labs/agents/skills?ref=docs-labs-agents-overview" linkText="Skills">
The model sees each skill's name and description, and opens the full instructions when it needs them.
</Annotation>

<Annotation id="inbox" lines="19" tease="every message on the thread" title="Inbox" href="/docs/labs/agents/inboxes?ref=docs-labs-agents-overview" linkText="Inboxes">
Takes the messages waiting on the thread in batches. The loop ends when the inbox is empty, and so does the run.
</Annotation>

<Annotation id="loop" lines="20" tease="model and tools" title="loop()" href="/docs/labs/agents/models?ref=docs-labs-agents-overview#write-a-handler" linkText="Models and the loop">
Runs the model and its tool calls until it answers, and returns the answer in `result.text`.
</Annotation>

<Annotation id="post" lines="22-24" tease="your code, once" title="Post the review" href="/docs/durable-execution/primitives/step-run?ref=docs-labs-agents-overview" linkText="step.run">
Your own code, in a step, so the review is posted once even if the run retries.
</Annotation>

</AnnotatedCode>

The sandbox checks out the pull request's head with a read-only token and gives the model three of the built-in tools:

```typescript {{ title: "inngest/sandboxes/checkout.ts" }}
import { secret } from "inngest/experimental";
import { sandbox } from "inngest/experimental/agents";

const { run, read, search } = sandbox.tools;

export const checkout = sandbox({
  id: "checkout",
  repo: ({ thread }) => {
    return {
      url: "https://github.com/acme/web",
      ref: `refs/pull/${thread.key}/head`,
      auth: secret("GITHUB_READ_TOKEN"),
      push: false,
    };
  },
  tools: { run, read, search },
});
```

An app with sandboxes adds `sandboxMiddleware()` to its client:

```typescript {{ title: "inngest/client.ts" }}
import { Inngest } from "inngest";
import { inboxMiddleware, sandboxMiddleware } from "inngest/experimental";
import { createAgents } from "inngest/experimental/agents";

export const inngest = new Inngest({
  id: "acme",
  middleware: [inboxMiddleware(), sandboxMiddleware()],
});

export const agents = createAgents(inngest);
```

The skill is a folder with a `SKILL.md` file:

```markdown {{ title: "skills/review-checklist/SKILL.md" }}
---
name: review-checklist
description: How we review a pull request. Use before you review any pull request.
---

1. Run the test suite and read any failures first.
2. Check that every changed function has a test.
3. Say what is good about the change as well as what is wrong.
```

The [PR reviewer recipe](/docs/labs/agents/recipes/pr-reviewer?ref=docs-labs-agents-overview) has the complete project, including the events and the GitHub client.

## Example: a lead and its specialists

Agents can hand work to other agents. Here, a lead agent receives a pull request, finds the specialists that fit it, starts them, and combines their findings into one review. The lead has no code that names the specialists: its model finds them at run time from their cards.

<AnnotatedCode>

```typescript {{ title: "inngest/agents/specialists.ts" }}
import { invoke } from "inngest";
import { z } from "zod";
import { agents } from "../client";
import { claude } from "../models/claude";
import { readDiff } from "../tools/readDiff";

const prInput = z.object({ pr: z.number() });

export const securityReviewer = agents.agent({
  id: "security-reviewer",
  triggers: [invoke(prInput)],
  model: claude,
  system: "You review a pull request for security problems. List each one with its file and line.",
  tools: { readDiff },
  card: {
    description: "Reviews a pull request for security problems",
    capabilities: ["security review", "leaked secrets", "unsafe input handling"],
  },
});

export const docsReviewer = agents.agent({
  id: "docs-reviewer",
  triggers: [invoke(prInput)],
  model: claude,
  system: "You check that a pull request updates the docs for every change users will notice.",
  tools: { readDiff },
  card: {
    description: "Checks that a pull request updates the docs it should",
    capabilities: ["documentation review", "changelog entries"],
  },
});
```

<Annotation id="invoke" lines="11" tease="typed input" title="invoke()" href="/docs/labs/agents/agent-teams?ref=docs-labs-agents-overview" linkText="Agent teams">
Types the input that other agents and your code start this agent with.
</Annotation>

<Annotation id="card" lines="15-18" tease="how it's found" title="Card" href="/docs/labs/agents/agent-discovery?ref=docs-labs-agents-overview" linkText="Agent discovery">
What a model reads when it decides which agent to start. Describe the problems the agent handles, in the words a caller would use.
</Annotation>

</AnnotatedCode>

<AnnotatedCode>

```typescript {{ title: "inngest/agents/lead.ts" }}
import { agents } from "../client";
import { prReady } from "../events";
import { claude } from "../models/claude";
import { comment } from "../tools/comment";

export const lead = agents.agent({
  id: "review-lead",
  triggers: [prReady],
  thread: "event.data.pr",
  model: claude,
  system:
    "Find the reviewers that fit this pull request and start each one. " +
    "When they finish, combine their findings into one review and post it with comment.",
  tools: { comment },
});
```

<Annotation id="discovery" lines="11-13" tease="no wiring" title="Find and start agents" href="/docs/labs/agents/agent-discovery?ref=docs-labs-agents-overview" linkText="Agent discovery">
Every model agent has `list_agents`, `describe_agent`, and `start_agent` tools by default. Each specialist's result comes back to the lead's inbox, and the loop adds it to the next model call.
</Annotation>

</AnnotatedCode>

A run that starts agents with `start_agent` stays open until they finish, so the lead combines every result in the same run. To start an agent from your own code instead, call `securityReviewer.start({ pr: 42 })` and wait for `.result()`. The [Lead and specialists recipe](/docs/labs/agents/recipes/agent-teams?ref=docs-labs-agents-overview) has the complete project.

## When to use Inngest Agents

| You want to | Use |
| --- | --- |
| Run a model with tools on conversations that last for days, take new messages mid-task, or need a machine per conversation | Inngest Agents |
| Write your own loop around a provider SDK, with full control over every step | A [durable agent](/docs/durable-execution/durable-agents?ref=docs-labs-agents-overview) built with `step.run()` |
| Call a model once inside a workflow | A plain [Inngest function](/docs/durable-execution/primitives/step-run?ref=docs-labs-agents-overview) with the call in a step |

Agents are Inngest functions, so an agent and your plain functions can live in the same app. A scheduled function can message an agent's thread, and an agent's tool can send an event that starts a workflow.
