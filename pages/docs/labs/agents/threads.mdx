# Threads

> Say which events belong together, and their runs share one thread.

A run is thrown away when it ends; a thread is what its runs share.

The sections below grow a PR helper for `acme/web`, built like [`hello`](/docs/labs/agents/agents?ref=docs-labs-agents-threads). After the first block, a block shows only what changes, and [the last section](#a-trigger-with-its-own-key) has the whole file.

## Three events, three strangers

You want one helper for everything that happens to a PR. List its events as triggers.

```typescript {{ title: "inngest/events.ts" }}
import { eventType } from "inngest";
import { z } from "zod";

const ciRun = z.object({ pr: z.number() });

export const prOpened = eventType("pr/opened", {
  schema: z.object({ pr: z.number(), author: z.string() }),
});

export const prComment = eventType("pr/comment", {
  schema: z.object({ pr: z.number(), author: z.string(), body: z.string() }),
});

export const ciFailed = eventType("ci/run.failed", { schema: ciRun });

export const deployed = eventType("deploy/finished", {
  schema: z.object({ env: z.string(), pull: z.number() }),
});

export const prReviewed = eventType("pr/reviewed", {
  schema: z.object({ pr: z.number(), reviewer: z.string(), state: z.string() }),
});
```

```typescript
import { agents } from "../client";
import { ciFailed, deployed, prComment, prOpened } from "../events";

export const prHelper = agents.agent(
  { id: "pr-helper", triggers: [prOpened, prComment, ciFailed, deployed] },
  async ({ event }) => {
    return `Saw ${event.name}`;
  },
);
```

Open a PR, fail its CI and deploy it: three runs on three threads, because none of the events names a thread. None of them knows about the others.

## Which conversation is this?

You want everything about #42 to be one thread. Give the agent a `thread`: an [expression](/docs/durable-execution/guides-and-advanced/writing-expressions?ref=docs-labs-agents-threads) over the `event`.

<AnnotatedCode>

```typescript
{
  id: "pr-helper",
  triggers: [prOpened, prComment, ciFailed, deployed],
  thread: "event.data.pr",
}
```

<Annotation id="thread" lines="4" tease="the PR's number" title="thread" href="/docs/labs/agents/reference?ref=docs-labs-agents-threads#thread-keys-and-inbox-sources" linkText="Thread keys">
Events that carry the same `pr` land on one thread. The key is the number as a string.
</Annotation>

</AnnotatedCode>

Open PR #42 and fail its CI: both land on #42's thread, one run at a time, in order. There's no magic in a thread: it's a key on your own events, and events whose keys come out equal share a thread.

## What a conversation keeps

You want to know what joining a thread gets you. Ask what the last run on it did.

```typescript
async ({ event, previousRun }) => {
  if (!previousRun) {
    return `First run on this thread, saw ${event.name}`;
  }

  return `Last run on this thread ${previousRun.status}. Now saw ${event.name}`;
},
```

The first run gets `previousRun: undefined`; every run after the first gets how the one before it ended. That's the thread talking to its own future run, and it costs nothing to set up — a thread is a run, not a lookup, so it's the thread's own state doing the remembering, not a database you configured. The model's [history](/docs/labs/agents/models?ref=docs-labs-agents-threads#it-remembers) and a [sandbox](/docs/labs/agents/sandboxes?ref=docs-labs-agents-threads#it-belongs-to-the-thread) survive the same way, and so do values you name yourself. [Your own values →](#your-own-values)

A thread is a pair of long-lived functions the SDK serves beside your agent: one keyed on the thread, which never ends while the thread lives, and one that holds the log, the state and every subscription. You declare neither. What it buys you is that **a message a run never got to is not lost** - the thread still holds it, and hands it to the next run on the thread first. [Reference: the thread →](/docs/labs/agents/reference?ref=docs-labs-agents-threads#the-thread)

## No key is fine

You want an agent for one-off jobs. It needs no key.

```typescript {{ title: "inngest/agents/summarize.ts" }}
import { agents } from "../client";

export const summarize = agents.agent(
  { id: "summarize" },
  async ({ event }) => {
    return event.data.content.slice(0, 80);
  },
);
```

Each `start()` is its own thread, with nothing to set up. Its answer is the run's output. To run again on a thread you already have, pass its key: `summarize.start(input, { thread: key })`.

## Two conversations

You want to follow two pull requests at once. The agent needs no change; send CI failures for #42 and #43.

```typescript {{ title: "scripts/failBoth.ts" }}
import { inngest } from "../inngest/client";

await inngest.send([
  { name: "ci/run.failed", data: { pr: 42 } },
  { name: "ci/run.failed", data: { pr: 43 } },
]);
```

`thread` is the handle to the run's own thread, so `thread.key` names it: `"42"` or `"43"`.

```typescript
async ({ event, thread }) => {
  return `Saw ${event.name} on ${thread.key}`;
},
```

Each pull request has its own thread, with its own runs and state. Code turns the key back into the PR's number with `Number(thread.key)`.

## Your own values

You want to count CI failures on the PR. `kv.thread` keeps a value of your own on the thread, under a name you choose.

<AnnotatedCode>

```typescript
async ({ event, kv, thread }) => {
  if (event.is(ciFailed)) {
    const failures = ((await kv.thread.get<number>("failures")) ?? 0) + 1;

    await kv.thread.set("failures", failures);

    return `CI has failed ${failures} times on ${thread.key}`;
  }

  return `Saw ${event.name} on ${thread.key}`;
},
```

<Annotation id="get" lines="3" tease="no round trip" title="get" href="/docs/labs/agents/reference?ref=docs-labs-agents-threads#thread-state" linkText="Reference: thread state">
The run already holds the thread's state, so a `get` is local. It costs no step and nothing to wait for.
</Annotation>

<Annotation id="set" lines="5" tease="one event, no ack" title="set" href="/docs/labs/agents/reference?ref=docs-labs-agents-threads#thread-state" linkText="Reference: thread state">
One event to the thread, which is the only writer. Fire and forget: one step, no ack, no retry.
</Annotation>

</AnnotatedCode>

Fail CI on #42 three times and the third run says `CI has failed 3 times on 42`.

`kv.thread` is a shape you already recognise, and that is all it is - **it is not a key-value store, and there is no store behind it.** A `get` reads what this run was handed when it started; a `set` sends the thread one write, which the thread applies in the one order it has. There is nothing to configure, nothing to provision and nothing to bind.

`delete(key)` drops a key, the same way, and `all()` gives every key the run holds.

## Watch for something else

You want the helper to follow reviews of this PR, which the agent's definition says nothing about. `thread.listen` asks the thread to watch for an event.

```typescript
import { prReviewed } from "../events";

async ({ event, thread }) => {
  if (event.is(prOpened)) {
    await thread.listen(prReviewed, { "data.pr": Number(thread.key) });
  }

  return `Saw ${event.name} on ${thread.key}`;
},
```

`pr/reviewed` is not one of the agent's triggers and not an `inbox` source: the thread subscribes to it because this run asked, and from then on a review of #42 reaches the thread as a message like any other.

The **thread** holds the watch, not this run, so it outlives the run that asked for it and the events reach whichever run is live when they land. `thread.unlisten(prReviewed, { "data.pr": 42 })` drops it again, with the same event and filter it was asked for. Both return whether the thread confirmed.

This is for a handler. An agent with a `model` needs neither: the model has the same two things as tools, because what to watch for is usually its decision rather than yours. [Watching for things →](/docs/labs/agents/tools?ref=docs-labs-agents-threads#watching-for-things)

## A trigger with its own key

You want deploys in the thread too, though the deploy event names the PR `pull`. Give that trigger its own `thread`; it wins over the agent's.

```typescript {{ title: "inngest/agents/prHelper.ts" }}
import { agents } from "../client";
import { ciFailed, deployed, prComment, prOpened } from "../events";

export const prHelper = agents.agent(
  {
    id: "pr-helper",
    triggers: [
      prOpened,
      prComment,
      ciFailed,
      { event: deployed, thread: "event.data.pull" },
    ],
    thread: "event.data.pr",
  },
  async ({ event, thread }) => {
    return `Saw ${event.name} on ${thread.key}`;
  },
);
```

Every kind of event lands on #42's thread.
