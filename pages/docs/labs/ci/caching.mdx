# Caching

> Skip a job when nothing it depends on has changed, and restore its machine instead.

<Info>
  Inngest CI is an Inngest Labs project: early, moving fast, and shaped by your feedback. [What's Labs?](/docs/labs?ref=docs-labs-ci-caching)
</Info>

A job's `cache` skips the job when its key is unchanged. A job that started a machine is restored from its snapshot, so `from(base)` clones the saved machine without running `base` again.

```typescript {{ title: "TypeScript" }}
const base = ci.job(
  {
    id: "base",
    cache: {
      key: files("pnpm-lock.yaml", ".nvmrc"),
      refresh: [{ cron: "0 3 * * *" }],
    },
  },
  async () => {
    await checkout();
    await $`pnpm install`;
  },
);
```

A restored machine has the checkout from the commit it was built on. Jobs that start from it call `checkout()` again to move to this run's commit, and keep the installed dependencies:

```typescript {{ title: "TypeScript" }}
const test = ci.job("test", async () => {
  await from(base);
  await checkout();
  await $`pnpm test`;
});
```

## Shared by every run

Inngest keeps a cached job's machine as a snapshot and finds it again by its cache key, so every run shares it: CI on GitHub, your teammates, and your [local runs](/docs/labs/ci/local?ref=docs-labs-ci-caching) alike. Build `base` once, and every run with the same key starts from it.

- A pull request reads its own entries and its base branch's, and writes only its own, so one pull request never changes what another one reuses.
- A push to a branch reads and writes that branch's entries.
- Entries expire with their snapshot. The next run that needs one builds it again.

## Choose the key

A key is `files()`, a string, an array of them, or an async function that returns a string. `files()` hashes the matched files in the git tree for the run's commit. Locally it hashes your working tree, so an uncommitted change to a matched file is a new key.

```typescript {{ title: "TypeScript" }}
key: files("migrations/**", "seeds/**")
key: [files("go.mod", "go.sum"), "go1.25"]
```

A job's input is part of its cache identity, so the same key with a different input is a different entry. The first run with a new key always misses. A cached job that runs no commands has no machine to snapshot, so it runs again every time. A reused job shows as `Cached <time> ago` on its check.

## Chains of cached jobs

A cached job also depends on the cached jobs it starts [`from()`](/docs/labs/ci/machines?ref=docs-labs-ci-caching#start-a-job-from-another-job). When a parent changes its key, or the input it was called with, the child's entry is stale and the child runs again, through the whole chain of cached parents.

An uncached parent has no key and never invalidates its children. Add its files to the child's key when the child depends on them.

## Refresh ahead of time

`refresh` takes triggers that rebuild the cache on a schedule, so pull requests do not pay for it. Set `repo` on the pipeline so a cron has a repository to check out.

## Share across branches

`scope` is `"branch"` by default, which reads and writes entries as described in [Shared by every run](#shared-by-every-run). Set `scope: "global"` to share one set of entries across every branch and pull request.
