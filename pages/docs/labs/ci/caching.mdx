# Caching

> Skip a job when nothing it depends on has changed, and start from its machine instead.

<Info>
  Inngest CI is an Inngest Labs project: early, moving fast, and shaped by your feedback. [What's Labs?](/docs/labs?ref=docs-labs-ci-caching)
</Info>

Give a job a `cache` key, and its machine is kept as a snapshot under that key. Jobs that start [`from`](/docs/labs/ci/base-images?ref=docs-labs-ci-caching) it reuse the snapshot until the key changes, so `pnpm install` runs once per lockfile instead of once per run.

```typescript {{ title: "TypeScript" }}
const base = ci.job(
  {
    id: "base",
    cache: {
      key: files("pnpm-lock.yaml", ".nvmrc"),
      warm: [{ cron: "0 3 * * *" }],
      maxAge: "7d",
    },
  },
  async () => {
    await checkout();
    await $`pnpm install`;
  },
);

const test = ci.job({ id: "test", from: base }, async () => {
  await checkout();
  await $`pnpm test`;
});
```

A reused machine has the checkout from the commit it was built on. `test` calls `checkout()` to move to this run's commit and keeps the installed dependencies. A reused job shows as `Cached <time> ago` on its check.

## Shared by every run

Snapshots are found by name, so every run shares them: CI on GitHub, your teammates, and your [local runs](/docs/labs/ci/local?ref=docs-labs-ci-caching) alike. Build `base` once, and every run with the same key starts from it.

- A pull request reads its own snapshots and its base branch's, and writes only its own, so one pull request never changes what another one reuses.
- A push to a branch reads and writes that branch's snapshots.
- A local run reads the shared ones and writes its own, so your laptop never changes what CI reuses.

When many runs need the same missing snapshot at once, it's built once and they all start from it. [Base images](/docs/labs/ci/base-images?ref=docs-labs-ci-caching#built-once-then-reused) shows how.

## Choose the key

A key is `files()`, a string, an array of them, or an async function that returns a string. `files()` hashes the matched files in the git tree for the run's commit. Locally it hashes your working tree, so an uncommitted change to a matched file is a new key.

```typescript {{ title: "TypeScript" }}
key: files("migrations/**", "seeds/**")
key: [files("go.mod", "go.sum"), "go1.25"]
key: files("schema.graphql", { repo: "acme/api", ref: "main" })
```

`files()` can hash another repository: pass `repo`, and optionally `ref`, to rebuild when a file there changes.

A snapshot's name holds more than the key. It also holds the job's input and the snapshot the job started from, so:

- The same key with a different input is a different snapshot.
- A cached job rebuilds when anything it starts from changes, all the way up its chain. [See it in action](/docs/labs/ci/base-images?ref=docs-labs-ci-caching#chains-rebuild-from-the-change-down).
- A job on a parent with no `cache` rebuilds every run, since that parent is built fresh each time. Cache the parent too.

The first run with a new key always builds. A cached job that runs no commands has no machine to keep, so it runs every time.

## Warm the cache ahead of time

Without `warm`, a snapshot is built the first time a run needs it, and that run's jobs wait for the build. `warm` takes triggers that build it ahead of time instead, so pull requests find it ready:

```typescript {{ title: "TypeScript" }}
cache: {
  key: files("pnpm-lock.yaml"),
  warm: [github.push({ branches: ["main"] }), { cron: "0 3 * * *" }],
},
```

<CiBuilds scenario="just-in-time" />

A warm run does nothing when the snapshot is already there, so warming often is cheap. A cron has no repository of its own, so set `repo` on the pipeline. `warm` builds the job without an input; a job that takes one is built the first time each input is needed.

When a run had to wait for a build, its summary says so, and tells you whether `warm` would help:

```text
built just in time: `base` (add `cache.warm` to build it ahead of time)
built just in time: `base` (not warmed for these inputs yet)
```

## Set a maximum age

`maxAge` rebuilds a snapshot once it's older than the age you give, even when its key hasn't changed. Use it for setup that drifts without a file changing, like `apt-get upgrade` or `latest` tags.

```typescript {{ title: "TypeScript" }}
cache: { key: files("Dockerfile.ci"), maxAge: "1d" },
```

Ages are written like `"30m"`, `"1h30m"` or `"7d"`. The rebuild takes the same name, and cached jobs that start from it rebuild on the new snapshot. Without `maxAge`, a snapshot is reused until its key changes or it expires.

## Rebuild on demand

Send `invalidateEvent()` to throw away a job's snapshots, for example after rotating a credential baked into the image. Running jobs carry on, and the next run that needs the job rebuilds it.

```typescript {{ title: "TypeScript" }}
import { invalidateEvent } from "@inngest/ci";

await inngest.send(invalidateEvent("base"));
await inngest.send(invalidateEvent(base, { scope: "main" }));
```

Without `scope`, every branch's snapshots of the job are removed. Pass a branch, `pr:<number>`, `global`, or `local` to remove only that scope's.

## Share across branches

`scope` is `"branch"` by default, which reads and writes snapshots as described in [Shared by every run](#shared-by-every-run). Set `scope: "global"` to share one set across every branch and pull request.
