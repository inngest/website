# Base images

> Start a job on a machine that's already set up, so dependencies are installed and output is built before its first command.

<Info>
  Inngest CI is an Inngest Labs project: early, moving fast, and shaped by your feedback. [What's Labs?](/docs/labs?ref=docs-labs-ci-base-images)
</Info>

Set `from` on a job to start it on a copy of another machine. That machine is its base image, and it can be:

- **Another job** in your app, like a `base` job that installs dependencies.
- **A job in another app**, like a shared toolchain image your platform team owns.
- **A snapshot you captured** from a [Sandbox](/docs/sandboxes/overview?ref=docs-labs-ci-base-images).

```typescript {{ title: "TypeScript" }}
const base = ci.job(
  { id: "base", cache: { key: files("pnpm-lock.yaml") } },
  async () => {
    await checkout();
    await $`pnpm install`;
  },
);

const build = ci.job(
  { id: "build", from: base, cache: { key: files("src/**") } },
  async () => {
    await checkout();
    await $`pnpm build`;
  },
);

const test = ci.job({ id: "test", from: build }, async () => {
  await checkout();
  await $`pnpm test`;
});
```

`test` starts with dependencies installed and the project built. When nothing has changed, neither `base` nor `build` runs again: every run, on any branch and on your laptop, starts from the same snapshots.

## Start a job from another job

`from: base` starts the job on its own copy of `base`'s machine, like a Docker layer. The parent runs once in a run of its own however many jobs start from it, and each child gets an isolated copy, so jobs can't affect each other.

- A copy has the checkout from the commit it was built on. Call `checkout()` again to move it to this run's commit; only the changes are applied.
- Calling a job directly always runs it, so a job you both call and start from runs twice.
- A parent that takes an input is named with `.with()`: `from: build.with("web")`.
- To pick the parent from the job's own input, pass a function: `from: ({ input }) => build.with(input.target)`.
- A matrix takes `from` too, and every combination starts from it:

```typescript {{ title: "TypeScript" }}
const compat = ci.matrix(
  { id: "compat", axes: { node: ["20", "22"] }, from: base },
  async ({ node }) => {
    await checkout();
    await $`pnpm test`.env({ NODE_VERSION: node });
  },
);
```

`from` is checked when your app starts: a parent that isn't defined, an input that doesn't match the parent's `input` schema, or a chain that starts from itself throws before any run. A `from` function is checked when it runs. To choose between parents at run time, define both jobs and call the one you need from the pipeline.

## Built once, then reused

A cached job's snapshot is named after everything that went into it: its [cache key](/docs/labs/ci/caching?ref=docs-labs-ci-base-images#choose-the-key), its input, and the exact snapshot it started from. A job looks its parent up by that name before it starts.

<CiBuilds scenario="cold" />

When the name is found, the job starts from it straight away, with nothing to build and nothing to wait for:

<CiBuilds scenario="warm" />

A missing name is built once, however many jobs and runs ask for it at the same moment. Builds of one name take turns and look the name up again when they start, so the first one builds it and the rest start from its snapshot:

<CiBuilds scenario="herd" />

## Chains rebuild from the change down

Because each name includes the snapshot its job started from, a change anywhere in a chain gives every job after it a new name. Those jobs miss and rebuild in order, and the jobs above the change are still reused. A job never starts from a snapshot built on an older parent.

<CiBuilds scenario="invalidate" />

Give the parent of a cached job a `cache` too. A parent without one is built fresh in every run, so its children never find a snapshot to reuse.

## Start from a snapshot you captured

`image.custom(name)` starts a job from the newest ready snapshot with that name. Capture one from any Sandbox with `sandbox.snapshot({ name })`, for example a machine with your toolchain or a large dataset on it.

```typescript {{ title: "TypeScript" }}
const agent = ci.job(
  { id: "agent", from: image.custom("agent-deps") },
  async () => {
    await checkout();
    await $`pnpm test:agent`;
  },
);
```

Capture it again under the same name to update it. A cached job on a captured image is keyed on that snapshot, so the next run rebuilds it on the new one.

To start every job without a `from` on an image, set it on `createCi`:

```typescript {{ title: "TypeScript" }}
const ci = createCi(inngest, { from: image.custom("agent-deps") });
```

Names starting with `ci/` belong to CI's own snapshots, so capture yours under another name.

## Start from another app's job

`image.job("app/job")` starts a job from a job defined in another app, such as a base image your platform team owns and every service builds on. Pass an input as the second argument when the job takes one.

```typescript {{ title: "TypeScript" }}
const test = ci.job(
  { id: "test", from: image.job("platform/node-base") },
  async () => {
    await checkout();
    await $`pnpm test`;
  },
);
```

The owning app looks the job up and builds it if it's missing, once for every app that asks, from the commit it's deployed from. Your job starts from the result. When the owner changes the job, everything built on it rebuilds.

<CiBuilds scenario="cross-app" />

- Both apps must run `@inngest/ci` in the same Inngest environment.
- The owning app reads its repository and commit from its host: Vercel, Netlify, Render, Railway, GitHub Actions, or a git checkout. A job that calls `files()` or `checkout()` fails with an error naming the job when the deployment doesn't say which repository it came from.
- A chain of `image.job()` calls that comes back to a job already in it fails instead of waiting forever.
