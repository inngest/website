# Base images & caching

> Start jobs from a machine that's already set up, and keep it ready across pipeline runs.

A lot of CI time goes on redoing work that's already been done: installing dependencies, compiling, setting up tools. In `@inngest/ci`, a job can pick up where another one left off, and caching lets that carry over from one pipeline run to the next.

## Every job gets its own machine

Each job runs on a fresh machine with Node, Python, git and the usual tools, which is enough for a quick job like this:

```typescript {{ title: "ci/jobs.ts" }}
const lint = ci.job({ id: "lint" }, async () => {
  await checkout();
  await $`npx eslint .`;
});
```

For anything heavier, we probably don't want every job repeating the same setup.

## Start where another job left off

`from` points a job at another job. It starts on a copy of that job's machine, with everything it installed still in place.

```typescript {{ title: "ci/jobs.ts" }}
const install = ci.job({ id: "install" }, async () => {
  await checkout();
  await $`npm ci`; // ← runs once
});

const test = ci.job({ id: "test", from: install }, async () => {
  await checkout(); // ← moves to this commit, keeps node_modules
  await $`npm test`; // ← nothing to install
});
```

When a pipeline run needs `install`, Inngest runs it once and snapshots its machine. Every job that starts from it begins from that snapshot.

<CiBuilds scenario="parent-once" />

`install` was built **just in time**, the first time this pipeline run needed it. The job you point at can be in the same pipeline, elsewhere in your app, or in another app ([Jobs from anywhere](#jobs-from-anywhere)).

Jobs that aren't inline are built in their own run, with their own trace, so you can open the build on its own.

That snapshot only lasts for the pipeline run, though. Push again, and `install` runs again from scratch.

<CiBuilds scenario="two-runs" />

## Keep it across pipeline runs with `cache`

Give the job a `cache` key, and its snapshot is kept as a **base image** for later pipeline runs to start from.

```typescript {{ title: "ci/jobs.ts" }}
const install = ci.job(
  {
    id: "install",
    cache: { key: files("package-lock.json") }, // ← rebuild only when this changes
  },
  async () => {
    await checkout();
    await $`npm ci`;
  },
);
```

The first pipeline run builds it, and later ones start from it straight away.

<CiBuilds scenario="cache-key" />

When `package-lock.json` changes, the key changes and the base image is rebuilt. That also happens just in time: the next pipeline run that needs it builds it and waits. You'll see that in the trace:

<CiBuilds scenario="warn-jit" />

## Build it ahead of time with `cache.refresh`

Rather than letting a pipeline run wait, rebuild the base image in the background. `refresh` takes any trigger: a schedule, a push, or your own event.

```typescript {{ title: "ci/jobs.ts" }}
cache: {
  key: files("package-lock.json"),
  refresh: [
    { cron: "0 3 * * *" },
    github.push({ branches: ["main"] }),
  ], // ← rebuild in the background
},
```

<CiBuilds scenario="refresh" />

You can also cap a base image's age with `maxAge: "7d"`, or force a rebuild by sending `ci/base-image.invalidate`. See [triggers](/docs/labs/ci/pipelines?ref=docs-labs-ci-base-images#triggers) and [crons](/docs/guides/scheduled-functions?ref=docs-labs-ci-base-images).

## Many pipeline runs at once

When several pipeline runs need the same base image at the same moment, only one builds it. The rest wait for that build, then all carry on in parallel.

## Jobs from anywhere

`from` works the same wherever the job lives.

```typescript {{ title: "ci/jobs.ts" }}
import { image } from "@inngest/ci";
import { install } from "./install";

const test = ci.job({ id: "test", from: install }, fn); // ← in this pipeline, or imported from elsewhere in your app

const web = ci.job(
  { id: "web", from: image.job("platform/install") }, // ← a job in another app
  fn,
);
```

<CiBuilds scenario="cross-app" />

Every job that isn't inline is built in its own run, with its own trace, linked from the pipeline run. That makes a slow or failed build easy to look into on its own.

```text {{ title: "Trace of the pipeline run" }}
test
  Build install in its own run     41s    view run →
  $ npm test                       12s
```

```text {{ title: "Trace of the build run" }}
install
  Start sandbox
  checkout
  $ npm ci
  Save sandbox
```

## Start from an image directly

Sometimes you just want a ready-made machine and no job:

```typescript {{ title: "ci/jobs.ts" }}
import { image } from "@inngest/ci";

const a = ci.job({ id: "a", from: image.docker("node:22") }, fn); // ← any Docker Hub image, pulled once and kept
const b = ci.job({ id: "b", from: image.inngest("node") }, fn); // ← one of Inngest's runtime images
const c = ci.job({ id: "c", from: image.custom("ghcr.io/acme/ci") }, fn); // ← your own registry
const d = ci.job({ id: "d", from: image.snapshot("my-snapshot") }, fn); // ← a snapshot you saved by name
```

These are used exactly as they are. Nothing is built or refreshed for you, so for anything you'd otherwise set up with commands, start from a job.
