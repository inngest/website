# `step.run`

> Retry failed work without repeating earlier completed steps.

Put receipt generation in `step.run` so Inngest can retry that work and reuse its successful result when the function resumes. Keep the step ID stable so the run can find that saved result after a deployment.

## TypeScript v4 API

```typescript
step.run(id: string, handler: () => T | Promise<T>): Promise<T>
```

- `id` names the step in logs and identifies its saved state. Give each logical operation a stable, descriptive ID. The SDK counts repeated calls with the same ID, including calls in a loop.
- `handler` runs synchronous or asynchronous code. Return the data later steps need, or return nothing for work with no result.
- `step.run` returns a Promise. Use `await` when later work needs the result.

## Build a receipt

This function builds a receipt when an order is paid. The client import assumes you have created an Inngest client in `./client`.

```typescript
import { inngest } from "./client";

export const createReceipt = inngest.createFunction(
  { id: "create-receipt", triggers: { event: "shop/order.paid" } },
  async ({ event, step }) => {
    const receipt = await step.run("build-receipt", () => ({
      orderId: event.data.orderId,
      issuedAt: new Date().toISOString(),
    }));

    return receipt;
  }
);
```
The `build-receipt` result is saved. If the function resumes, Inngest supplies that result instead of running the handler again.

## Retries and side effects

If the handler throws, Inngest retries this step according to the function's `retries` setting. Each `step.run` call has its own retry count. By default, a step gets one initial attempt and up to four retries. A completed earlier step keeps its saved result.

Put database writes and API calls inside `step.run` so a resumed function does not repeat completed work. A failed attempt can still have changed an external system before it threw or timed out. Use an idempotency key, an upsert, or another duplicate-safe operation for effects that a retry could repeat. Use a non-retriable error for a permanent failure; catch an exhausted step failure when the workflow can recover or compensate.

## Results and limits

Inngest serializes returned values as JSON. Return only the data later work needs; for example, return a record ID instead of an entire record. Current platform limits are:

- 4 MiB step results
- 32 MiB total function run state
- 1,000 steps per function
- A step can run for up to two hours, subject to the hosting provider's shorter timeout
