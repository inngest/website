# `step.subscribe`

> Receive a stream of events inside a running function, and read them when you're ready.

<Compatibility endpoints={false} />

`step.waitForEvent()` waits for one event. `step.subscribe()` opens an inbox that keeps every matching event that arrives, in order, while the run does other work.

It's useful when:

- A run follows something that changes many times, like a pull request's reviews and checks.
- Events can arrive while the run is busy, and none may be missed.
- You want to handle everything that piled up in one go.

<Callout variant="info">
  `step.subscribe()` is experimental in the TypeScript SDK, and the API may change. Run it on the latest Dev Server. Python and Go don't support it yet.
</Callout>

## Merge a pull request when it's ready

This function listens to one pull request's reviews and checks, and merges it once it is approved and passing.

<AnnotatedCode>

```typescript {{ title: "TypeScript" }}
import { eventType, Inngest } from "inngest";
import { z } from "zod";
import { mergePr } from "./github";

const inngest = new Inngest({ id: "github-bot" });

const prOpened = eventType("github/pr.opened", {
  schema: z.object({ pr: z.number() }),
});
const prReviewed = eventType("github/pr.reviewed", {
  schema: z.object({ pr: z.number(), approved: z.boolean() }),
});
const prChecked = eventType("github/pr.checked", {
  schema: z.object({ pr: z.number(), passed: z.boolean() }),
});

export const autoMerge = inngest.createFunction(
  { id: "auto-merge", triggers: [prOpened] },
  async ({ event, step }) => {
    await using inbox = step.subscribe("pr-activity", [
      { event: prReviewed, if: "async.data.pr == event.data.pr" },
      { event: prChecked, if: "async.data.pr == event.data.pr" },
    ]);

    let approved = false;
    let passed = false;

    for await (const message of inbox) {
      if (prReviewed.is(message)) {
        approved = message.data.approved;
      }

      if (prChecked.is(message)) {
        passed = message.data.passed;
      }

      if (approved && passed) {
        break;
      }
    }

    await step.run("merge", () => mergePr(event.data.pr));
  },
);
```

</Annotation>

<Annotation id="sources" lines="21-22" tease="written like triggers" title="Sources" href="/docs/durable-execution/guides-and-advanced/writing-expressions" linkText="Writing expressions">

Send `github/pr.reviewed` and `github/pr.checked` with the same `pr`. Events for other pull requests don't reach this run.

## Read in batches

When events arrive faster than you handle them, take everything that piled up at once. This digest tells a pull request's owner about new comments at most once an hour, and stops after a quiet day.

```typescript {{ title: "TypeScript" }}
const prCommented = eventType("github/pr.commented", {
  schema: z.object({ pr: z.number(), body: z.string() }),
});

export const commentDigest = inngest.createFunction(
  { id: "comment-digest", triggers: [prOpened] },
  async ({ event, step }) => {
    await using inbox = step.subscribe("comments", {
      event: prCommented,
      if: "async.data.pr == event.data.pr",
    });

    while (true) {
      const batch = await inbox.nextBatch({ max: 50, timeout: "1d" });

      if (!batch) {
        return;
      }

      await step.run("notify-owner", () => {
        return notifyOwner(event.data.pr, batch);
      });

      await step.sleep("wait-an-hour", "1h");
    }
  },
);
```

Comments that arrive during the hour's sleep are kept, and the next `nextBatch()` takes all of them.

- `nextBatch()` waits for at least one message, then takes every unread one.
- `drain()` takes every unread message now and never waits. It returns `[]` when there are none.
- `max` caps a batch. The rest stays unread, oldest first.
- `for await (const batch of inbox.batches())` reads batch after batch.

## Read one kind, or listen to more

A view is another reader on the same inbox. Every reader keeps its own place, so reading from a view never takes messages from the inbox.

```typescript {{ title: "TypeScript" }}
const reviews = inbox.of(prReviewed);
const review = await reviews.next({ timeout: "1h" });

await using deploys = inbox.listen({
  event: deployFinished,
  if: "async.data.pr == event.data.pr",
});
const deploy = await deploys.next({ timeout: "1h" });
```

- `of(types)` reads only those event types. It reads from the start of the inbox, and the same types always give the same view.
- `listen(sources)` adds sources from now on, and reads only what they receive. Closing it stops those sources; the inbox keeps its copies.

## Close an inbox

`close()` stops the sources, ends any read that is waiting, and returns the messages that reader hadn't read. Closing the inbox closes every view on it. `await using` calls `close()` at the end of the block.

```typescript {{ title: "TypeScript" }}
const inbox = step.subscribe("approvals", approvalRecorded);

const first = await inbox.next({ timeout: "1h" });
const unread = await inbox.close();
```

After `close()`, reads return `undefined` and `drain()` returns `[]`.

## API

```ts {{ title: "TypeScript" }}
const inbox = step.subscribe(id, sources);
```

- **`id`**: a stable step ID.
- **`sources`**: one source or an array. A source is an event type, an event name, or `{ event, if }`.
- **Returns** an `Inbox` at once. Read it with:
  - `next()`: the next message. With `{ timeout }`, `null` if none arrives in time.
  - `nextBatch({ max, timeout })`: every unread message, waiting for at least one.
  - `drain({ max })`: every unread message now.
  - `for await` over the inbox, or over `inbox.batches({ max })`.
  - `of(types)` and `listen(sources)`: views.
  - `close()`: stops the inbox and returns its unread messages. `closed` is then `true`.

Timeouts take a duration such as `"30m"`, milliseconds, or a `Date`. See the [`step.subscribe()` reference](/docs/reference/typescript/v4/functions/step-subscribe) for every type.

## Things to know

- **Open before you act.** An inbox receives only events that arrive after it opens, like `step.waitForEvent()`. Open it before the step that causes the events.
- **Racing a read.** To continue when either a read or a step settles first, race them inside [`group.parallel()`](/docs/durable-execution/primitives/group-parallel#continue-after-the-first-step-settles). A read that loses keeps its place and takes the next message, so keep it and reuse it.
- **Read in the foreground.** A read loop left running in the background beside other steps can keep the run from finishing, even after you close the inbox.

## How it works

- Each message is saved as its own step the moment it arrives, read or not. It is saved once, however many views read it.
- Opening, `listen()`, `close()` and each batch read are one step. `of()` and a `next()` that finds a message waiting add none, so a `next()` loop over 10 messages is 11 steps.
- Messages count toward the run's [step and state limits](/docs/durable-execution/limits#platform-limits). A run that receives more fails with the usual limit error, even while it sleeps.
