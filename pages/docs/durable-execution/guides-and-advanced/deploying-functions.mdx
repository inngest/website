# Deploying functions

> Deploy durable functions alongside your app while Inngest coordinates their runs.

Serve functions from AWS, Google Cloud, Vercel, Cloudflare, or another compatible host while Inngest coordinates durable runs. When Inngest compute becomes available, you can place another app there in the same environment; compute placement is per app.
Compute placement belongs to an **app**. An environment can include an app on your infrastructure and another app on Inngest compute. You do not need separate Inngest products or environments to use both.
## Deploy on your infrastructure
Your app runs the function code. Inngest triggers runs, tracks their progress, and calls back into your app when work can continue. You can host the app on AWS, Google Cloud, Vercel, Cloudflare, or another compatible runtime. The provider examples below are starting points, not a complete list.
1. **Define your functions in an Inngest app.** Keep the app ID stable across deployments. Register the functions you want this app to expose.
2. **Expose the app to Inngest.** Use an HTTP `serve()` handler for an API route or serverless function. Use Connect for a long-running worker that opens an outbound connection to Inngest.
3. **Configure production credentials and reachability.** Set the Inngest signing key. Set the event key when the app sends events; Connect requires both keys. For HTTP, make the endpoint reachable by Inngest and configure its URL or route as your framework requires. For Connect, allow the worker to connect outbound.
4. **Deploy and sync the app.** HTTP apps need a sync after a deployment changes function definitions. A Connect worker syncs when it connects.
5. **Check the deployed app.** Confirm that Inngest lists the expected functions, then trigger a run and inspect its trace.
Choose HTTP `serve()` for a reachable endpoint or Connect for a long-running worker. [Apps and syncing](/docs/platform-and-operations/apps-and-syncs) explains app IDs and how HTTP deployments register function changes.
### How HTTP and Connect differ

|  | HTTP `serve()` | Connect worker |
| --- | --- | --- |
| Your app provides | A reachable HTTP endpoint | A long-running worker with an outbound persistent connection |
| Common fit | API routes and serverless runtimes | Containers and long-running processes |
| Function sync | Sync the app after relevant deployments | The worker syncs when it connects |
| Main runtime constraint | Provider request and execution limits | A runtime that supports persistent connections |

Both expose your app's Inngest functions. Use HTTP when your app has a reachable endpoint; use Connect when you run a persistent worker with outbound access. Connect does not run on serverless platforms such as AWS Lambda or Vercel.
### Serve functions over HTTP
Use `serve()` when your functions live in an existing web app, API route, or serverless deployment. Your app exposes one reachable endpoint, usually `/api/inngest`. Inngest calls that endpoint to run functions and steps. The handler also returns function metadata and registers definitions during an app sync. Your cloud provider runs the code, so its request duration, memory, and body-size limits still apply.
For TypeScript v4, import the handler for your framework and give it the client and the functions the app exposes:
```typescript
import { serve } from "inngest/next";
import { inngest, functions } from "./inngest";

export const { GET, POST, PUT } = serve({ client: inngest, functions });
```
The endpoint uses `GET` for development metadata, `POST` for invocation, and `PUT` to sync function definitions. In production, set `INNGEST_SIGNING_KEY` on the deployed app. After a deployment changes the functions, sync the app so Inngest sees the new definitions. Confirm the registered functions in the dashboard, then trigger a run. Configure the host to accept requests up to 4 MB. Export the route and methods required by your framework.
The `serve()` handler accepts these options. `client` and `functions` are required. Set `serveOrigin` or `servePath` when a proxy or host prevents the SDK from finding the public URL. Set `streaming` only when the framework and host support streamed responses and you need the host's longer execution window. Configure `signingKey`, `logger`, `baseUrl`, and `fetch` on the Inngest client, not on `serve()`.
### Run Connect workers
Use Connect when you run functions in a long-running process such as a container worker. The worker opens an outbound persistent connection to Inngest, so it needs no public Inngest endpoint or inbound load balancer. Inngest sends work over that connection. Run more workers to add capacity. The connection reduces dispatch latency and avoids HTTP request timeouts for steps, while your worker's own runtime limits still apply. Connect cannot run on serverless runtimes such as AWS Lambda or Vercel.
Start the worker with the app client and its functions:
```typescript
import { connect } from "inngest/connect";
import { inngest, functions } from "./inngest";

const connection = await connect({
  apps: [{ client: inngest, functions }],
  instanceId: process.env.WORKER_ID,
  maxWorkerConcurrency: 10,
});

await connection.closed;
```
In production, set `INNGEST_SIGNING_KEY` and `INNGEST_EVENT_KEY`. Set an `appVersion` on the Inngest client for each deployment so Inngest can track rolling releases. Give each worker a distinct `instanceId`; without one, the SDK attempts to use the worker hostname. Set `maxWorkerConcurrency` to cap simultaneous steps on that worker. The default has no worker-level cap, though account limits still apply. Keep the installed `inngest` package in a bundled worker's runtime image.
A worker syncs its functions when it connects. If the connection drops, the SDK reconnects; during graceful shutdown, it stops accepting new steps. Check worker connection status and the latest heartbeat in the dashboard. For container readiness checks, report ready only when the connection is active. If every worker is at its capacity, Inngest re-enqueues the step; this does not use a function retry. Check worker readiness and shutdown behavior in your deployment.
### Move from Serve to Connect
Keep the function model and triggers, then test Connect in a separate app before moving an existing Serve app. A migration path for an existing app is TBD. Verify function registration, events, active workers, and new runs before switching production traffic.
### Provider examples
- AWS Lambda and Google Cloud Run Functions use the documented HTTP handlers.
- Vercel has a deployment guide and an integration that can set keys and sync the app.
- Cloudflare Pages has a deployment guide. The HTTP handler reference also covers Cloudflare Workers. Enable Node.js compatibility for `AsyncLocalStorage` when serving on the Workers runtime.
- Connect covers long-running workers on container platforms.
If your provider is not listed, start with the HTTP handler and custom adapter guidance or the Connect requirements. Check that your runtime supports the chosen SDK, connection, request handling, and execution limits.
## Best practices
Check [Limits](/docs/durable-execution/limits) and your SDK's configuration before you deploy. Your cloud provider can also set request duration, memory, payload, and network constraints. [Sandboxes](/docs/sandboxes) are isolated execution within work which Inngest manages without having to deploy new infrastructure.
