# Workflows best practices

> Build workflows that resume safely, fit available capacity, and stay understandable after deployment.

Keep workflows safe to resume and easy to operate after a deployment. Put recoverable work in steps, control repeated side effects, and match concurrency to your app's capacity. Use [Performance](/docs/durable-execution/best-practices/performance) to reduce latency with checkpointing and Connect, the [guides](/docs/durable-execution/guides-and-advanced) for procedures, and the [reference](/docs/sdk/overview/reference) for exact options.
## Put each recoverable action in a step
Wrap database writes, external API calls, and other side effects in `step.run()`. Give separate steps to actions that should retry or appear in a trace independently. Inngest saves a completed step's result, so a later retry can continue without repeating that completed action.
Keep ordinary calculations outside steps when they can run again without changing anything. Do not start a side effect outside a step: the function handler can run again as Inngest resumes a workflow. Use waits and sleeps through step methods so the run can pause with compute stopping.
Choose a boundary at the point where you would want to retry, inspect, or change an action on its own.
One step for an entire long process hides which action failed. A step for every item in a large loop can produce too many steps.  Process a bounded batch in one step or fan work out to separate functions when each item needs its own retry history.
Put recoverable work in named steps so Inngest can reuse saved results when a run resumes.
## Keep step IDs stable
Use a descriptive, unique ID for each step in a function, such as `charge-customer`. Keep that ID when you edit the step's implementation. Avoid IDs made from a timestamp, an input value, or a label you expect to rename. Inngest uses step IDs to find saved results when a run resumes, including after a deployment.
Treat a step ID change as a behavior change for live runs. Before you deploy a change to step order, IDs, or branching, test a run that is waiting or sleeping, deploy the new code locally, and inspect how it resumes. For a substantial rewrite, give the new function a new ID and route new events to it. Keep the old function available until its existing runs finish. Make the event routes mutually exclusive so one event does not start both functions.
Read [Versioning](/docs/durable-execution/guides-and-advanced/versioning) for the deployment procedure.
## Keep run state small
Return only data that later steps need. Store large files and documents in your own storage, then pass a durable reference to the next step. Avoid returning the same large object from several steps or copying it into event data. Step results, event data, and the final return value contribute to the run's persisted state.
Keep loop outputs bounded. If a workflow processes a large collection, split it into batches or child functions instead of accumulating every result in one run. Check the current [Workflows limits](/docs/durable-execution/limits) before choosing batch and payload sizes.
Check the current plan limits before choosing batch sizes and concurrency.
## Make retries safe for external systems
A completed step does not run again on a normal resume. An external request can still succeed and then fail before Inngest records its result. A retry can then send that request again. Give payment, email, provisioning, and database operations a stable idempotency key or another way to detect a prior success. Derive the key from the business operation, not from the retry attempt.
Separate permanent errors from temporary ones. Let transient provider failures retry. Stop retries for invalid input or another condition that another attempt cannot fix. Add a failure handler or a compensating action when an exhausted run needs cleanup or an alert. Verify that the cleanup action is safe if it also retries.
Read [Idempotency](/docs/durable-execution/guides-and-advanced/idempotency) to choose event, function, and external operation keys. Use [Error handling](/docs/durable-execution/guides-and-advanced/error-handling) for the full recovery path, including [Retries](/docs/durable-execution/guides-and-advanced/error-handling/retries), [Failure handlers](/docs/durable-execution/guides-and-advanced/error-handling/failure-handlers), and [Inngest errors](/docs/durable-execution/guides-and-advanced/error-handling/inngest-errors).
## Set deadlines and handle cancellation
Set a start deadline when queued work becomes useless after a certain time. Set a finish deadline when the entire run must end by a certain time. Give waits a timeout and decide what the workflow should do when the expected signal never arrives.
Cancellation takes effect at workflow boundaries. Do not assume it interrupts a step that is already executing. Set timeouts on external calls in your code, and make cleanup explicit for resources that can outlive a cancelled run. Use cancellation events or failure handling where another system needs to know that work stopped.
Use [Timeouts](/docs/durable-execution/guides-and-advanced/cancellation/timeouts) for start and finish deadlines. Use [Events](/docs/durable-execution/guides-and-advanced/cancellation/events) to cancel when a matching business event arrives; match a stable identifier so one run does not cancel another. [Cancellation](/docs/durable-execution/guides-and-advanced/cancellation) explains the boundary, cleanup, and bulk cancellation.
## Protect downstream services from bursts
Set function concurrency to match the database, provider, or tenant you need to protect. Use a concurrency key when separate customers can run independently but one customer needs a cap. Use throttling or rate limiting when an external API has a request budget. A backlog can grow when you accept work faster than your capacity can complete it, so inspect queue delay as well as run duration.
If you use Connect workers, set `maxWorkerConcurrency` to fit each worker's CPU, memory, and connection pool. This worker cap sits alongside function and account concurrency limits. Give each worker a distinct `instanceId` so its capacity is tracked separately. Test burst behavior before increasing concurrency.
Read [Deploying functions](/docs/durable-execution/deploying-functions) for Connect setup, autosync, readiness, and shutdown. Use [Flow control](/docs/durable-execution/flow-control) for function-level controls and [Limits](/docs/durable-execution/limits) for platform boundaries.
## Use middleware for shared behavior and protect sensitive data
Use [Middleware](/docs/durable-execution/guides-and-advanced/middleware) when several functions need the same logging context, dependency setup, error reporting, or data protection. Register it on the client for shared behavior or on one function for a narrower scope. Keep each hook's effect clear so retries and resumes do not duplicate external actions.
For end-to-end encryption of supported workflow data, use [Encryption middleware](/docs/durable-execution/guides-and-advanced/middleware/encryption-middleware). It encrypts step data and function output before Inngest receives them. By default, it encrypts event values only inside `event.data.encrypted`; other event fields remain visible. Put sensitive event values in the encrypted field, keep the key in your secret store, and plan key rotation around runs that still need older data.
## Deploy and observe deliberately
Deploy the same workflow code on your infrastructure through `serve()` or Connect, or on Inngest compute when that option launches. For your own infrastructure, confirm the endpoint or worker can connect to Inngest, has the right keys, and has enough capacity for its configured concurrency. Check the host's request and step duration constraints before relying on a long step.
[Deploying functions](/docs/durable-execution/deploying-functions) covers the Serve and Connect connection models, provider setup, sync, and worker lifecycle. Connect needs a long-running worker and outbound access. Check that the worker is active before declaring it ready; use an app version to track rolling deployments.
After deployment, inspect a test run's trace. Check step results, retry attempts, queue delay, and the function's failure rate. Keep the run ID when investigating a customer report. Use a logger that preserves run context, and put logs with the work they describe so retries do not create confusing duplicates.
Inspect run traces and metrics after deployment to find failures, retries, and slow steps.
## Before you ship
- Can each external action retry without a duplicate charge, message, or resource?
- Will a run that started before this deployment resume with the intended step IDs and branches?
- Are step results and event payloads small enough for the current limits?
- Do deadlines and cancellation events stop work when it no longer has value?
- Do retries, final failure handling, and cleanup leave external systems in a known state?
- Do middleware hooks and encryption settings cover the sensitive data you intend to protect?
- Do concurrency settings protect the slowest downstream service and each Connect worker?
- Can you find a failed run and understand it from its trace and logs?
