# Sandboxes troubleshooting

> Diagnose a failed operation and decide whether it is safe to retry.

## Before you retry

1. **Find the operation.** Note the surface, then read `SandboxError.action`, `code`, `ambiguous`, `retryable`, and `requestId`.
2. **Check state.** Get the Sandbox, process, or snapshot. SDK objects are stale views.
3. **Check the effect.** A failed response can follow success. Inspect results before repeating.
4. **Keep evidence.** Run ID, step ID, error code, request ID, resource IDs, and time.

## `403 access_denied` on create

- Check that the account is on Pro or above, the call targets the intended environment, and the server uses its `INNGEST_SIGNING_KEY`.
- On a lower plan, [upgrade your plan](https://app.inngest.com/billing/plans). Changing name or size does not help.

## Size rejected or no capacity

- Sizes are `1 / 1024`, `2 / 2048`, `4 / 4096`, from one pair. Entitlement or capacity can still reject.
- `compute_unavailable` is temporary.
- Retry with the **same active name and config**. A conflict returns `sandbox_name_taken`.

## Secrets rejected

- Names are exact and case-sensitive, unique, valid env keys, and distinct from literal `env` keys.
- Use the workspace that owns them.
- Clones cannot select new secrets. Pause and resume do not fetch rotated values.

## Created but not ready

- Create waits 120 s for `RUNNING`. A timeout does not cancel or destroy it.
- Get the Sandbox. Wait if `STARTING`. Inspect the error and clean up if `FAILED`.
- Use `runningTimeout: false` to keep the ID, then call `waitUntilRunning`.
- Do not create another while the first may still start.

## Command failed, timed out, or lost output

- Through `step.sandbox`, an exit code outside `exitCodes` fails the step. [Exit codes →](/docs/sandboxes/features/exit-codes?ref=docs-sandboxes-troubleshooting)
- Read it with `getCommandError(err)`. Direct clients return non-zero exits as results.
- Timeouts are 30 s default, 5 min max. `sandbox_exec_timed_out`, `sandbox_exec_output_too_large`, and `operation_ambiguous` can follow a command that ran.
- Check a completion marker before rerunning. Use a managed process for longer work.
- Output caps are 4 MiB direct and a 2 MiB tail through `step.sandbox`. Check `result.output.truncated`.

## `operation_ambiguous`

It means the operation may have completed. It is not a Sandbox state.

```typescript {{ title: "By action" }}
// exec:             inspect external effects or a completion marker
// process.start:    list processes, compare command and start time
// process.signal:   get or wait for the process, then signal only if duplicates are safe
// snapshot.create:  list recent snapshots before creating another
```

- Create, Destroy, Pause, Resume, snapshot Delete, and identical upload are safe to repeat.
- In `step.sandbox` it is non-retryable. Let it surface unless you reconcile.

## Process `LOST` or output missing

- Get the process and Sandbox states. `LOST` follows runtime loss and cannot be recovered.
- Check external effects before starting a replacement.
- Set `includeChildren` explicitly. SDK defaults `true`, REST `false`. Descendant delivery is reliable only with signal 9. Use `false` for graceful `SIGTERM`.
- `sandbox_process_output_not_retained` means evicted. About 512 KiB per process, newest 32 kept.
- `sandbox_process_wait_timed_out` ends the wait, not the process.

## Pause or resume unfinished

- Get the Sandbox. Pause may return `PAUSING`, resume `RESUMING`.
- Wait for `PAUSED` or `RUNNING`. Repeating either continues the transition.
- A `FAILED` or terminal Sandbox cannot resume. Inspect its error.
- Pause can interrupt network connections.

## Snapshot or clone pending or expired

- Create starts as `CREATING`. The SDK waits five minutes. A timeout does not cancel it.
- List recent snapshots before another create. Clone needs `READY`.
- `sandbox_snapshot_not_ready` means wrong status. `sandbox_snapshot_not_found` can mean another workspace.
- `FAILED`, `LOST`, deleted, or expired: snapshot a valid source again.
- Flush application state first. Snapshots are crash-consistent.

## Runtime limit reached

- Each Sandbox gets one hour of active runtime. Paused time is free.
- Get the Sandbox for its state. Save artifacts elsewhere and create a new one for later work. [Runtime expiry →](/docs/sandboxes/limits?ref=docs-sandboxes-troubleshooting#runtime-expiry)

## Is a Sandbox left over?

- Inside a function, nothing is. The run owns it and destroys it, even if the run fails or is cancelled. [Run-owned →](/docs/sandboxes/features/run-owned?ref=docs-sandboxes-troubleshooting)
- `owner: "persistent"` and direct-client Sandboxes stay. Destroy them by ID in `finally`.
- Make cleanup tolerate terminating, terminal, or missing Sandboxes.

## Missing from the trace

- Use `step.sandbox` in a function, with `sandboxMiddleware()` and stable step IDs.
- Open the run in the environment that received the event.
- Direct client and REST calls create no steps.
