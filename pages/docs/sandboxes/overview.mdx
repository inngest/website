Run generated code or test a project in a fully isolated microVM while your durable function coordinates the job. Sandboxes boot in under a second. You can pause and resume the same Sandbox, or snapshot it and clone a new one. Inngest coordinates their lifecycle with the run and shows sandbox activity in the same trace. You can give code its own execution environment without building a separate service to start, stop, and track it.

## Why use a Sandbox?

For example, an agent can edit a repository and run its tests in a Sandbox. The durable function coordinates the task while the generated code runs in a separate microVM.

A durable run can include steps, waits, and retries that span more than one request or process. Sandbox operations belong in that run. Inngest can coordinate the environment as the work advances and record what happened alongside the rest of the execution. This lets you inspect the code execution and the workflow that led to it in one place.

## What you can do

- **Boot quickly.** Start a microVM in under a second when work needs an isolated environment.
- **Run code in isolation.** Keep code that needs its own environment apart from the function's runtime.
- **Run code in one statement.** Python, TypeScript, or shell, with a typed value back. See [Run code](/docs/sandboxes/features/run-code).
- **Fail loudly.** A non-zero exit fails its step and shows red in the trace. See [Exit codes](/docs/sandboxes/features/exit-codes).
- **Pause and continue.** Stop active work and continue when the job is ready.
- **Snapshot and clone.** Save Sandbox state and start a new Sandbox from it. Pause and resume continue the original Sandbox. Files persist through these operations.
- **Call your functions from the Sandbox.** Code in the Sandbox calls your functions as durable steps, with your credentials. See [Tools](/docs/sandboxes/features/tools).
- **Reuse sandbox code.** Wrap a runner in a plain function with typed input and output. See [Reusable sandbox functions](/docs/sandboxes/features/sandbox-functions).
- **Never leak one.** Whatever your run creates is cleaned up when it ends. See [Run-owned Sandboxes](/docs/sandboxes/features/run-owned).
- **Follow the work in a trace.** See sandbox activity with the steps and events of the durable run.

The lifecycle depends on the API you use. `step.sandbox.python`, `step.sandbox.typescript`, and `step.sandbox.sh` start a Sandbox, run code, and destroy it in one call. With `step.sandbox.create()`, `await using` destroys the Sandbox at the end of its scope, and Inngest cleans up anything your run still owns when it ends.

## How Sandboxes fit into Inngest

An Inngest function coordinates the job. It may call a Sandbox for isolated code execution, wait for another event, and continue later. The durable run provides the shared context for those actions. The trace connects the workflow and its Sandbox activity.

Sandboxes provide an execution environment for work inside a run. They are separate from where you host an Inngest app's functions. Inngest [branch deploys](/docs/platform-and-operations/environments-and-branch-deploys) are different: they give a Git branch its own deployment preview and event data.
