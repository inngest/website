Run generated code or test a project in a fully isolated microVM while your durable function coordinates the job. One statement boots a Sandbox, runs Python, TypeScript, or shell, returns the result as a value, and cleans up. Sandboxes boot in under a second. You can pause and resume the same Sandbox, or snapshot it and clone a new one. Inngest ties their lifecycle to the run and shows sandbox activity in the same trace, so you can give code its own execution environment without building a separate service to start, stop, and track it.

```typescript {{ title: "TypeScript" }}
const total = await step.sandbox.python<number>("sum", "return sum(xs)", { input: { xs } });
```

## Why use a Sandbox?

For example, an agent can edit a repository and run its tests in a Sandbox. The durable function coordinates the task while the generated code runs in a separate microVM.

A durable run can include steps, waits, and retries that span more than one request or process. Sandbox operations belong in that run. Inngest can coordinate the environment as the work advances and record what happened alongside the rest of the execution. This lets you inspect the code execution and the workflow that led to it in one place.

## What you can do

- **Run code in one statement.** [Python, TypeScript, and shell runners](/docs/sandboxes/features/run-code?ref=docs-sandboxes-overview) take your data as variables and return a typed value.
- **Boot quickly.** Start a microVM in under a second when work needs an isolated environment.
- **Run code in isolation.** Keep code that needs its own environment apart from the function's runtime.
- **Fail loudly.** A command that exits non-zero fails its step and shows red. [Allow the codes that are information](/docs/sandboxes/features/exit-codes?ref=docs-sandboxes-overview).
- **Call your functions from the Sandbox.** [Tools](/docs/sandboxes/features/tools?ref=docs-sandboxes-overview) run in your function, as durable steps, with your credentials.
- **Give an LLM a Sandbox.** [Sandbox functions](/docs/sandboxes/features/sandbox-functions?ref=docs-sandboxes-overview) become tools for the AI SDK, Anthropic, OpenAI, and MCP.
- **Never leak one.** [Sandboxes and snapshots your run creates are cleaned up when it ends](/docs/sandboxes/features/run-owned?ref=docs-sandboxes-overview), however it ends.
- **Pause and continue.** Stop active work and continue when the job is ready.
- **Snapshot and clone.** Save Sandbox state and start a new Sandbox from it. Pause and resume continue the original Sandbox. Files persist through these operations.
- **Follow the work in a trace.** See each statement as one [SANDBOX group](/docs/sandboxes/features/traces?ref=docs-sandboxes-overview) with the steps and events of the durable run.

The lifecycle follows the API you use. A runner such as `step.sandbox.python()` creates and destroys its own Sandbox. `step.sandbox.create()` returns a handle you can use with `await using`, and `group.sandbox()` wraps a callback. Anything still alive when the run ends is cleaned up.

## How Sandboxes fit into Inngest

An Inngest function coordinates the job. It may call a Sandbox for isolated code execution, wait for another event, and continue later. The durable run provides the shared context for those actions. The trace connects the workflow and its Sandbox activity.

Sandboxes provide an execution environment for work inside a run. They are separate from where you host an Inngest app's functions. Inngest [branch deploys](/docs/platform-and-operations/environments-and-branch-deploys) are different: they give a Git branch its own deployment preview and event data.
