# Sandboxes best practices

> Keep cleanup, retries, and results visible in your workflow.

## Pick the client

- `step.sandbox` in functions. Each call is a durable step with a stable ID.
- `inngest.sandboxes` in trusted server code. It runs immediately, with files and live output, and never retries.
- Keep the client and `INNGEST_SIGNING_KEY` out of browsers.

## Let the run clean up

- Inside a function, the run destroys what it owns. No `onFailure` needed. [Run-owned →](/docs/sandboxes/features/run-owned?ref=docs-sandboxes-best-practices)
- Prefer a runner such as `step.sandbox.python()` when one statement is enough.
- End one early with `await using` or `group.sandbox()`.
- Let failures fail. Use `exitCodes` only where the code is information.
- With the direct client, destroy in `finally`.
- Store the Sandbox ID, not a serialized object. Fetch by ID to reconnect.

```typescript {{ title: "TypeScript" }}
const sb = await step.sandbox.create("work", { runningTimeout: false });

await sb.waitUntilRunning("ready", { timeout: "2m" });
```

## Make retries safe

- Use a stable step ID and job-specific `name` with the same resources. A repeated active name returns the same Sandbox.
- Changed resources for an active name fail with `sandbox_name_taken`.
- Treat `operation_ambiguous` as unknown, not failed. Never repeat on a lost response.
- Let it escape the function unless you reconcile deliberately. [Troubleshooting →](/docs/sandboxes/troubleshooting?ref=docs-sandboxes-best-practices)

## Save results outside

- Read output and files before Destroy.
- Captured output: 4 MiB direct, 2 MiB tail through `step.sandbox`. Check `result.output.truncated`.
- Process logs are best effort. Write important output to a file or store.
- Pause and snapshots are not backups. Snapshots expire.
- Shared files need external coordination between writers.

## Pause or snapshot

- **Pause** to continue one Sandbox under its ID. [Pause and resume →](/docs/sandboxes/features/pause-and-resume?ref=docs-sandboxes-best-practices)
- **Snapshot and clone** for new Sandboxes from a prepared state. [Cloning →](/docs/sandboxes/features/cloning?ref=docs-sandboxes-best-practices)

## Size to the limits

- Sizes are 1 vCPU / 1024 MiB, 2 / 2048, or 4 / 4096.
- One hour of active runtime per Sandbox. Paused time is free. [Limits →](/docs/sandboxes/limits?ref=docs-sandboxes-best-practices)

## Protect credentials

- Keep secrets out of `input`, `env`, and code. They appear in the trace.
- Use `secrets` for names, and [tools](/docs/sandboxes/features/tools?ref=docs-sandboxes-best-practices) to use a credential without holding it.
- Select only the secrets a task needs. Output, files, and snapshots are not redacted.
- Egress is allowed by default. Review what generated code can reach.
- Never put private keys in a Sandbox.
