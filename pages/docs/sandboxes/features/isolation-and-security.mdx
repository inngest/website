# Isolation and security

> Run generated code in a separate microVM with its own files, processes, and network identity.

- **Separate VM.** Isolated from the host and from other Sandboxes. Sandboxes cannot send traffic to each other.
- **Credentials stay home.** Tools keep secrets in your function. [Tools →](/docs/sandboxes/features/tools?ref=docs-sandboxes-isolation-and-security)
- **Nothing outlives the run.** [Run-owned →](/docs/sandboxes/features/run-owned?ref=docs-sandboxes-isolation-and-security)
- **Secrets by name.** Pick workspace secrets at create. [Secrets →](/docs/sandboxes/features/secrets?ref=docs-sandboxes-isolation-and-security)

## How it works

- Each Sandbox has its own filesystem, processes, environment, CPU, and memory.
- Destroying it removes the filesystem, processes, and retained output.
- Network is the workspace's default egress-only VPC. Outbound is allowed, with no public ingress. Validate untrusted URLs.
- Create and control Sandboxes from server code. Keep `INNGEST_SIGNING_KEY` out of browsers.
- Snapshots copy memory, disk, and environment, secrets included. Review before you snapshot.
- Rotating a secret does not revoke values already delivered.
- Planned: SSH and S3-backed shared mounts. [SSH →](/docs/sandboxes/features/ssh?ref=docs-sandboxes-isolation-and-security)
