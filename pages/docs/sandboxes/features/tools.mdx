# Tools and code mode

> Let code in a Sandbox call your functions, with your credentials, as durable steps.

A tool is a function in your Inngest function that code in the Sandbox can call. The code runs in isolation, and the tool runs where your database clients, API keys, and local variables already are. The Sandbox only gets a small stub that asks your function to run it, so credentials never enter the Sandbox.

<AnnotatedCode>

```typescript {{ title: "inngest/functions/churn-report.ts" }}
import { step } from "inngest";
import { tool } from "inngest/experimental";
import { z } from "zod";

const report = await step.sandbox.python(
  "churn-report",
  `
  customers = await tools.listCustomers(plan="pro")
  at_risk = [c for c in customers if c["seats_used"] < c["seats"] * 0.3]

  for c in at_risk:
      await tools.sendSlack(channel="#cs", text=f"{c['name']} is under 30% seat use")

  return {"checked": len(customers), "flagged": len(at_risk)}
  `,
  {
    tools: {
      listCustomers: tool({
        description: "List customers on a plan",
        input: z.object({ plan: z.enum(["free", "pro"]) }),
        output: z.array(Customer),
        run: ({ plan }) => {
          return db.customers.where({ plan });
        },
      }),

      sendSlack: tool({
        input: z.object({ channel: z.string(), text: z.string() }),
        run: ({ channel, text }, ctx) => {
          return slack.post(channel, text, { idempotencyKey: ctx.idempotencyKey });
        },
      }),
    },
    schema: { output: z.object({ checked: z.number(), flagged: z.number() }) },
  },
);
```

## Why tools

- **Your credentials stay yours.** The Slack token, the database, and the retry policy live in your function. The Sandbox sees a stub, not a secret.
- **Every call is durable.** Each call is a step, so it's saved, retried on failure, and shown in the [trace](/docs/sandboxes/features/traces?ref=docs-sandboxes-tools).
- **It works with any code.** Python or TypeScript, written by you or by an LLM, with any model or none.

## Declare tools

Pass `tools` to a runner. Each tool is a plain function or a `tool()` with a schema.

| Form | The Sandbox sees | Use it for |
| --- | --- | --- |
| A plain function: `sendSlack: (msg) => post(msg)` | Positional JSON arguments, untyped. | Quick scripts. |
| `tool({ input, output, run })` | Named arguments, generated types, validation on both sides, and the description as a docstring. | Anything an LLM writes code against. |
| `sandboxFn.tool()` | The same, and the call runs a [sandbox function](/docs/sandboxes/features/sandbox-functions?ref=docs-sandboxes-tools). | Code that calls a library function. |

- `input` and `output` take any [Standard Schema](https://standardschema.dev). With `input` declared, the call takes named arguments: keyword-only in Python, one object in TypeScript.
- A bad call is rejected before any step is created, and the Sandbox gets a `ToolError`.
- `timeout` sets the limit per call and defaults to `"30s"`. Throw `NonRetriableError` in `run` to skip retries.
- `run` receives `(input, ctx)`. `ctx.idempotencyKey` is stable across retries, `ctx.sandbox.id` names the caller, and `ctx.signal` fires at the timeout.

`tools` is accepted by the [runners](/docs/sandboxes/features/run-code?ref=docs-sandboxes-tools), as a default on `step.sandbox.create()` and `group.sandbox()`, and on `sandbox.fn`. A call's own `tools` merge over the default. It isn't available on `sb.$` or `sb.sh`, because a shell line has no language to host a stub. Run a script that needs tools through a runner. On `commands.run`, the script imports the stub itself:

```python {{ title: "Python" }}
from inngest_tools import tools

customer = await tools.getCustomer("cus_1")
```

## Call a tool from the Sandbox

Inside the Sandbox, every tool lives on one global, `tools`. It can't clash with built-ins or your `input` keys.

Inngest generates a typed declaration for each language from your schemas:

```python {{ title: "Python" }}
class Customer(TypedDict):
    id: str
    name: str
    plan: Literal["free", "pro"]
    seats: int
    seats_used: int

class tools:
    @staticmethod
    async def listCustomers(*, plan: Literal["free", "pro"]) -> list[Customer]:
        """List customers on a plan"""

    @staticmethod
    async def sendSlack(*, channel: str, text: str) -> None: ...
```

```typescript {{ title: "TypeScript" }}
declare const tools: {
  /** List customers on a plan */
  listCustomers(input: { plan: "free" | "pro" }): Promise<Customer[]>;
  sendSlack(input: { channel: string; text: string }): Promise<void>;
};
```

`describeTools(tools, "python")` returns the same text, so a model that writes the code sees exactly what it can call.

A tool that throws raises `ToolError` in the Sandbox, which the code can catch. If it isn't caught, the command exits non-zero and [`exitCodes`](/docs/sandboxes/features/exit-codes?ref=docs-sandboxes-tools) decides the row colour, as for any command.

## Every call is a durable step

Each call is its own step, shown in the trace. A run that never calls a tool costs the same as a run without `tools`.

```text {{ title: "Trace" }}
SANDBOX  churn-report
  create
  exec                    exit 0 · 2 waits, folded in
  tool listCustomers      #1
  tool sendSlack          #2
  tool sendSlack          #3
  destroy
```

- Calls found together run in parallel, up to 8 at a time.
- A tool step that fails is retried like any step. When retries run out, or it throws `NonRetriableError`, the Sandbox gets a `ToolError`.
- A reply is limited to 1 MiB, and a request to 256 KiB. Over the limit, the code gets a `ToolError` that says to write large data to a file.
- A run can make 100 tool calls by default.
- The runner's `timeout` covers the whole run, tool time included. It defaults to five minutes when `tools` is set.

## Code mode

Code mode gives an LLM one tool that writes code against all your others. Instead of ten round trips to call ten tools, the model writes a short program and runs it once.

```typescript {{ title: "inngest/functions/support-agent.ts" }}
import { sandbox } from "inngest/experimental";
import { agentLoop, toAnthropic } from "@inngest/sandbox-tools";

const runCode = sandbox.codeTool({
  language: "python",
  timeout: "2m",
  tools: { getCustomer, listInvoices, sendSlack },
});

export const supportAgent = inngest.createFunction(
  { id: "support-agent", triggers: { event: "support/ask" } },
  async ({ event }) => {
    return agentLoop({
      adapter: toAnthropic,
      tools: [runCode],
      model: (messages, defs) => {
        return anthropic.messages.create({ model: "claude-sonnet-4-5", max_tokens: 2048, tools: defs, messages });
      },
      messages: [{ role: "user", content: event.data.question }],
    });
  },
);
```

The model sees one tool, `run_code`, whose description is the typed API of your real functions. It can chain ten calls in one turn, and your schemas reject bad arguments before a step exists.

<Tip>
  The model's code is untrusted, and your tools are the boundary. Expose only what the agent should be able to do, and use `ctx.idempotencyKey` for side effects.
</Tip>

```text {{ title: "Trace" }}
FUNCTION  support-agent
  llm-0        step.run: the model writes the code
  run_code     SANDBOX · 4 tool calls · 3.1s
  llm-1        step.run: the model answers
```

Expand `run_code` to see the exec and each tool call. The agent loop runs in your function, so every model call and every tool call is a step. [Sandbox functions and agents](/docs/sandboxes/features/sandbox-functions?ref=docs-sandboxes-tools#the-agent-loop) shows the loop.
