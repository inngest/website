# Secrets

> Let sandboxed code deploy, publish, push, and call your APIs without holding your long-lived keys.

Anything in a Sandbox can be read by the code running in it. So the question is not how to hide a key from that code, but how to avoid putting the key there at all.

- **Keep the key on your server.** A [tool](#let-a-tool-do-it) runs with your credentials and hands back only the result.
- **Give a command a token that expires.** [Mint it, use it for one command, revoke it](#mint-use-and-revoke-a-token).
- **Let plain `git push` work.** [Command shims](/docs/sandboxes/features/shims) call home: your app pushes with its own token, so none enters the Sandbox.
- **Keep values out of the trace.** [Per-command `env`](#pass-a-secret-to-one-command) is redacted from the run.
- **Select workspace secrets.** For [low-risk keys](#select-workspace-secrets), by name at create.

## Where the secret lives

| Technique | Sandbox code can read it | Stored with the run | Lives until |
| --- | --- | --- | --- |
| [Tool](#let-a-tool-do-it) | No | Tool arguments and result | Your server only |
| [Tool that runs a command with a token](#run-the-command-from-a-tool) | One command | Exit code and the output you return | The token expires or is revoked |
| [Per-command `env`](#pass-a-secret-to-one-command) | That command | Names only, values `[redacted]` | The command, and anything it writes |
| [Command shim](/docs/sandboxes/features/shims) | No | Nothing in the run | Your server only |
| [Credential helper or `*_BASE_URL`](#call-home-for-a-credential) | A short-lived token | The tool result | The token expires |
| [Workspace secrets](#select-workspace-secrets) | Yes, for the Sandbox's whole life | Names only | The Sandbox and its snapshots |

## Pick a technique

| You want to | Use |
| --- | --- |
| Open a PR, query a database, call a billing API, sign something | A [tool](#let-a-tool-do-it). The key never enters. |
| `git clone`, `git push`, `gh`, or another CLI | A [command shim](/docs/sandboxes/features/shims) that does the work in your app, or a short-lived token [run from a tool](#run-the-command-from-a-tool) or as [per-command `env`](#pass-a-secret-to-one-command) |
| `npm publish` or a deploy CLI | A [command shim](/docs/sandboxes/features/shims) that runs it in your app, or a short-lived, single-resource token as [per-command `env`](#pass-a-secret-to-one-command) |
| Cloud SDKs | Short-lived session credentials from your provider, as per-command `env` |
| Call an LLM | A [`*_BASE_URL` route](#call-home-for-a-credential) on your server, else a [workspace secret](#select-workspace-secrets) with a spend cap |

Decide in this order:

1. Can a tool do the work? Use it.
2. Can the credential be short-lived and scoped to one resource? Mint it per use.
3. Only then inject a long-lived key, with a workspace secret.

## Let a tool do it

A [tool](/docs/sandboxes/features/tools) runs in your function, with your credentials. The Sandbox calls it by name and gets the result.

<CodeGroup>
```typescript {{ title: "TypeScript" }}
import { tool } from "inngest/experimental";
import { z } from "zod";

const openPr = tool.step({
  description: "Open a PR for a branch",
  input: z.object({
    branch: z.string().regex(/^[\w./-]+$/),
    title: z.string().max(120),
  }),
  output: z.object({ url: z.string() }),
  run: async ({ branch, title }) => {
    const pr = await octokit.rest.pulls.create({
      owner: "acme",
      repo: "box",
      head: branch,
      base: "main",
      title,
    });

    return { url: pr.data.html_url };
  },
});

await sb.commands.run("agent", "node agent.js", { tools: { openPr } });
```

<SdkUnsupported title="Go" feature="Sandboxes" />
</CodeGroup>

- **`input` is validated before `run` starts.** Arguments come from untrusted code, so constrain them.
- **The result is stored with the run.** Return ids and status, never tokens.
- **The code can only ask for what the tool allows.** Its blast radius is the tool's own surface.

## Pass a secret to one command <VersionBadge version="v4.26.0+" />

`environment` on a `step.sandbox` command, or `env` on `$`, overrides the Sandbox's environment for that command. The SDK records the step with every value replaced by `[redacted]`, then restores the real values before running it. A command run with `tools` records no environment at all.

<CodeGroup>
```typescript {{ title: "TypeScript" }}
const publish$ = sb.$({ env: { NPM_TOKEN: process.env.NPM_TOKEN! } });

await publish$.sh`pnpm publish`;

await sb.commands.run("publish", ["pnpm", "publish"], {
  environment: { NPM_TOKEN: process.env.NPM_TOKEN! },
});
```

<SdkUnsupported title="Python" feature="Sandboxes" />
<SdkUnsupported title="Go" feature="Sandboxes" />
</CodeGroup>

- **The command can read and print the value.** Redaction hides it from the trace, not from the code.
- **Read the value from your app's environment.** If it comes from a step's return value, it is stored with the run.
- **Only `environment` values are redacted.** The command text, step ID, and output are not.
- **Values are literal strings.** A selected workspace secret cannot be passed by name per command, so pair per-command values with a short-lived token.

The same redaction applies to `step.sandbox.create` and `processes.start`. A Create `environment` is also stored as Sandbox configuration, so never put a secret there.

## Mint, use, and revoke a token

A token that expires turns a leak into a small problem. The host keeps one credential that can mint tokens, creates a token for one resource and a few minutes, and revokes it when the command ends.

Do all three in one place. A token returned from `step.run` is stored with the run, so mint and use it inside one tool.

### Run the command from a tool

A tool can mint a token, run the command in the Sandbox with it as `environment`, and revoke it in `finally`. The token exists only in that tool step's memory.

<CodeGroup>
```typescript {{ title: "TypeScript" }}
const sb = await step.sandbox.create("create", {
  name: `pr-${event.data.jobId}`,
  vcpu: 2,
  memoryMb: 2048,
});

const createPr = tool.step({
  input: z.object({ branch: z.string().regex(/^[\w./-]+$/) }),
  output: z.object({ ok: z.boolean(), tail: z.string() }),
  run: async ({ branch }) => {
    const { data } = await appOctokit.rest.apps.createInstallationAccessToken({
      installation_id: installationId,
      repositories: ["box"],
      permissions: { pull_requests: "write", contents: "read" },
    });

    try {
      const sandbox = await inngest.sandboxes.get(sb.id);
      const result = await sandbox!.commands.run(
        ["gh", "pr", "create", "--fill", "--head", branch],
        { cwd: "/work/box", environment: { GH_TOKEN: data.token }, timeout: "2m" },
      );

      return { ok: result.exitCode === 0, tail: result.stderr.slice(-500) };
    } finally {
      await new Octokit({ auth: data.token }).rest.apps.revokeInstallationAccessToken();
    }
  },
});

await sb.commands.run("agent", "node agent.js", {
  tools: { createPr },
  toolOptions: { toolTimeout: "5m" },
});
```

<SdkUnsupported title="Python" feature="Sandboxes" />
<SdkUnsupported title="Go" feature="Sandboxes" />
</CodeGroup>

- **The code cannot pick the command.** It supplies a validated branch name and nothing else.
- **The token is scoped.** One repository, two permissions, and GitHub expires it after an hour if revoke never runs.
- **Return an exit code and a trimmed tail.** Never return raw output.
- **Use the Sandbox your run created.** Do not look one up from untrusted input.
- **Raise `toolTimeout`.** It defaults to 30 seconds.
- **Make the work safe to retry.** A tool that fails runs again. Tools receive an `idempotencyKey` as their second argument; pass it to APIs that deduplicate writes. See [Tools](/docs/sandboxes/features/tools#type-the-arguments-with-toolstep).

`inngest.sandboxes` is the [direct client](/docs/sandboxes/features/managed-lifecycle). It has no step replay, which is why the token stays in the tool's memory.

## Call home for a credential

Two patterns let the Sandbox use a credential without holding a long-lived one.

> **Prefer a shim for git.** [`tool.shim.git()`](/docs/sandboxes/features/shims#push-from-your-app) clones, fetches and pushes from your app, so no token enters the Sandbox at all and there is no credential helper to write.

**A credential helper asks a tool for a token on demand.** Run the command with the tool, and the helper, a child of that command, can call it.

<CodeGroup>
```typescript {{ title: "TypeScript" }}
const gitToken = tool.step({
  output: z.object({ password: z.string() }),
  run: async () => {
    const { data } = await appOctokit.rest.apps.createInstallationAccessToken({
      installation_id: installationId,
      repositories: ["box"],
      permissions: { contents: "write" },
    });

    return { password: data.token };
  },
});

await sb.commands.run(
  "push",
  ["git", "-c", "credential.helper=!node /opt/git-credential.js", "push", "origin", "HEAD"],
  { tools: { gitToken } },
);
```

<SdkUnsupported title="Python" feature="Sandboxes" />
<SdkUnsupported title="Go" feature="Sandboxes" />
</CodeGroup>

```js
// /opt/git-credential.js
const { tools } = require("inngest_tools");

(async () => {
  if (process.argv[2] !== "get") {
    return;
  }

  const { password } = await tools.gitToken();

  console.log("username=x-access-token");
  console.log(`password=${password}`);
})();
```

Git also calls the helper with `store` and `erase`, so the script answers only `get`. Put the helper in your image or write it once with `files.write`; it holds no secret. The result of a tool call is stored with the run, so keep this token short-lived and scoped.

**A `*_BASE_URL` points an SDK at a route on your server.** The route adds the real key and forwards the request, so the key never enters the Sandbox.

<CodeGroup>
```typescript {{ title: "TypeScript" }}
await sb.$({
  env: {
    ANTHROPIC_BASE_URL: "https://app.example.com/llm",
    ANTHROPIC_API_KEY: runToken,
  },
}).sh`node agent.js`;
```

<SdkUnsupported title="Python" feature="Sandboxes" />
<SdkUnsupported title="Go" feature="Sandboxes" />
</CodeGroup>

`runToken` is a per-run token that only your route accepts. The Sandbox can use the route while it is reachable, so expire the token, allowlist what it can call, and rate limit it.

## Select workspace secrets

For keys that are cheap to rotate and cheap to leak, such as a capped LLM key or a read-only token, select existing workspace secrets by exact name when you create a fresh Sandbox. Inngest makes each value available as an environment variable with that name for the Sandbox's whole life.

Secret selection is in the access-gated beta, and its API can change before launch.

> **Note**  Secret injection is not output redaction. Any code in the Sandbox can read selected values. A value printed to stdout, stderr, logs, or files can be returned by the Sandbox APIs.

Create the secrets in the same Inngest workspace that will create the Sandbox. The public Sandbox REST API and JavaScript SDK select existing secrets; they do not create, list, rotate, or archive secret values. Names are case-sensitive, so save a secret under the variable name your application expects, such as `OPENAI_API_KEY`.

### Select secrets at Create

Direct client:

<CodeGroup>
```typescript {{ title: "TypeScript" }}
const sandbox = await inngest.sandboxes.create({
  name: `agent-${crypto.randomUUID()}`,
  vcpu: 1,
  memoryMb: 1024,
  environment: {
    APP_ENV: "beta",
  },
  secrets: ["OPENAI_API_KEY", "GITHUB_TOKEN"],
});
```

The SDK and API send only the names. Values are injected under those same names and inherited by commands and managed processes. Selection is supported only for a fresh Sandbox: a snapshot clone restores the environment captured by its snapshot and cannot select new secrets.

### Environment precedence

Environment is layered in this order:

1. guest defaults;
2. literal Sandbox `environment` values and selected secret values; and
3. command- or process-specific `environment` values.

An operation-specific value can override a selected secret for that operation. A Create request cannot include the same key in both `environment` and `secrets`.

### Rotation and lifecycle

Secret names resolve to stable secret identities when the Sandbox is created.

- Selection order does not affect Create identity.
- Rotating a secret changes the value fetched by a future launch, but does not replace a value already delivered to a running or paused guest.
- Archiving a selected secret and creating another secret with the same name affects new Sandboxes. An existing Sandbox remains bound to the original identity.
- Pause and Resume do not fetch secrets again.
- A user snapshot captures guest memory, disk, and environment after delivery. Values can remain in the snapshot and its clones.
- A clone does not fetch current values and cannot select additional secrets.

Rotation or archival cannot revoke a value already delivered to a guest or captured in a snapshot. Destroy Sandboxes and delete snapshots when their sensitive state is no longer needed.

### Delivery and failure

Unknown, archived, duplicated, or colliding names reject Create as invalid input. If the values cannot be fetched at launch, the launch fails.

### Validation and limits

- Each name is exact and case-sensitive.
- Each name must be non-empty and at most 256 UTF-8 bytes.
- Names cannot have leading or trailing Unicode whitespace.
- Names cannot contain `=`, carriage return, line feed, or NUL.
- Names must be unique and cannot overlap literal `environment` keys.
- Literal environment keys and selected names share a maximum of 256 entries.
- Literal `environment` and selected names together are limited to 64 KiB.

## What not to do

<CodeGroup>
```typescript {{ title: "TypeScript" }}
const token = await step.run("mint", () => {
  return mintToken();
});

await sb.files.write("env", { path: "/work/.env", data: `TOKEN=${token}` });

await sb.$`curl -H ${`Authorization: Bearer ${token}`} https://api.example.com`;
```

<SdkUnsupported title="Python" feature="Sandboxes" />
<SdkUnsupported title="Go" feature="Sandboxes" />
</CodeGroup>

- **A file's contents are stored with the run.** `files.write` is a step, so the data is its input, up to about 2 MiB. It also stays on the Sandbox disk and in every snapshot.
- **Command text and the step ID are stored.** Put the value in `env`.
- **A step's return value is stored.** A token returned from `step.run` stays in step data until the run is purged.

## What is stored with the run

| Value | In the trace |
| --- | --- |
| `environment` or `env` values on a `step.sandbox` call | Names only, values `[redacted]`. A command run with `tools` records none |
| `secrets` | Names only |
| Command text and step ID | Stored |
| Command output | Stored, the last 2 MiB (512 KiB when `timeout` is over 5 minutes) |
| `files.write` data | Stored as step input |
| Tool arguments and results | Stored |
| A value returned from `step.run` | Stored |

Values in the Sandbox itself, on disk or in memory, go into any snapshot you take. Destroy Sandboxes and delete snapshots when their sensitive state is no longer required. See [Managed lifecycle](/docs/sandboxes/features/managed-lifecycle#clean-up-after-failure) for cleanup that runs after a failure.
