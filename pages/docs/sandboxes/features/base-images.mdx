# Base images

> Start isolated work with Node.js, Python, Ruby, and common command-line tools already installed.

Run generated code or inspect a repository without building an image first. The base image includes Node.js, Python, Ruby, and common command-line tools. To pin a language version, pick a [runtime image](#runtime-images).

## What the base image includes

New Sandboxes start from the base image unless you choose another. A Sandbox cloned from a snapshot starts with the captured image and filesystem changes.

| Tool | Included |
| --- | --- |
| Node.js | Latest release as `node`, `npm`, and `npx`; LTS release as `node-lts`, `npm-lts`, and `npx-lts` |
| Python | Python 3.14 |
| Ruby | Ruby 4.0 |
| Repository and network tools | Git, curl, OpenSSH, and CA certificates |
| Shell and utilities | BusyBox `sh`, `grep`, `sed`, `awk`, `ripgrep`, `jq`, `find`, `tar`, and `gzip` |

The base image does **not** include Go, Rust, Java, Bun, or Deno. For Deno and Bun, use a [runtime image](#runtime-images). To use your own image, see [Choose an image](#choose-an-image). Exact installed versions can change when Inngest rebuilds the image. Check versions in the Sandbox if your task depends on them.

Inngest CI jobs start from images the same way: [Base images](/docs/labs/ci/base-images?ref=docs-sandboxes-base-images).

## Choose an image

Pass `from` when you create a Sandbox:

<CodeGroup>
```typescript {{ title: "TypeScript" }}
import { image } from "inngest";

const sandbox = await inngest.sandboxes.create({
  name: "agent-1",
  vcpu: 2,
  memoryMb: 2048,
  from: image.inngest("base"),
});
```

<SdkUnsupported title="Python" feature="Sandboxes" />
<SdkUnsupported title="Go" feature="Sandboxes" />
</CodeGroup>

- `image.inngest(name)` is an image Inngest maintains: `base`, the default, or one of the [runtime images](#runtime-images). Omit `from` to use `base`.
- `image.custom(ref)` is an image published to your workspace: `"my-image"`, `"my-image:v1"`, or `"my-image@sha256:<hex>"`.

<CodeGroup>
```typescript {{ title: "TypeScript" }}
const sandbox = await inngest.sandboxes.create({
  name: "agent-2",
  vcpu: 2,
  memoryMb: 2048,
  from: image.custom("my-image:v1"),
});

console.log(sandbox.imageDigest);
```

<SdkUnsupported title="Python" feature="Sandboxes" />
<SdkUnsupported title="Go" feature="Sandboxes" />
</CodeGroup>

The image is resolved once, when the Sandbox is created. Creating the same Sandbox name again returns the original Sandbox and image, even if a tag has moved. Use a new Sandbox name to pick up an updated tag.

`imageDigest` (for example `sha256:...`) says exactly which image the Sandbox started from.

### Runtime images

Each runtime image is the base image plus one language runtime at a pinned version. The runners pick one for you with `runtime`, and `from` names it directly.

| `runtime` | `from` | Adds |
| --- | --- | --- |
| `"node@20"` | `image.inngest("node-20")` | Node.js 20 |
| `"node@22"` | `image.inngest("node-22")` | Node.js 22, which runs TypeScript directly |
| `"node@24"` | `image.inngest("node-24")` | Node.js 24 |
| `"python@3.11"`, `"python@3.12"`, `"python@3.13"` | `image.inngest("python-3.12")`, and so on | Python at that version |
| `"deno"` | `image.inngest("deno")` | Deno |
| `"bun"` | `image.inngest("bun")` | Bun |

```typescript {{ title: "TypeScript" }}
await step.sandbox.python("ml", code, { runtime: "python@3.12" });
await step.sandbox.ts("edge", code, { from: image.inngest("deno") });
```

Nothing installs at run time, so the version is exact and starts fast. [Run code](/docs/sandboxes/features/run-code?ref=docs-sandboxes-base-images#choose-a-runtime) shows the runners. Inngest CI jobs can start from the same images: [Base images](/docs/labs/ci/base-images?ref=docs-sandboxes-base-images).

### Image or snapshot?

| | Image | [Snapshot](/docs/sandboxes/features/snapshots-and-restore?ref=docs-sandboxes-base-images) |
| --- | --- | --- |
| Starts | Fresh, from a filesystem | Where the source left off: memory, processes, and files |
| Size, environment, secrets | Yours to set | The source's |
| Lasts | Until you delete it | Until it expires, or until the [run that owns it](/docs/sandboxes/features/run-owned?ref=docs-sandboxes-base-images) ends |
| Use it for | A base you reuse across many runs | Fanning out from one prepared machine, or keeping a running process like an open browser |

A common pattern uses both: build an image with your toolchain, start a Sandbox from it, get it ready, then snapshot it and clone that for each task.

## Inspect the image

Run commands after the Sandbox reaches `RUNNING`. This example assumes you already have a Sandbox object from `inngest.sandboxes.create()`:

<CodeGroup>
```typescript {{ title: "TypeScript" }}
const result = await sandbox.commands.run(
  "node --version && python3 --version && ruby --version && git --version",
  { timeout: "30s" },
);

console.log(result.stdout);
console.error(result.stderr);
console.log(result.exitCode);
```

<SdkUnsupported title="Go" feature="Sandboxes" />
</CodeGroup>

Inside an Inngest function, use the same command through `step.sandbox` and give the operation a stable step ID:

<CodeGroup>
```typescript {{ title: "TypeScript" }}
const result = await sandbox.commands.run(
  "inspect-image",
  "node --version && python3 --version && ruby --version && git --version",
  { timeout: "30s" },
);
```

Through `step.sandbox`, a non-zero exit code fails the step. See [Exit codes and errors](/docs/sandboxes/features/exit-codes?ref=docs-sandboxes-base-images).

## Add dependencies for a task

Install packages inside a running Sandbox when the task needs them. For example, create a project directory and install a Node package:

<CodeGroup>
```typescript {{ title: "TypeScript" }}
await sandbox.commands.run(
  "mkdir -p /tmp/project && cd /tmp/project && npm init -y && npm install lodash",
  { timeout: "5m" },
);
```

<SdkUnsupported title="Python" feature="Sandboxes" />
<SdkUnsupported title="Go" feature="Sandboxes" />
</CodeGroup>

This changes **that Sandbox**, not the fixed base image. The files remain in the Sandbox across pause and resume. A snapshot captures its disk, so clones start with the installed files. Destroying the Sandbox removes its filesystem. User snapshots expire and are not permanent storage. For files shared across different Sandboxes, use S3-backed persistent filesystem mounts.

## Choose a supported size

Fresh Sandboxes accept these exact resource pairs:

| `vcpu` | `memoryMb` |
| --- | --- |
| 1 | 1024 |
| 2 | 2048 |
| 4 | 4096 |

Set both values from the same row. The API does not accept a size profile name. A snapshot clone inherits the snapshot's CPU and memory. Access or available capacity can still prevent a supported size from starting.
