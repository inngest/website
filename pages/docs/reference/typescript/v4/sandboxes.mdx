# TypeScript Sandbox SDK

Snapshot, clone, Pause, and Resume require Inngest SDK 4.20 or newer. Sandbox
secret selection requires Inngest SDK 4.21 or newer. Named snapshots require
SDK 4.23 or newer. The image-selection, durable file, scoped cleanup, and
code-runner examples below use the published SDK 4.25 API.

The TypeScript SDK exposes two clients over the same sandbox resources:

```ts
import { Inngest } from "inngest";
import { sandboxMiddleware } from "inngest/experimental";

const inngest = new Inngest({
  id: "sandbox-demo",
  middleware: [sandboxMiddleware()],
});

// Direct REST-backed client
await inngest.sandboxes.create({
  name: "direct-sandbox",
  vcpu: 1,
  memoryMb: 1024,
});

// Memoized middleware-backed step client
await step.sandbox.create("step-id", {
  name: "durable-sandbox",
  vcpu: 1,
  memoryMb: 1024,
});
```

| Operation                                     | `inngest.sandboxes` |       `step.sandbox`        |
| --------------------------------------------- | :-----------------: | :-------------------------: |
| Create, List, Get, Destroy                    |         Yes         |             Yes             |
| Pause and Resume                              |         Yes         |             Yes             |
| Snapshot Create, List, Get, Delete, and Clone |         Yes         |             Yes             |
| Captured Exec                                 |         Yes         |             Yes             |
| Start, List, Get, Signal, Wait process        |         Yes         |             Yes             |
| Retained process output                       |         Yes         |             Yes             |
| Sandbox log stream                            |         Yes         |             No              |
| Live process output stream                    |         Yes         |             No              |
| File upload and download                      |         Yes         |             No              |
| Small-file read and write                     | Via upload/download | Yes (examples use SDK 4.25) |

Live streams and Fetch `Response` bodies cannot be reconstructed from memoized
JSON step state. Durable file helpers instead serialize small files into step
data; they do not expose the direct upload/download interface.

`sandboxMiddleware()` is required only for the durable `step.sandbox` surface.
The direct `inngest.sandboxes` client works without it.

Read [Sandbox limitations](/docs/features/sandboxes/limitations) before relying
on process recovery, output retention, stream delivery, custom runtime
configuration, or idempotency.

## Sandbox resource

Create, List, and Get use one resource shape:

```ts
interface SandboxResource {
  id: string;
  name: string;
  status:
    | "PENDING"
    | "STARTING"
    | "PAUSING"
    | "RUNNING"
    | "PAUSED"
    | "RESUMING"
    | "TERMINATING"
    | "TERMINATED"
    | "FAILED";
  vpcId: string;
  imageRef: string;
  imageDigest?: string;
  resources: {
    vcpu: number;
    memoryMb: number;
  };
  createdAt: string;
  startedAt?: string;
  endedAt?: string;
  error?: string;
}
```

`id` and `vpcId` are canonical lowercase UUIDs. Timestamps are RFC 3339
strings.

SDK Create chooses the workspace's default egress-only VPC and, unless you
select an image, the default image. `vpcId` and `imageRef` describe the created
resource; they are not SDK Create options. SDK 4.25 adds `from` and `image`
for selecting an already-published image. `imageDigest`, when present, is the
pinned launch artifact, in `sha256:<hex>` form.

Sandbox objects are immutable views of the state observed by a request:

```ts
const sandbox = await inngest.sandboxes.get(sandboxId);

if (sandbox) {
  console.log(Object.isFrozen(sandbox)); // true
  console.log(Object.isFrozen(sandbox.resources)); // true
}
```

Each Get returns a new object. It never mutates an earlier result.

## Snapshot resource

```ts
interface SandboxSnapshotResource {
  id: string;
  name?: string;
  sourceImageId: string;
  status: "CREATING" | "READY" | "DELETING" | "DELETED" | "FAILED" | "LOST";
  compatibilityId?: string;
  resources: {
    vcpu: number;
    memoryMb: number;
  };
  memoryPackCount: number;
  diskPackCount: number;
  storedBytes: number;
  createdAt: string;
  updatedAt: string;
  expiresAt: string;
  error?: string;
}
```

`READY` snapshots include `compatibilityId` and an immutable image digest in
`sourceImageId`. `error` can be present on a failed snapshot. Every snapshot
has a server-defined expiration time.

## Process resource

```ts
interface SandboxProcessResource {
  id: string;
  command: readonly string[];
  pid?: number;
  state: "STARTING" | "RUNNING" | "EXITED" | "KILLED" | "FAILED" | "LOST";
  exitCode?: number;
  terminationSignal?: number;
  startedAt?: string;
  endedAt?: string;
}
```

The public process ID is a UUID, not an internal `p1` or `p2` guest handle.
`pid` is visible to commands inside the sandbox. `exitCode` is present only
for `EXITED`; `terminationSignal` is present only for `KILLED`.

## Reconnecting by ID

Store the sandbox ID when work needs to reconnect later:

```ts
const sandboxId = sandbox.id;
const current = await inngest.sandboxes.get(sandboxId);
```

Inside an Inngest function, use the durable Get operation:

```ts
const current = await step.sandbox.get("get-sandbox", sandboxId);
```

Get returns current state and confirms that the sandbox still exists in the
active workspace. Reload a process through its sandbox:

```ts
const process = await current?.processes.get(processId);
```

## Direct client: `inngest.sandboxes`

The direct client:

- uses the Inngest client's base URL, signing key, environment headers, and
  Fetch implementation;
- requires a signing key;
- executes each call immediately;
- never retries automatically or reconnects a stream; and
- returns `SandboxError` for API and transport failures.

Keep it in trusted server-side code.

### `create(options)`

```ts
const sandbox = await inngest.sandboxes.create({
  name: "agent_job-42",
  vcpu: 1,
  memoryMb: 1024,
  environment: {
    APP_ENV: "beta",
  },
  secrets: ["OPENAI_API_KEY"],
});
```

| Option           | Required | Meaning                                                                         |
| ---------------- | :------: | ------------------------------------------------------------------------------- |
| `name`           |   Yes    | 1–255 Unicode characters; no control characters or surrounding whitespace       |
| `vcpu`           |   Yes    | Virtual CPU count from a supported resource configuration                       |
| `memoryMb`       |   Yes    | Memory in MiB from the same supported configuration                             |
| `environment`    |    No    | Literal values inherited by commands and processes                              |
| `secrets`        |    No    | Exact workspace secret names injected under the same environment variable names |
| `from`           |    No    | SDK 4.25+: image made with `image.inngest()` or `image.custom()`                |
| `image`          |    No    | SDK 4.25+: published reference string; alternative to `from`                    |
| `runningTimeout` |    No    | Wait bound; defaults to `"120s"`; `false` returns immediately                   |

New sandboxes currently support these exact pairs:

| `vcpu` |          `memoryMb` |
| -----: | ------------------: |
|      1 |    1024, 2048, 4096 |
|      2 |    2048, 4096, 8192 |
|      4 |   4096, 8192, 16384 |
|      8 |  8192, 16384, 32768 |
|     16 | 16384, 32768, 65536 |

The SDK does not accept a profile name. Choose one memory value from the
CPU's row. The SDK validates positive integers; the API additionally rejects
unsupported pairs with `400 invalid_field_format`. Valid sizes remain subject
to capacity and account limits. Clones inherit the snapshot's resource
configuration.

Names are case-sensitive. An active name must be unique in the workspace.
Creating the same active name with the same fresh-Create intent returns the
existing sandbox. Secret selection is compared by resolved identity and is
order-independent. A conflicting request throws `sandbox_name_taken`.

Create waits for `RUNNING` for up to 120 seconds by default. It does not
redispatch Create while waiting. Set an explicit duration up to five minutes,
or opt out:

```ts
const accepted = await inngest.sandboxes.create({
  ...options,
  runningTimeout: false,
});
```

With `false`, the returned object can be `STARTING` or `RUNNING`. Call
`accepted.waitUntilRunning({ timeout: "30s" })` to wait later without repeating
Create.

#### Select a published image

In SDK 4.25 or newer, use the image helpers from `inngest/experimental`:

```ts
import { image } from "inngest/experimental";

const sandbox = await inngest.sandboxes.create({
  name: `job-${crypto.randomUUID()}`,
  vcpu: 2,
  memoryMb: 4096,
  from: image.inngest("base"),
});
```

Use `image.custom("my-image:v1")` only for an image already published and
accessible to your workspace. The helpers select an image; they do not build,
upload, or pull an arbitrary image from a container registry. Follow
[Custom images](/docs/features/sandboxes/custom-images) for the Docker
build, archive upload, and publication flow.

Alternatively, `image: "inngest/base:latest"` accepts a published reference
string. Supply either `from` or `image`, never both. Accepted references are
`name`, `name:tag`, `name@sha256:<hex>`, or `sha256:<hex>`, with 64 lowercase
hex characters in a digest. A name without a tag uses `latest`. Omit both
options for the default image; do not pass `image: "default"` or an empty
string. Snapshot clones cannot override the image.

Create resolves the image once for a new sandbox. Retrying the same active
name and configuration returns its original artifact even if the tag moved.
Use a new sandbox name to pick up a moved tag, or a digest to pin an artifact.
Selection still depends on image access and compatible runtime capacity.

#### Launch secrets

`secrets` is an array of exact, case-sensitive names from the authenticated
workspace. The SDK sends only those names. Each resolved value becomes a
sandbox-level environment variable under the same name and is inherited by
commands and managed processes.

Names must be unique, must be valid environment keys, and cannot overlap keys
in `environment`. Literal environment keys and selected secret names share the
256-entry and 64 KiB resolved environment limits. The SDK validates the
selection before dispatch.

Secret selection is available only for a fresh Create. A
`SandboxCreateFromSnapshotOptions` request cannot include `environment` or
`secrets`; the clone restores the values captured by its snapshot.

Read [Secrets](/docs/features/sandboxes/secrets) for rotation, delivery,
snapshot, and redaction behavior.

### `list(options?)`

```ts
let cursor: string | undefined;

do {
  const result = await inngest.sandboxes.list({
    cursor,
    limit: 100,
  });

  for (const sandbox of result.items) {
    console.log(sandbox.id, sandbox.status);
  }

  cursor = result.page.cursor;
} while (cursor);
```

| Option   | Default | Limits                                          |
| -------- | ------: | ----------------------------------------------- |
| `cursor` |    None | Use only a cursor returned by the previous page |
| `limit`  |      50 | 1–250                                           |

```ts
interface SandboxListResult<TSandbox> {
  items: TSandbox[];
  page: {
    cursor?: string;
    hasMore: boolean;
    limit: number;
  };
  fetchedAt: string;
}
```

Sandbox List orders by creation time descending, then ID descending. It
includes active and retained terminal resources. Cursors are opaque.

### `get(sandboxId)`

```ts
const sandbox = await inngest.sandboxes.get(sandboxId);
```

Returns a `Sandbox` or `null` when the resource is missing or hidden by
workspace scope. Other errors are thrown.

`sandboxId` must be a canonical lowercase, non-nil UUID.

### `sandbox.destroy()`

```ts
const result = await sandbox.destroy();
```

```ts
type SandboxDestroyResult =
  | {
      status: "TERMINATING";
      sandbox: SandboxRef;
    }
  | {
      status: "TERMINATED";
      sandbox: null;
    };
```

`TERMINATING` means the destroy intent was accepted and teardown continues.
`TERMINATED` means teardown completed synchronously. A missing sandbox throws
`sandbox_not_found`.

### `sandbox.pause(options?)` and `sandbox.resume(options?)`

```ts
const paused = await sandbox.pause({ timeout: "5m" });
const running = await paused.resume({ timeout: "5m" });
```

Both methods dispatch the lifecycle operation once, poll Get, and return a new
Sandbox object only after reaching `PAUSED` or `RUNNING`. The timeout defaults
to five minutes and cannot exceed five minutes.

Direct calls can use `signal?: AbortSignal`. Aborting stops local waiting; it
does not prove the remote transition was cancelled. Get the sandbox by ID to
reconcile current state.

Pause and Resume preserve the same sandbox ID and network identity. Time spent
paused does not consume its remaining runtime. See
[Pause and resume](/docs/features/sandboxes/pause-and-resume).

### Snapshots

Create a crash-consistent snapshot of a `RUNNING` sandbox:

```ts
const snapshot = await sandbox.snapshot({}, { timeout: "5m" });
```

The first argument accepts an optional `name` in SDK 4.23 or newer:

```ts
const snapshot = await sandbox.snapshot({ name: "prepared-runtime" });
const page = await inngest.sandboxes.snapshots.list({
  name: "prepared-runtime",
});
```

Snapshot names use the sandbox name rules. A `CREATING` or unexpired `READY`
snapshot holds its name in the workspace. A repeated Create with that name
throws `sandbox_snapshot_name_taken`; it is not an idempotent lookup. List by
exact name to reconcile, and use the UUID for Get, Clone, and Delete.

The second argument
accepts `timeout?: SandboxDuration` and `signal?: AbortSignal`. The timeout
defaults to five minutes and begins after Create returns. Create is dispatched
once, then the SDK polls Get from the current invocation until the snapshot
reaches `READY`. A timeout stops observation but does not cancel snapshot
creation or its background upload.

Clone a ready snapshot into a new sandbox:

```ts
const clone = await snapshot.clone({
  name: `prepared-${crypto.randomUUID()}`,
  runningTimeout: "2m",
});
```

Snapshot creation and clone startup use separate waits. After the snapshot is
`READY`, the clone gets a new sandbox UUID and restores the captured memory,
disk, environment, image, and resources. A clone returned as `RUNNING` resolves
immediately. If Create returns `STARTING`, the SDK waits up to `runningTimeout`,
which defaults to 120 seconds and can be at most five minutes.

List and Get are exposed on the top-level collection:

```ts
const page = await inngest.sandboxes.snapshots.list({
  cursor,
  limit: 50,
});

const current = await inngest.sandboxes.snapshots.get(snapshotId);
```

They use the same cursor and page shapes as Sandbox List. Get returns `null`
for a missing or workspace-hidden snapshot.

Delete is permanent:

```ts
await snapshot.delete();
```

See [Sandbox snapshots](/docs/features/sandboxes/snapshots) for consistency,
retention, and ambiguity behavior.

### `sandbox.commands.run(command, options?)`

```ts
import type { SandboxCommand } from "inngest/experimental";

const command: SandboxCommand = "npm test";
```

`SandboxCommand` is `string | readonly string[]`.

```ts
const result = await sandbox.commands.run("printf 'tests passed\n'", {
  environment: {
    CI: "true",
  },
  cwd: "/",
  timeout: "5m",
});
```

| Argument or option |    Default | Meaning                                       |
| ------------------ | ---------: | --------------------------------------------- |
| `command`          |   Required | Shell string or direct argv array             |
| `environment`      |  Inherited | Overrides matching sandbox environment values |
| `cwd`              |        `/` | Working directory inside the sandbox          |
| `timeout`          | 30 seconds | Positive duration, at most five minutes       |

A string is passed unchanged as `["/bin/sh", "-c", command]`. The shell owns
quoting, variables, pipes, redirects, and chaining. An argv array bypasses the
shell:

```ts
await sandbox.commands.run(["git", "commit", "-m", "hello world"]);
```

Bare executable names use the effective `PATH`. Paths containing `/` are used
directly and can be absolute or relative to `cwd`.

Guest defaults are retained. Sandbox Create values override those defaults,
and command values override matching sandbox values. These values are visible
inside the guest. Put ordinary configuration in `environment`; select
credentials through Create's `secrets` option. Command values can override an
inherited secret for that command. Output is not automatically redacted.

Numeric durations are milliseconds. Strings accept forms such as `"500ms"`,
`"30s"`, and `"5m"`. `Temporal.Duration` is also supported, except calendar
years, months, and weeks.

```ts
type SandboxCommandOutputMetadata =
  | {
      truncated: false;
    }
  | {
      truncated: true;
      strategy: "tail";
      originalBytes: {
        stdout: number;
        stderr: number;
      };
      retainedBytes: {
        stdout: number;
        stderr: number;
      };
    };

interface SandboxCommandResult {
  stdout: string;
  stderr: string;
  exitCode: number;
  output: SandboxCommandOutputMetadata;
}
```

The direct client accepts up to 4 MiB across stdout and stderr and reports
`output: { truncated: false }`. A non-zero exit code is a successful result,
not an exception. Invalid or truncated UTF-8 sequences in captured output are
represented by the Unicode replacement character.

### `sandbox.logs.stream(options?)`

```ts
const stream = await sandbox.logs.stream({ follow: true });
const reader = stream.getReader();

for (;;) {
  const { done, value } = await reader.read();
  if (done) break;

  console.log(value.stream, new TextDecoder().decode(value.data));
}
```

`follow` defaults to `false`.

```ts
interface SandboxOutputChunk {
  stream: "STDOUT" | "STDERR";
  data: Uint8Array;
  at?: string;
}
```

The SDK decodes base64 NDJSON frames. A terminal `errors[]` frame makes the
stream throw `SandboxError`. Cancelling the `ReadableStream` aborts the HTTP
request. The SDK never reconnects automatically.

### `sandbox.files.upload(options)`

```ts
const uploaded = await sandbox.files.upload({
  path: "/tmp/input.bin",
  data: new Uint8Array([0x00, 0xff]),
  mode: 0o640,
});
```

| Option |  Default | Meaning                                      |
| ------ | -------: | -------------------------------------------- |
| `path` | Required | Absolute path inside the sandbox             |
| `data` | Required | Fetch-compatible `BodyInit`                  |
| `mode` |  `0o644` | Permission bits from `0o001` through `0o777` |

Uploads are limited to 100 MiB. A successful upload atomically replaces a
regular file. It cannot replace `/`, a directory, symlink, device, socket, or
FIFO.

Repeating an upload with the same path, bytes, and mode is safe. Each successful
upload atomically replaces the complete destination.

### `sandbox.files.download(options)`

```ts
const response = await sandbox.files.download({
  path: "/tmp/output.bin",
});

const bytes = new Uint8Array(await response.arrayBuffer());
const mode = response.headers.get("X-Sandbox-File-Mode");
const modifiedAt = response.headers.get("Last-Modified");
```

Returns the raw Fetch `Response`. Successful responses contain
`Content-Type`, `Content-Length`, `X-Sandbox-File-Mode`, and, when available,
`Last-Modified`.

Only regular files up to 100 MiB are downloadable.

### `sandbox.processes.start(options)`

```ts
const process = await sandbox.processes.start({
  command: "while :; do sleep 1; done",
  environment: {
    PORT: "8080",
  },
  cwd: "/",
});
```

Uses the same command, environment, and working-directory rules as captured
Exec, but has no runtime timeout. Returns a `RUNNING` process with UUID and PID.

### `sandbox.processes.list(options?)`

```ts
const page = await sandbox.processes.list({
  cursor,
  limit: 50,
});
```

`SandboxProcessListOptions` and `SandboxProcessListResult` use the same
`cursor`, `limit`, `items`, `page`, and `fetchedAt` shapes as Sandbox List.

Pages are ordered by process UUID and include terminal processes while their
metadata remains. Internal guest handles are excluded.

### `sandbox.processes.get(processId)`

```ts
const process = await sandbox.processes.get(processId);
```

Returns a process snapshot or `null`.

### Process methods

```ts
const current = await sandbox.processes.get(process.id);

await process.signal({
  signal: 15,
  includeChildren: false,
});

const terminal = await process.wait({ timeout: "1m" });
const output = await process.getOutput({ tailBytes: 64 * 1024 });
const stream = await process.streamOutput({ tailBytes: 8 * 1024 });
```

See [Managed processes](/docs/features/sandboxes/managed-processes) for state,
signal, Wait, retention, and streaming semantics.

The SDK defaults `includeChildren` to `true`; pass it explicitly when signal
delivery semantics matter. The REST API defaults the same field to `false`.

## Step client: `step.sandbox`

Each operation that communicates with the API adds a stable step ID as its
first argument:

```ts
const sandbox = await step.sandbox.create("create-sandbox", {
  name: "agent_job-42",
  vcpu: 1,
  memoryMb: 1024,
  secrets: ["OPENAI_API_KEY"],
});

const page = await step.sandbox.list("list-sandboxes", { limit: 50 });
const loaded = await step.sandbox.get("get-sandbox", sandbox.id);

const paused = await sandbox.pause("pause-sandbox", { timeout: "5m" });
const resumed = await paused.resume("resume-sandbox", { timeout: "5m" });

const snapshot = await resumed.snapshot(
  "create-snapshot",
  {},
  { timeout: "5m" }
);
const snapshotPage = await step.sandbox.snapshots.list("list-snapshots", {
  limit: 50,
});
const loadedSnapshot = await step.sandbox.snapshots.get(
  "get-snapshot",
  snapshot.id
);
const clone = await snapshot.clone("clone-snapshot", {
  name: `prepared-${crypto.randomUUID()}`,
});

const result = await sandbox.commands.run("run-command", ["true"]);

const process = await sandbox.processes.start("start-process", {
  command: "while :; do sleep 1; done",
  cwd: "/",
});

const processPage = await sandbox.processes.list("list-processes", {
  limit: 50,
});
const loadedProcess = await sandbox.processes.get("get-process", process.id);

await process.signal("stop-process", {
  signal: 15,
  includeChildren: false,
});

const terminal = await process.wait("wait-process", {
  timeout: "1m",
});

const output = await process.getOutput("get-output", {
  tailBytes: 64 * 1024,
});

await sandbox.destroy("destroy-sandbox");
```

Complete signatures:

```text
step.sandbox.create(step, options)
step.sandbox.list(step, options?)
step.sandbox.get(step, sandboxId)
step.sandbox.snapshots.list(step, options?)
step.sandbox.snapshots.get(step, snapshotId)

sandbox.destroy(step)
sandbox.pause(step, options?)
sandbox.resume(step, options?)
sandbox.snapshot(step, options?, waitOptions?)
sandbox.snapshots.create(step, options?, waitOptions?)
sandbox.commands.run(step, command, options?)
sandbox.files.write(step, { path, data })
sandbox.files.read(step, path)
sandbox.processes.start(step, options)
sandbox.processes.list(step, options?)
sandbox.processes.get(step, processId)

process.signal(step, options)
process.wait(step, options?)
process.getOutput(step, options?)

snapshot.waitUntilReady(step, options)
snapshot.clone(step, options, waitOptions?)
snapshot.delete(step)
```

`step` is a string ID or `{ id, name? }`.

### Durable files

In SDK 4.25, write UTF-8 text or a `Uint8Array` and read bytes through
memoized steps:

```ts
await sandbox.files.write("write-input", {
  path: "/tmp/input.txt",
  data: "hello from a step\n",
});

const bytes = await sandbox.files.read("read-result", "/tmp/result.txt");
const text = new TextDecoder().decode(bytes);
```

These are not aliases for the direct streaming APIs. `write()` returns no
value; `read()` returns a `Uint8Array`. Paths and regular-file restrictions
are the same as direct transfers. Read rejects files larger than 2 MiB, and
both helpers must fit within Inngest step payload limits after serialization.
Keep files comfortably below those limits; use direct transfers for larger
files. A replayed Read returns its memoized bytes rather than reading a
possibly changed file again.

### Scoped cleanup

SDK 4.24 or newer supports explicit resource management for sandbox creation:

```ts
await using sandbox = await step.sandbox.create("create-sandbox", {
  name: `job-${event.data.jobId}`,
  vcpu: 1,
  memoryMb: 1024,
});

await sandbox.commands.run("run-job", "printf 'done\n'");
```

When the scope ends, disposal attempts Destroy in a memoized
`create-sandbox:destroy` step. Reserve that ID rather than using it for another
operation. Disposal runs on errors too, including before a function retry;
use explicit lifecycle steps when later attempts must keep using the sandbox.
Your TypeScript and runtime must support `await using`.

### Run a code snippet

In SDK 4.25 or newer, `step.sandbox.python()` and
`step.sandbox.typescript()` create a sandbox, run a snippet, and clean it up:

```ts
const result = await step.sandbox.python<{ total: number }>(
  "sum-values",
  "return {'total': sum(values)}",
  { input: { values: [2, 5, 9] } }
);
```

Each `input` key is available as a global in the snippet. Use a top-level
`return` for a JSON-compatible result. `schema.output` accepts a Standard
Schema validator when you need runtime result validation; a TypeScript type
argument alone does not validate the result. Options also accept command
settings such as `cwd` and `timeout`, and optional fresh-sandbox settings
such as `vcpu`, `memoryMb`, `environment`, and `secrets`.

The TypeScript runner requires Node.js 22.13 or newer in the selected image.
A non-zero snippet exit fails the step; it is not a successful command result
with a non-zero `exitCode`.

### Call application tools from sandbox code

SDK 4.25 adds experimental `tools` to durable `commands.run()` and the Python
and TypeScript runners. Tools run in your application, not in the sandbox.
Expose only operations that sandbox code should be allowed to invoke:

```ts
const result = await step.sandbox.python(
  "format-label",
  "return await tools.label('report')",
  { tools: { label: (name: string) => `Ready: ${name}` } }
);
```

Each tool call is a durable step with normal retries and memoization. Plain
functions take positional JSON arguments. For validated named arguments, use
`tool.step({ input, output, run })` from `inngest/experimental` with Standard
Schema validators. Its context includes an `idempotencyKey` stable across
retries; pass it to external APIs that support deduplicating writes.

`tool.group()` lets the tool body run multiple Inngest steps. An Inngest
function or function reference can also be a tool: named arguments become
its event data, and its result is returned to the caller.

Runners expose `tools` automatically. For a script run through
`commands.run()`, Python imports `tools` from `inngest_tools`; Node uses
`const { tools } = require("inngest_tools")`. A failed tool raises a
`ToolError` in sandbox code after its step retries are exhausted.

`toolOptions` defaults to 100 calls per command, a 30-second tool timeout,
and a 20-second wait window. The wait window is an observation interval, not
the command lifetime. A command with tools defaults to five minutes when
`timeout` is omitted. The direct client does not expose this durable tool
bridge.

### Replay and retries

The opt-in Sandbox middleware follows standard `step.run` retry and
memoization semantics.

- Retriable `SandboxError` becomes an ordinary retriable step error.
- Non-retryable `SandboxError` becomes `NonRetriableError`.
- `SandboxValidationError` becomes `NonRetriableError`.

On replay, a completed step reconstructs the Sandbox object from its memoized
result. An observed `operation_ambiguous` is non-retriable. As with an external
mutation inside `step.run`, a process crash after an unsafe operation succeeds
but before its result is persisted can allow that operation to run again.

Snapshot Create and its readiness wait use separate memoized steps, so replaying
or retrying readiness observation does not create another snapshot. The
readiness step polls while the current SDK invocation remains active; it is not
an executor-owned sleep or notification. Pause and Resume are safe-to-repeat
lifecycle transitions and do not redispatch after a completed step is replayed.

### Durable captured-output limit

`step.sandbox` retains at most 2 MiB across stdout and stderr before returning
from `step.run`. It reserves half for each stream, gives unused capacity to the
other stream, and keeps each tail.

Larger successful commands do not throw. Inspect `result.output`:

```ts
if (result.output.truncated) {
  console.warn({
    strategy: result.output.strategy,
    original: result.output.originalBytes,
    retained: result.output.retainedBytes,
  });
}
```

### Excluded methods

`step.sandbox` deliberately does not expose:

```ts
sandbox.logs;
sandbox.files.upload();
sandbox.files.download();
process.streamOutput();
```

Use `inngest.sandboxes` for live streams and Fetch file bodies. Use the durable
`files.write()` and `files.read()` helpers only for small serialized files.

## Decode streamed output

Captured command output is already decoded as UTF-8:

```ts
console.log(result.stdout);
```

Log and managed-process output remains byte-safe `Uint8Array`. For streaming
UTF-8, reuse a decoder so split multi-byte characters are handled correctly.
Use one decoder per stream when stdout and stderr are decoded separately.

## Handle errors

Inside an Inngest function, do not catch `step.sandbox` errors merely to log
or retry them. Let them escape. The middleware turns retryable sandbox errors
into retriable step errors and non-retryable failures into
`NonRetriableError`.

Catch a failed step only when you intend to recover with a fallback,
compensate for earlier work, or deliberately mark the error as handled.

The direct `inngest.sandboxes` client does not receive Inngest's automatic
retries. It throws `SandboxError` for API and transport failures and
`SandboxValidationError` for invalid local input or malformed responses. If
you catch either error outside an Inngest function, make sure your code owns
the resulting retry or reconciliation policy.

`SandboxError.action` always identifies the attempted operation.
`operation_ambiguous` means an unsafe-to-repeat operation may have completed
without a confirmed result; it is not a sandbox or process state. Use `action`
to follow the operation-specific recovery guidance in the error guide. Create,
Destroy, Pause, Resume, snapshot Delete, and identical file uploads use
retryable availability errors instead. Snapshot Create can be ambiguous;
reconcile snapshot List before creating another.

Read [Sandbox errors and retries](/docs/features/sandboxes/errors-and-retries)
before implementing retry logic.
