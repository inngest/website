# Sandbox limitations

These are current product and implementation boundaries to design around.

## Availability and configuration

- The public Sandbox REST API is cloud-only.
- Sandbox access is entitlement-gated.
- Create uses the workspace's default egress-only VPC.
- Create uses the default image unless you select a published image through
  REST or SDK 4.25 or newer. See [Custom images](/docs/features/sandboxes/custom-images)
  to build and upload your own image.
- Users cannot select a VPC, template, profile, or disk size for a new sandbox.
  A clone inherits these details from its snapshot.
- New sandboxes accept 1, 2, 4, 8, or 16 vCPUs with 1024, 2048, or 4096 MiB
  per vCPU. Unsupported combinations return `400 invalid_field_format`, not
  a retryable capacity error. See the [size table](/docs/features/sandboxes#supported-sandbox-sizes).
- Supported configurations can still be rejected by capacity or account
  entitlements.

## Sandbox lifecycle

- The REST API can return `STARTING`. SDK Create waits up to 120 seconds for
  `RUNNING` by default; set `runningTimeout: false` to return immediately.
- There is no dedicated readiness endpoint. The SDK's `runningTimeout` option
  and `waitUntilRunning()` helper poll Get with a bounded timeout.
- Pause and Resume are exposed through REST and Inngest SDK 4.20 or newer. SDK
  calls wait up to five minutes for the stable state by default.
- Pause uses a private cold checkpoint. It preserves sandbox identity and
  filesystem state, but runtime operations are unavailable until Resume
  reaches `RUNNING`.
- There is no resize operation.
- There is no user-configurable sandbox TTL.
- Concurrency is account-scoped and entitlement-dependent, not a universal
  published number. Create and Resume can return
  `429 sandbox_concurrency_limit_exceeded`. Paused sandboxes release their
  runtime slot; resuming needs capacity again.
- Paused checkpoints expire after a server-defined retention period,
  currently 24 hours by default. Expired sandboxes cannot resume.
- Destroy is asynchronous when it returns `TERMINATING`.
- Files, processes, and process output disappear when the sandbox is
  destroyed.

## Captured commands

- Captured Exec has a maximum observation timeout of five minutes.
- It buffers stdout and stderr instead of streaming them.
- Direct captured Exec accepts 4 MiB of combined raw output.
- `step.sandbox` retains at most 2 MiB and tail-truncates larger successful
  results.
- REST timeout and output-limit failures do not prove that the command did not
  execute.
- There is no stdin, PTY, interactive terminal, or interactive Exec API.
- The REST API accepts argument vectors. The SDK also accepts command strings
  and runs them as `["/bin/sh", "-c", command]`.
- Bare executables are resolved with the effective guest `PATH`. Paths that
  contain `/` are used as supplied and can be relative to `cwd`.
- Command environment variables override the sandbox environment, which
  overrides guest defaults. Put ordinary configuration in `environment` and
  use Create's `secrets` selection for credentials.

## Secrets

- A fresh Create can select existing workspace secrets by exact name. The
  public Sandbox REST API and SDK do not manage secret values.
- Snapshot clones cannot select new secrets. They restore values already
  captured in the snapshot.
- Any code running in the sandbox can read selected values.
- Command output, process output, logs, files, and snapshots are not
  automatically scrubbed for secret values.
- Rotation affects a future authorized fetch; it cannot revoke a value already
  delivered to a running or paused guest.
- Pause and Resume do not refetch secrets.
- Secret delivery permits one workload-scoped fetch attempt. A failed or lost
  fetch response can leave that sandbox unable to launch.

## Managed processes

- Processes are live runtime resources, not durable records.
- Process metadata is held in memory.
- There is no restart reconciliation or automatic process recovery.
- There is no process runtime timeout.
- There is no process delete endpoint.
- Terminal metadata remains while the sandbox runtime retains it.
- There is no built-in port readiness, HTTP health, or log-pattern wait.
- Direct Start has no persisted HTTP idempotency key.
- An ambiguous Start can leave a running process whose UUID the caller did not
  receive.
- `operation_ambiguous` is an operation-outcome error, not a process state. List
  processes and reconcile by command and start time before considering another
  Start.
- Signals are numeric Unix signals rather than portable names.
- `includeChildren` is currently reliable only with `SIGKILL`; using it with
  another signal can leave the process state `LOST`.

## Process output

- Each process retains approximately 512 KiB across stdout and stderr.
- Only the newest 32 process output rings are retained.
- Starting more processes can evict output while process metadata remains.
- Output is memory-only and not durable.
- Chunks are arbitrary byte segments, not lines.
- `tailBytes` preserves whole chunks and is approximate at a chunk boundary.
- A slow live subscriber can miss chunks.
- Streams have no sequence number, resume token, or dropped-chunk marker.
- The SDK never reconnects automatically.
- Manual reconnection can replay retained chunks and create duplicates.
- Live output is available through `inngest.sandboxes`, not `step.sandbox`.

## Sandbox logs

- Sandbox logs are a live NDJSON stream, not durable log storage.
- Admission failures return an ordinary non-200 JSON error before HTTP 200 is
  committed.
- Live failures after HTTP 200 use terminal `errors[]` frames.
- Consumers must inspect frames; HTTP status alone is insufficient.
- Live logs are not available through `step.sandbox`.

## Files

- Upload and download support regular files only.
- Directories, symlinks, devices, sockets, and FIFOs are rejected.
- Files are limited to 100 MiB.
- Upload replaces a whole file.
- There is no append, ranged write, directory listing, delete, rename, or
  recursive transfer API.
- Download does not implement HTTP range requests.
- A binary failure after HTTP 200 appears as a short body, not a JSON terminal
  frame.
- Streaming upload and download use `inngest.sandboxes`. In SDK 4.25,
  `step.sandbox` has small-file `files.write()` and `files.read()` helpers;
  these memoize file data rather than transferring a live body. Keep files
  comfortably below the step payload limit.

## Direct SDK

- `inngest.sandboxes` is server-only because it uses a secret key.
- It requires a Fetch-compatible runtime with `ReadableStream`.
- It does not make calls durable.
- It does not automatically retry requests.
- It does not automatically reconnect streams.
- Returned Sandbox objects contain the state observed by that request and can
  become stale. Use Get to retrieve current state.
- Both the first-party client and hand-written REST clients authenticate with
  an Inngest signing key. The environment name is optional unless explicitly
  selecting another environment, such as a branch environment.

## `step.sandbox`

- Live streams and Fetch `Response` bodies are unavailable. Small-file
  read/write helpers are available in SDK 4.25.
- Every call requires a stable, unique step ID.
- Operations follow standard `step.run` retry and memoization semantics.
- Durable execution does not make a sandbox or process recoverable after
  runtime loss.
- Process output is not stored durably.

## REST API

- Sandbox List has no name, status, image, or VPC filters.
- Sandbox and process List use opaque cursors with a default of 50 and maximum
  of 250 items per page.
- There is no public `Idempotency-Key` contract for Create, Exec, Start,
  Signal, Destroy, snapshot Create, or file upload.
- JSON request bodies reject unknown fields.
- UUID path parameters use canonical lowercase UUIDs.
- Scoped 404 responses do not reveal resources in another workspace.

## Snapshots

- Snapshots are crash-consistent, not application-consistent.
- REST snapshot Create returns `202 CREATING`; artifact upload and readiness
  continue asynchronously after that response.
- `sandbox.snapshot()` always polls Get from the current SDK invocation until
  `READY` or its readiness deadline. It has no non-blocking SDK option.
- The readiness deadline defaults to five minutes and begins after Create
  returns. Timing out stops observation, not snapshot creation or upload.
- Snapshot creation, metadata, and object storage are durable, but a snapshot
  remains usable only until its server-defined `expiresAt`.
- Count and storage quotas are account-specific.
- A snapshot name is optional and workspace-scoped. A name held by a
  `CREATING` or unexpired `READY` snapshot cannot be reused. Named Create is
  not idempotent; a conflict returns `sandbox_snapshot_name_taken`.
- A clone must use a `READY` snapshot and inherits its image, resources, and
  environment. These values cannot be overridden during clone Create.
- Snapshot and clone operations are available on both SDK surfaces in Inngest
  SDK 4.20 or newer.
- Clone uses normal Create readiness behavior. It resolves immediately when the
  clone is returned as `RUNNING`; a `STARTING` clone waits up to
  `runningTimeout`, which defaults to 120 seconds.
- Snapshot Create has no idempotency key. After an uncertain response, list
  and reconcile snapshots before creating another.
- A user snapshot always clones into a new sandbox ID. It does not restore a
  sandbox in place; Pause and Resume use a separate private checkpoint for
  that lifecycle.
- Snapshots do not provide incremental checkpoints or live migration.

## Pause and resume

- Pause and Resume are cold, asynchronous lifecycle transitions rather than
  application-coordinated quiescing or live migration.
- The private pause checkpoint is hidden from snapshot List and excluded from
  user snapshot quotas.
- The sandbox keeps the same UUID and network identity, and time spent paused
  does not consume its remaining runtime.
- Pause retention is separate from runtime. Resume is rejected once the
  private checkpoint expires, even if runtime remains.
- Direct and durable SDK methods wait for `PAUSED` or `RUNNING`, with a default
  and maximum wait of five minutes.
- A timeout or local abort stops observation, not necessarily the remote
  transition. Get the sandbox by ID to reconcile it.
- A paused sandbox is not permanent archival storage. Persist durable data
  outside the sandbox.

## Planned but not currently available

- interactive Exec and PTYs
- general runtime and process recovery beyond pause/resume transition
  reconciliation
- durable process recovery
- durable output storage
- custom or user-selectable VPCs
- user-selectable templates
- user-configurable TTLs
- live data on the `step.sandbox` surface.

<Callout variant="warning">
  If your application needs durable process recovery or lossless output, persist
  application-level intent and results outside the sandbox.
</Callout>
