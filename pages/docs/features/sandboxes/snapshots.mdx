# Sandbox snapshots

Snapshots capture a running sandbox's memory and disk so you can create a new
sandbox from the same point later. They are useful for preparing a runtime
once, preserving expensive setup work, and cloning it for multiple jobs.

Snapshots are available through both `inngest.sandboxes` and `step.sandbox`
in Inngest SDK 4.20 or newer, as well as through the REST API.

## How snapshots work

A snapshot records:

- memory and disk state;
- the source image;
- vCPU and memory allocation; and
- sandbox-level environment variables.

This includes secret values that were delivered to the guest environment.
Snapshot clones do not fetch current workspace secret values and cannot select
additional secrets. Rotating or archiving a secret cannot revoke a value
already captured in a snapshot. Treat snapshots of secret-bearing sandboxes as
sensitive data and delete them when they are no longer needed. See
[Secrets](/docs/features/sandboxes/secrets).

Snapshots are crash-consistent. The platform captures the VM without asking
each application to flush its own state first. If your application buffers
important data, flush or quiesce it before creating the snapshot.

The source sandbox must be `RUNNING`. It continues running after the snapshot
is captured.

Cloning is the user-facing restore operation. A clone receives a new sandbox
UUID and name. If you need to suspend and later restore the same sandbox ID,
use [pause and resume](/docs/features/sandboxes/pause-and-resume) instead.

## Create and clone with the SDK

### Direct client

```ts
const snapshot = await sandbox.snapshot({}, { timeout: "5m" });

console.log(snapshot.status); // "READY"
console.log(snapshot.storedBytes);

const clone = await snapshot.clone({
  name: `prepared-${crypto.randomUUID()}`,
  runningTimeout: "2m",
});
```

The REST API accepts snapshot creation with `202 CREATING` while the snapshot
artifact finishes uploading in the background. `sandbox.snapshot()` dispatches
Create once, then polls Get from the current SDK invocation until the snapshot
is `READY`. Its readiness timeout begins after Create returns and defaults to
five minutes. A timeout stops waiting but does not cancel or delete the
snapshot; use snapshot List or Get to inspect its current state.

Snapshot creation and clone startup use separate waits. After the snapshot is
`READY`, `snapshot.clone()` uses normal sandbox Create behavior. A clone returned
as `RUNNING` resolves immediately. If Create returns `STARTING`, the SDK waits up
to `runningTimeout`, which defaults to 120 seconds, for the new sandbox to become
`RUNNING`.

List, reconnect to, and delete snapshots through the top-level collection:

```ts
const page = await inngest.sandboxes.snapshots.list({ limit: 50 });
const current = await inngest.sandboxes.snapshots.get(snapshot.id);

await current?.delete();
```

### In an Inngest function

Every operation takes a stable step ID:

```ts
const snapshot = await sandbox.snapshot(
  "snapshot-sandbox",
  {},
  { timeout: "5m" }
);

const clone = await snapshot.clone("clone-snapshot", {
  name: `prepared-${event.data.jobId}`,
  runningTimeout: "2m",
});

await clone.destroy("destroy-clone");
await snapshot.delete("delete-snapshot");
```

`sandbox.snapshots.create(...)` is an alias for `sandbox.snapshot(...)`.
Snapshot Create and its readiness wait are separate memoized steps, so replay
does not create another snapshot after the Create result is recorded. The
readiness step polls while the current SDK invocation remains active; it is not
an executor-owned sleep or notification.

Workspace-wide List and Get are also durable operations:

```ts
const page = await step.sandbox.snapshots.list("list-snapshots", {
  limit: 50,
});

const current = await step.sandbox.snapshots.get("get-snapshot", snapshot.id);

const ready = await current?.waitUntilReady("wait-for-snapshot", {
  timeout: "5m",
});
```

The direct client does not retry requests automatically. Durable calls use
ordinary `step.run` retry and memoization behavior.

## Name and find a snapshot

In SDK 4.23 or newer, pass an optional name when capturing state and filter
List by that exact name:

```ts
const snapshot = await sandbox.snapshot({ name: "prepared-runtime" });
const page = await inngest.sandboxes.snapshots.list({
  name: "prepared-runtime",
  limit: 50,
});
```

Inside an Inngest function, use
`sandbox.snapshot("capture-runtime", { name: "prepared-runtime" })` and
`step.sandbox.snapshots.list("find-runtime", { name: "prepared-runtime" })`.
The snapshot name is separate from the name you give a clone.

Names are case-sensitive and workspace-scoped, with the same 1–255 character
rules as sandbox names. A `CREATING` or unexpired `READY` snapshot holds its
name. Another Create with that name returns `409 sandbox_snapshot_name_taken`;
it does not return the existing snapshot. List by name to reconcile an
uncertain Create, then inspect the returned ID and status. Continue to use
the snapshot UUID for Get, Clone, and Delete.

## Use the REST API

### Before you start

All requests use your Inngest signing key. Set the environment when you need
to target a branch environment explicitly:

```sh
export INNGEST_SIGNING_KEY="signkey-..."
export INNGEST_ENV="production"
```

The examples use these headers:

```sh
--header "Authorization: Bearer $INNGEST_SIGNING_KEY" \
--header "X-Inngest-Env: $INNGEST_ENV"
```

### 1. Create a snapshot

The body can be empty, `{}`, or an object with an optional `name`:

```sh
curl --request POST \
  "https://api.inngest.com/v2/sandboxes/$SANDBOX_ID/snapshots" \
  --header "Authorization: Bearer $INNGEST_SIGNING_KEY" \
  --header "X-Inngest-Env: $INNGEST_ENV" \
  --header "Content-Type: application/json" \
  --data '{}'
```

Success returns HTTP 202 with a `CREATING` snapshot. Snapshot Create does not
currently accept an idempotency key, so do not repeat it blindly after an
uncertain response. List snapshots and reconcile first.

Keep the returned snapshot `id`.

### 2. Wait for `READY`

```sh
curl \
  "https://api.inngest.com/v2/snapshots/$SNAPSHOT_ID" \
  --header "Authorization: Bearer $INNGEST_SIGNING_KEY" \
  --header "X-Inngest-Env: $INNGEST_ENV"
```

Poll with bounded backoff until `data.status` is `READY`. Stop on `FAILED`,
`LOST`, `DELETING`, or `DELETED`. A ready snapshot includes a
`compatibilityId` and reports its stored byte count.

Snapshot states are:

```text
CREATING
READY
DELETING
DELETED
FAILED
LOST
```

### 3. Clone the snapshot

Use the ordinary Create endpoint with a new sandbox name:

```sh
curl --request POST \
  "https://api.inngest.com/v2/sandboxes" \
  --header "Authorization: Bearer $INNGEST_SIGNING_KEY" \
  --header "X-Inngest-Env: $INNGEST_ENV" \
  --header "Content-Type: application/json" \
  --data '{
    "name": "prepared-runtime-copy",
    "snapshotId": "'"$SNAPSHOT_ID"'"
  }'
```

Omit `vcpu` and `memoryMb` to inherit them; if supplied, they must match the
snapshot. The clone restores the captured environment along with memory, disk,
and the source image. A requested `environment` does not override captured
values. It gets a new sandbox UUID and follows the normal Create behavior:
HTTP 201 when already `RUNNING`, HTTP 202 while `STARTING`, or HTTP 200 when an
identical active Create is repeated.

### List snapshots

```sh
curl \
  "https://api.inngest.com/v2/snapshots?limit=50" \
  --header "Authorization: Bearer $INNGEST_SIGNING_KEY" \
  --header "X-Inngest-Env: $INNGEST_ENV"
```

The list is workspace-scoped and newest-first. `limit` defaults to 50 and is
capped at 250. When `page.hasMore` is true, pass `page.cursor` unchanged in the
next request.

### Delete a snapshot

```sh
curl --request DELETE \
  "https://api.inngest.com/v2/snapshots/$SNAPSHOT_ID" \
  --header "Authorization: Bearer $INNGEST_SIGNING_KEY" \
  --header "X-Inngest-Env: $INNGEST_ENV"
```

Success returns HTTP 204. Deletion is permanent.

## Limits and failure handling

- Every snapshot has a server-defined `expiresAt`.
- A clone requires compatible runtime capacity. Snapshots are not a portable
  export format and do not guarantee restore across arbitrary machines or
  future platform versions.
- Snapshot count and stored-byte quotas are account-specific.
- Exceeding either quota returns `403 sandbox_snapshot_limit_exceeded`.
- A missing or workspace-hidden snapshot returns
  `404 sandbox_snapshot_not_found`.
- A clone or conflicting operation on a non-ready snapshot returns
  `409 sandbox_snapshot_not_ready`.
- `409 operation_ambiguous` means the mutation may have completed. Read the
  snapshot before deciding whether to retry.
- Snapshots are not incremental checkpoints, live migration, or durable
  process supervision.

`409 operation_ambiguous` during snapshot Create means the capture may have
started, and retrying can create a second snapshot. Use
`inngest.sandboxes.snapshots.list()` or `step.sandbox.snapshots.list()` to
reconcile recent snapshots before creating another.

See the [REST API reference](/docs/reference/rest/v2/sandboxes#create-a-snapshot)
for complete resource fields and response shapes.
