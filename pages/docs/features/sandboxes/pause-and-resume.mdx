# Pause and resume sandboxes

Pause suspends a running sandbox without turning it into a reusable user
snapshot. Resume restores that private checkpoint as the same sandbox.

Use pause and resume when you need to release live compute temporarily while
preserving:

- the sandbox UUID and name;
- filesystem and memory state;
- image and resource allocation;
- VPC, MAC address, and IP address; and
- the remaining platform-defined runtime.

Time spent in `PAUSED` does not consume the sandbox's remaining runtime.

Pause preserves secret values already delivered to the guest. Resume does not
fetch current workspace secret values, so rotation or archival does not change
the value inside that sandbox. See
[Secrets](/docs/features/sandboxes/secrets#selection-and-rotation-behavior).

<Callout variant="info">
  Pause uses a private checkpoint. It is hidden from snapshot List, does not
  count against user snapshot quotas, and cannot be cloned through the public
  snapshot API.
</Callout>

## Direct client

`pause()` and `resume()` wait for their stable state and return a new immutable
Sandbox object:

```ts
const paused = await sandbox.pause({ timeout: "5m" });

console.log(paused.id === sandbox.id); // true
console.log(paused.status); // "PAUSED"

const running = await paused.resume({ timeout: "5m" });

console.log(running.id === sandbox.id); // true
console.log(running.status); // "RUNNING"
```

The timeout defaults to five minutes and cannot exceed five minutes. Direct
calls also accept an `AbortSignal`:

```ts
const controller = new AbortController();

const paused = await sandbox.pause({
  timeout: "2m",
  signal: controller.signal,
});
```

Aborting stops the local request or polling. It does not prove that the remote
lifecycle transition was cancelled. Get the sandbox by ID before deciding
what to do next.

## In an Inngest function

Pass a stable step ID to each durable operation:

```ts
const paused = await sandbox.pause("pause-sandbox", {
  timeout: "5m",
});

const running = await paused.resume("resume-sandbox", {
  timeout: "5m",
});
```

Pause and resume follow ordinary `step.run` retry and memoization behavior.
The server treats repeating the same lifecycle transition as safe: Pause can
continue an existing pause, and Resume returns or continues the existing
resume. A completed step is reconstructed on replay.

Do not use an `AbortSignal` as durable cancellation. Cancel the Inngest
function or design a separate lifecycle step instead.

## REST API

Pause a sandbox:

```text
POST /v2/sandboxes/{sandboxId}/pause
```

Resume it:

```text
POST /v2/sandboxes/{sandboxId}/resume
```

Send no request body. Both endpoints return HTTP 200 with the full sandbox
resource and `Cache-Control: no-store`.

Pause can initially return `PAUSING` and Resume can initially return
`RESUMING`. Poll `GET /v2/sandboxes/{sandboxId}` until the resource is
`PAUSED` or `RUNNING`. During a transition, Get or List can currently report
the generic transient state `STARTING`; treat it as non-running and continue
polling.

The endpoints are state-sensitive:

- Pause accepts `RUNNING`, `PAUSING`, or `PAUSED`.
- Resume accepts `PAUSED`, `RESUMING`, or `RUNNING`.
- Other states return `409 invalid_request`.
- A missing or workspace-hidden sandbox returns `404 sandbox_not_found`.
- Temporary compute or snapshot-storage failure returns
  `503 compute_unavailable`; repeating Pause or Resume is safe.

## Pause is different from a user snapshot

|                      | Pause and resume                     | User snapshot and clone                        |
| -------------------- | ------------------------------------ | ---------------------------------------------- |
| Identity             | Preserves the same sandbox UUID      | Creates a new sandbox UUID                     |
| Intended use         | Temporarily suspend one live sandbox | Reuse one captured state for new sandboxes     |
| Visibility           | Private lifecycle checkpoint         | Listed through the snapshot APIs               |
| Quota                | Excluded from user snapshot quotas   | Uses account snapshot count and storage quotas |
| Source after capture | Becomes `PAUSED`                     | Keeps running                                  |

## Limitations

- The private checkpoint has server-defined retention, currently 24 hours by
  default from the pause. This is separate from the remaining runtime budget:
  paused time does not consume runtime, but the checkpoint still expires.
  Resume before expiry. After expiry, Resume is rejected and the platform
  cleans up the sandbox and checkpoint.
- Pausing releases the sandbox's runtime concurrency slot. Resume must pass
  the account's concurrency limit again and find compatible capacity; it is
  not a capacity reservation. Inspect the current sandbox after a failed
  Resume rather than creating a replacement blindly.
- Commands, files, logs, and process operations require `RUNNING`; they are
  unavailable while the sandbox is paused or transitioning.
- Pause is a cold lifecycle transition, not an application-coordinated
  quiesce. Treat network connections and other external sessions as
  interruptible across the pause.
- A paused sandbox is still a live beta resource, not permanent archival
  storage. Keep durable data outside the sandbox.
- Restoring a checkpoint requires compatible runtime capacity. Pause and
  snapshots do not guarantee portability across arbitrary machines or future
  platform versions.
- There is no resize operation.

See [Snapshots](/docs/features/sandboxes/snapshots) for reusable clones and
[Sandbox errors and retries](/docs/features/sandboxes/errors-and-retries) for
failure handling.
