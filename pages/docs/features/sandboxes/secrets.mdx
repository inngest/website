# Secrets

Sandbox secrets let you pass credentials to a new sandbox without putting the
secret values in your source code or Create request. You select existing
workspace secrets by their exact names, and each value is exposed inside the
sandbox as an environment variable with the same name.

<Callout variant="warning">
  Secret injection is not output redaction. Any code in the sandbox can read the
  selected values, and a value printed to stdout, stderr, a log, or a file can
  be returned by the Sandbox APIs.
</Callout>

## Before you start

Create the secrets in the same Inngest workspace that will create the
sandbox. The public Sandbox REST API and JavaScript SDK currently select
existing secrets; they do not create, list, rotate, or archive secret values.

Secret names are case-sensitive. Save a secret under the environment variable
name the application expects, such as `OPENAI_API_KEY`.

## Select secrets when creating a sandbox

Pass an array of exact workspace secret names to `secrets`:

```ts
const sandbox = await inngest.sandboxes.create({
  name: `agent-${crypto.randomUUID()}`,
  vcpu: 1,
  memoryMb: 1024,
  environment: {
    APP_ENV: "beta",
  },
  secrets: ["OPENAI_API_KEY", "GITHUB_TOKEN"],
});
```

Inside an Inngest function, the middleware-backed client uses the same option:

```ts
const sandbox = await step.sandbox.create("create-sandbox", {
  name: `agent-${event.data.jobId}`,
  vcpu: 1,
  memoryMb: 1024,
  secrets: ["OPENAI_API_KEY"],
});
```

The SDK and API send only the names. They never include the secret values in
the Create request.

With REST, include the same name array:

```json
{
  "name": "agent_job-42",
  "vcpu": 1,
  "memoryMb": 1024,
  "environment": {
    "APP_ENV": "beta"
  },
  "secrets": ["OPENAI_API_KEY", "GITHUB_TOKEN"]
}
```

Secret selection is supported only when creating a fresh sandbox. A snapshot
clone restores the environment captured in the snapshot and cannot select new
secrets.

## Environment inheritance and overrides

Selected secrets become sandbox-level environment variables. Commands and
managed processes inherit them automatically:

```ts
await sandbox.commands.run([
  "node",
  "-e",
  "fetch('https://api.example.com', { headers: { Authorization: `Bearer ${process.env.API_TOKEN}` } })",
]);
```

Environment is layered in this order:

1. guest defaults;
2. sandbox `environment` values and selected secret values; and
3. command- or process-specific `environment` values.

An operation-specific value can override a selected secret for that operation.
The Create request cannot include the same key in both `environment` and
`secrets`.

## Selection and rotation behavior

Secret names resolve to stable secret identities when the sandbox is created.
This keeps repeated Create requests tied to the original selection:

- selection order does not affect Create identity;
- rotating a secret changes the value fetched by a future launch, but does not
  replace a value already delivered to a running or paused guest;
- archiving a selected secret and creating another secret with the same name
  affects new sandboxes, while an existing sandbox remains bound to the
  original secret identity; and
- pausing and resuming a sandbox does not fetch its secrets again.

If a secret cannot be resolved or delivered, sandbox launch fails. Secret
delivery uses short-lived, workload-scoped authorization and permits one fetch
attempt for that workload. The node never receives the control plane's cloud
credentials or encryption keys.

## Snapshots retain delivered values

A user snapshot captures the guest's memory, disk, and environment after
secret delivery. Secret values can therefore remain in a snapshot and in its
clones. A clone does not fetch current values and cannot select additional
secrets.

Rotating or archiving a workspace secret cannot revoke a value already
delivered to a guest or captured in a snapshot. Delete snapshots and destroy
sandboxes when they are no longer needed.

## Validation and limits

Each selected name must:

- match an active secret in the authenticated workspace;
- be unique within the request;
- be a non-empty, case-sensitive name of at most 256 UTF-8 bytes;
- have no leading or trailing Unicode whitespace;
- contain no `=`, carriage return, line feed, or NUL; and
- not overlap a key in the Create request's `environment` object.

Literal environment keys and selected secret names share the limit of 256
sandbox-level entries. After values resolve, their combined `KEY=value` data
must not exceed 64 KiB. Invalid names, duplicate names, collisions, and missing
or archived secrets reject Create with HTTP 400.

## Security checklist

- Select only the secrets needed by code in that sandbox.
- Never place secret values directly in `environment`.
- Do not print credentials or include them in returned command output.
- Treat files and snapshots created after injection as potentially sensitive.
- Use operation-specific environment overrides only when replacing a value is
  intentional.
- Destroy sandboxes and delete snapshots when their sensitive state is no
  longer required.
