A support answer can pass every code check and still fail to help the customer. Score the later resolution or feedback, link it to the run that produced the answer, and compare changes using those outcomes.

Inngest already records each durable run and its steps. Online Evals adds the context and outcome signals you need to learn from those runs, including signals that arrive after the work finishes. You can inspect the execution behind a good or bad score instead of relying only on a final output.

## From work to outcome

**Sessions → scores → deferred scoring → experiments** is the simplest way to learn the system. This is a learning path, not the order in which everything happens at runtime.

1. **Group related runs with sessions.** Use a conversation, ticket, or job ID to find all the runs involved in one user outcome. A session helps you inspect related work. It does not change which functions run.
2. **Record a score.** Attach a named number or true/false value to a run or step. Score an immediate check, such as whether an answer passed a guardrail, or a product outcome, such as whether a ticket stayed resolved. You can track outcomes without running an experiment.
3. **Defer the score when the result comes later.** A scorer can run separately while it waits for feedback, review, conversion, or another signal. Inngest attributes the returned score to the run that started the scorer. You can also score a past run from another process when you retain its run ID.
4. **Compare variants.** `group.experiment()` selects one variant for a run. Put a different step, or an entire workflow path, inside each variant callback to compare prompts, models, tools, or end-to-end strategies. The run keeps its selection on retries. Pass the experiment reference with a score so a later outcome counts toward the variant that produced it.

## One example

A support agent answers a ticket. The ticket ID groups the agent run with later feedback. The agent scores an immediate answer check. It also starts a deferred scorer that waits for a customer rating or ticket resolution. A step experiment sends the ticket through one of two answer strategies. When feedback arrives, the score points back to the original run and the selected variant. The trace shows the steps that produced the answer.

This lets you answer two different questions: **Did the system produce a valid answer?** and **Did the answer help the customer?** Track both. A successful function run tells you the work finished. The outcome score tells you whether the customer got the result they needed.
